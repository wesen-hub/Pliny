# 微服务治理架构与落地细节

> 状态:定稿(2026-10-11),汇总治理层选型定论与 P4 治理层 M1-M8 实施记录(代码已落地,未部署验证)。
> 定位:讲清治理方案「用了哪些框架、为什么这么选、每个框架落地做了什么配置」——是《微服务架构方案.md》治理章节的展开版,与《监控告警体系设计与落地.md》互为配套(监控在本文只列接入点,细节另文)。
> 配套:拆分原则与 M1-M8 计划版见《微服务架构方案.md》§13.3;M1-M8 实施记录见同文 §13.3a;服务清单见《代码服务清单.md》。

## 一、总体选型逻辑:一套生态 + 减法原则

治理层围绕两条主线拍板:

1. **一套生态到底**:全部走 Spring Cloud Alibaba(Nacos/Gateway/Sentinel 同生态,版本天然对齐,Java 17 + Boot 3 兼容性一致);
2. **减法优先**:能用 SDK 内嵌就不用独立组件(Sentinel 无 Dashboard)、能用轻量就不用重型(Zipkin 非 SkyWalking)、能用最终一致就不用分布式事务(无 Seata)、7 服务规模不上服务网格(Istio 负资产)、不引入 xxl-job(ShedLock 已覆盖互斥需求)。

## 二、治理拓扑

```
外部 → frontend(nginx:静态 + TLS 终结 + /api 反代)→ dcp-gateway(唯一入口)
  ├─ JwtAuthGlobalFilter(order -100):统一验 JWT
  ├─ SentinelRateLimitFilter(order -90):按「路径前缀:QPS」限流
  └─ lb:// 路由分发 → 6 控制面服务(Nacos 注册发现 + Config 配置)
       ├─ Sentinel @SentinelResource 注解限流(内嵌,规则存 yml)
       ├─ ShedLock 定时互斥(元库锁表)
       ├─ Zipkin 采样追踪(Micrometer Tracing + Brave)
       └─ Prometheus 直连抓取 /api/actuator/prometheus(不经网关)
```

## 三、框架逐个展开(为什么选 + 落地配置)

### 1. Nacos — 注册中心 + 配置中心

**为什么选**:替代旧「直连 URL」模式——直连下实例增减要改配置,无法支持自动扩缩容(worker 池弹性伸缩的直接障碍)。选 Nacos 而非 Eureka(停止维护)/Consul(生态割裂),注册与配置二合一,少一个组件。

**落地配置**:

```yaml
# 接入方(6 控制面 + dcp-worker)
spring:
  cloud:
    nacos:
      discovery:
        server-addr: nacos.dcp-infra.svc:8848
      config:
        server-addr: nacos.dcp-infra.svc:8848
        file-extension: yml
```

- 六控制面 + dcp-worker 直连 URL 全部换 `lb://` 服务名;Nacos Config 接入(bootstrap.yml + app-config 配置集),敏感项(etcd 地址/worker.bundles/目标库连接)经 env 覆盖;
- Nacos 独立 ×3 集群(4C/8G);
- **双轨并存(边界)**:compose 本地关发现(`SPRING_CLOUD_NACOS_DISCOVERY_ENABLED=false`),容器名直连仍是本地缺省——生产走 Nacos、本地走直连。

### 2. Spring Cloud Gateway(dcp-gateway)— 统一 API 网关

**为什么选**:平台唯一入口,集中承载 JWT 鉴权、路由、限流三件事,鉴权收敛一处,控制面不再各自验签。选 Gateway(WebFlux 响应式)而非 Zuul(阻塞式弃用);×2 无状态实例(8C/16G)。

**落地配置**(过滤器 + 路由表):

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: outlet-control
          uri: lb://dcp-outlet-control
          predicates: [Path=/api/outlet/**]
        - id: delivery
          uri: lb://delivery-service
          predicates: [Path=/api/chg/**, /api/outlet/contracts/**]
        - id: subscription
          uri: lb://subscription-service
          predicates: [Path=/api/data-sub/**]
        - id: asset
          uri: lb://asset-service
          predicates: [Path=/api/asset-catalog/**, /api/lineage/**]
        - id: tagengine
          uri: lb://tagengine-service
          predicates: [Path=/api/tagengine/**, /api/data-policy/**]
        - id: backend
          uri: lb://backend
          predicates: [Path=/api/**]          # 主控制面兜底,放最后
```

- `JwtAuthGlobalFilter`(order -100):白名单放行登录/actuator/agent 回调,其余验 JWT(拍板:网关统一验签);后端各服务保留自身过滤链(secret 同源);outlet/delivery 无用户 JWT 链,compose 不注入 secret;
- `SentinelRateLimitFilter`(order -90):「路径前缀:QPS」最长前缀匹配,超限 429;
- **base-path 细节**:6 业务服务 actuator 统一挪到 `/api/actuator` + 网关白名单 `ANY:/api/actuator/**`;gateway 自身保持 `/actuator`——若设 `/api/actuator` 会与 `Path=/api/**` 兜底路由冲突被转发到 backend。

### 3. Sentinel — 熔断限流

**为什么选**:流量防护要进网关(入口限流)也要进控制面(接口级熔断,目标库故障降级)。**全内嵌、无 Dashboard**——否决 Sentinel Dashboard(多一个容器 + 规则存外部,与「规则进代码、跟发布走」的诉求相反)。

**落地配置**:

```yaml
# 规则声明式存 application.yml,随代码版本走
dcp:
  sentinel:
    flow-rules:
      - resource: outletList              # 对应 @SentinelResource(value="outletList")
        grade: QPS
        count: 200
```

```java
@SentinelResource(value = "outletList", blockHandler = "outletListBlock")
public List<Outlet> outletList(...) { ... }
```

- WebFlux 纪律:`SphU.entry/exit` 同线程同步完成、不跨 reactor 持有 Entry,规避 ThreadLocal 跨线程丢失;
- 熔断语义:blockHandler 返回降级结果而非抛错,保护下游目标库。

### 4. ShedLock — 定时任务互斥

**为什么选**:多实例部署后定时任务(对账/巡检/文件同步触发)会被每个实例各跑一遍。ShedLock 用元库一行锁记录保证同一时刻只有一个实例执行,替代旧内存态 running map(仅单实例有效)。不引入 xxl-job:新组件 + 新 DB + 改造大,ShedLock 已覆盖互斥需求。

**落地配置**:

```java
@Scheduled(cron = "0 */5 * * * *")
@SchedulerLock(name = "outletStackCollect", lockAtMostFor = "4m", lockAtLeastFor = "1m")
public void collect() { ... }
```

- 锁载体:元库 MySQL shedlock 表(JDBC 模板 LockProvider,单条 SQL 原子抢锁);
- 覆盖点:backend 历史已有(cronTrigger/filesync autoTick/lakesync flush);M3 补 delivery OutletStackCollector 对账 tick。

### 5. Zipkin — 链路追踪

**为什么选**:跨服务调用链定位(backend→outlet-service 提交、控制面→dcp-worker REST)。**Zipkin 而非 SkyWalking**——SkyWalking 需 OAP+ES 重型底座,7 服务规模不值。

**落地配置**:

```xml
<!-- 7 个 Spring 服务统一 -->
<dependency>io.micrometer:micrometer-tracing-bridge-brave</dependency>
<dependency>io.zipkin.reporter2:zipkin-reporter-brave</dependency>
<dependency>io.zipkin.reporter2:zipkin-sender-urlconnection</dependency>
```

- **显式加 zipkin-sender-urlconnection**(防 Boot 3.2/3.3 运行时缺类坑);
- agent 非 Spring,手写 Brave:`AsyncReporter` + `URLConnectionSender` + shutdown hook flush;
- sampling 1.0(开发口径)、b3_multi 传播;tracing 为旁路,服务不 depends_on zipkin。

### 6. Prometheus + Grafana — 监控

**为什么选**:指标监控事实标准,Actuator 原生暴露。**Prometheus 容器网络直连抓取、不经网关**——监控链路与业务链路物理分开,网关挂了监控不受影响。

**落地配置**:

```yaml
management:
  endpoints:
    web:
      exposure:
        include: prometheus,health
      base-path: /api/actuator    # 6 业务服务统一
```

- 7 服务 micrometer-registry-prometheus;网关白名单放行 `ANY:/api/actuator/**` 供抓取;
- 指标三层(应用层 JVM/HTTP/连接池、中间件 exporter、基础设施)与告警规则细节见《监控告警体系设计与落地.md》。

## 四、明确不引入的三项(「不选型」也是选型)

| 组件 | 为什么不用 | 替代机制 |
|---|---|---|
| Seata(分布式事务) | 平台是最终一致架构,跨库写靠对账/幂等收敛 | 唯一键 + 幂等 + 写 API 对账(元库跨域更新走「写 API + 对账」而非 2PC) |
| Istio/Linkerd(服务网格) | 7 服务规模是负资产;全 Java 栈 SDK 内嵌治理已闭环 | SDK 内嵌(Nacos/Sentinel/Zipkin) |
| xxl-job(调度中心) | 新组件 + 新 DB + 改造大 | ShedLock 已覆盖互斥需求 |

## 五、M1-M8 落地记录摘要(代码已落地,未部署验证)

| 项 | 落地形态 | 关键决策/与计划差异 |
|---|---|---|
| M1 Nacos | 六控制面 + dcp-worker 换 `lb://` 服务名;Nacos Config 接入,敏感项经 env | compose 关发现,容器名直连为本地缺省,双轨并存 |
| M2 Gateway | JwtAuthGlobalFilter(-100) 白名单放行登录/actuator/agent 回调;lb:// 路由 | 网关统一验 JWT;后端保留自身过滤链(secret 同源) |
| M3 ShedLock | delivery 对账 tick 加 @SchedulerLock + 元库 shedlock 表 | 只补空白点(backend 历史已有) |
| M4 Sentinel | 全内嵌:网关限流过滤器(-90,超限 429)+ 控制面 @SentinelResource + FlowRuleManager | 无 Dashboard(拍板);WebFlux 不跨线程持有 Entry |
| M5 Prometheus | 7 服务暴露指标;6 业务服务 base-path /api/actuator + 网关白名单;9090 直连抓取 | gateway 自身保持 /actuator(避免与 /api/** 兜底冲突) |
| M6 Zipkin | 7 服务 Brave 三件套(显式 sender);agent 手写 Brave | sampling 1.0;tracing 旁路 |
| M7 MinIO jar_release | LogicArtifactStore 端口 + File/Minio 双实现;sha256 内容寻址缓存 | PutObject 原子 + sha256 内嵌元数据(免 sidecar 两步不一致) |
| M8 编排 | compose 补 prometheus/zipkin;backend 移除 DCP_ETCD;dcp-etcd 保留(dcp-worker 仍用) | Sentinel 无独立容器;SeaTunnel checkpoint 已切 MinIO |

## 六、落地状态与边界(诚实说明)

1. **已落地未验证**:M1-M8 编码完成,部署验证是下一跳——重点测「lb:// 路由 + JWT 验签 + 限流三件套」在真实集群下的行为;
2. **双轨并存**:生产 lb:// 服务名、本地 compose 容器名直连;compose 关 Nacos 发现;
3. **K8s 目标态**:Nacos ×3 进 dcp-infra namespace、gateway ×2 进 dcp-control,入口仍收敛 frontend VIP(MetalLB),gateway 零对外暴露(只 ClusterIP)。

## 七、面试口径(一句话版)

> 治理方案 = Spring Cloud Alibaba 生态做底座(Nacos 注册配置 + Gateway 统一入口 + Sentinel 内嵌限流),外挂三个轻量件(ShedLock 互斥、Zipkin 追踪、Prometheus 监控),明确拒绝 Seata/服务网格/xxl-job——每处选型都有「否决的替代品」作对照,落地形态是「SDK 内嵌、规则进代码、监控独立链路」。
