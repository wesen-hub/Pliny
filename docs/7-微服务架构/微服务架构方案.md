# 数据服务平台微服务架构方案（微服务设计篇）

> 本文档 = 微服务**设计**（拆分依据、维度嵌套划分、代码仓库组织、治理框架选型、改动清单）。实际部署架构方案另文讨论。
> 拆分依据以业界微服务原则为准，不以"谁依赖 etcd"这类实现细节为指导——**"控制面不依赖 etcd"是正确拆分之后的结果，不是拆分的指导原则**。

## 一、设计目标与约束

| 目标 | 对微服务设计的约束推导 |
|---|---|
| PB 级存量数据 | 全链路分区并行、批流分离；写路径与读路径（API）互不干扰 |
| 10万+ qps 吞吐 | 写路径（消费执行）必须拥有独立扩展轴——按分区/吞吐扩缩容，不能与按请求量扩缩容的 API 层耦合 |
| HA 必须 | 每服务有明确的集群形态（LB 多活 / 框架分派 / 引擎自带）；单点清零 |
| 做减法总纲 | 确定性>协调、唯一键>分布式锁、无状态重建>状态复制；不引入 ZK/Redis 协调、不引入分布式事务 |

## 二、拆分原则（业界基准 + 本平台应用）

### 2.1 原则清单

1. **DDD 限界上下文（首要原则）**：一个上下文 = 一套统一业务语言 + 一个内聚领域模型；判断标准——同一术语在两处语义不同，必是两个上下文（例：本平台"任务"在采集域=SeaTunnel 作业、在出口域=消费任务、在打标域=打标任务，语义各不相同）。
2. **独立部署性/变更率对齐**：发布频率、变更原因不同的模块拆开，否则互相阻塞。拆分的根本动机是"能独立修改并部署"。
3. **独立扩展轴（AKF 立方 Y 轴）**：扩展维度不同的模块拆开。API 按请求量扩、写路径按分区吞吐扩——这是拆执行体的正当理由。
4. **故障隔离**：故障半径不同的模块拆开。写路径的目标库雪崩不应拖死管理 API。
5. **数据主权（Database per Service）**：每服务拥有自己的数据，他域只经 API 访问。共享数据库是公认反模式（本平台的取舍见 §七.7）。
6. **团队边界（逆康威定律）**：按期望的组织结构拆，流对齐团队各拥一服务。
7. **横切关注点不拆**：鉴权、日志、监控、告警用共享库/埋点/基础设施解决，不拆成服务。

### 2.2 反模式清单（本平台明确规避）

按技术层拆（controller/service/dao 各一服务）、按实体拆（表对表）、强拆小服务、共享数据库无节制。

### 2.3 关于 etcd 依赖的定位

`etcd` 是"消费执行"上下文的存储（TaskSpec/归属键/快照/租约）。按原则 1/5，消费执行上下文因业务语言不同、存储主权不同而独立成服务，**拆分的结果**自然是"只有执行体依赖 etcd"——它不作为拆分依据写入原则。

## 三、现状问题（为什么必须拆）

| # | 问题 | 违反的原则 | 后果 |
|---|---|---|---|
| 1 | backend 八域混居：写库执行体（SyncConsumer，10万 qps 写路径）与 API 层同进程 | 独立扩展轴/故障隔离 | 资源挤压、扩缩容耦合、API 延迟被写路径拖累 |
| 2 | 出口域横跨 backend（63 文件）与 outlet-service 两个服务；订阅、打标、资产同仓 | 限界上下文 | 域分裂，多处 API 出口，模型漂移 |
| 3 | 打标流是独立 Flink 作业、湖同步仍是 Spark 批、事件投递入站消费组自治 | 上下文模型不统一 | 重复造"分派/防双/扩缩容"轮子，HA 能力缺失 |
| 4 | 定时任务无互斥、jar 仓库本地文件、Flink 提交非幂等、业务 jar 依赖宿主提供 | 部署性 | 集群部署障碍（全链路 HA 审计结论） |

## 四、整体架构（三层 + 执行分层关系）

```
┌─ 控制面服务（无状态 API，LB 多活，不依赖 etcd）────────────────┐
│ backend / outlet-service / delivery-service / subscription-   │
│ service / tagengine-service / asset-service                    │
└──────────────────────────────────────────────────────────────┘
        │ 任务提交走 dcp-worker REST（框架管理 API）
        ▼
┌─ 执行体：dcp-worker（纯宿主，唯一依赖 etcd 的服务）─────────────┐
│ 宿主 = scheduler-core 骨架 + BundleAssembler + 白名单 ClassLoader│
│ SPI 装载业务 jar：dcp-synclink / dcp-indexer-rt / dcp-outlet-rt │
└──────────────────────────────────────────────────────────────┘
        │ 消费 Kafka
        ▼
┌─ 作业集群（作业托管，非微服务）────────────────────────────────┐
│ SeaTunnel Zeta（采集）· Spark（湖批/打标批/快照）·              │
│ Flink（打标流，过渡形态）· agent（边缘文件采集）                 │
└──────────────────────────────────────────────────────────────┘
```

**执行分层关系（核心定论）**：

```
业务域（维护自己的逻辑 jar + 管理面）
   │ 业务任务提交
   ▼
数据消费底座（通用数据作业执行平台：规划/批流衔接/索引/计算面）
   │ 增量阶段委托
   ▼
消费任务调度框架（调度底座：ns=sync / ns=indexer / ns=outlet）
```

- 业务域只维护逻辑，执行统一交给消费底座 → 调度框架；
- 现有三场景（同步链路/索引器/打标）**已框架化**，非未来规划；
- 打标任务以业务 jar 形态提交给消费底座执行（不新建 ns）；
- 未来数据作业（同步 ES、同步数湖仓）同模式：各自维护逻辑，统一交消费底座。

### 6.2 backend 内部：三维度聚合 + 纪律

backend 横跨 ②⑦⑨ 三个轻量控制面维度，仓库内按维度分模块：

```
backend/
├── module/platform     ← 维度⑨ 平台管理
├── module/ingest       ← 维度⑧ 数据接入控制面
└── module/synccontrol  ← 维度② 同步编排控制面
```

纪律：**三个模块互不调用、不共享业务类**（只共享 platform 提供的横切件：auth 上下文、审计日志）；任一维度变更率升高，模块整体搬出成独立仓库即可，边界已预切。

### 6.3 维度间横向引用规则（三级白名单）

| 允许 | 例子 | 不允许 |
|---|---|---|
| 契约级（零依赖） | 业务 jar → dcp-scheduler-api | 业务 jar → 他维业务类 |
| 任务契约级 | dcp-tag-task/dcp-lake-task/dcp-sub-push → outlet-sdk | 控制面 → EtcdStore |
| 内核级 | 批/流/任务 → dcp-tag-kie | 业务 jar → 宿主类 |

控制面间一律 REST/事件通信；执行态统一经①调度框架或③消费底座，**没有任何业务 jar 直接依赖其他业务维度的代码**。

### 6.4 编译依赖图（组织核心约束）

```
dcp-scheduler-api（零依赖）
  ▲provided  ▲provided  ▲provided
dcp-synclink dcp-indexer-rt dcp-outlet-rt dcp-filesync-rt ──内含──▶ outlet-sdk
                                     ▲provided
              dcp-tag-task（依赖 dcp-tag-kie）/ dcp-sub-push / dcp-lake-task（二级 jar）
dcp-scheduler-core ─▶ api
dcp-worker ─▶ core + api（pom 无任何业务 jar 坐标）
控制面六服务 ──HTTP──▶ dcp-worker REST
批/流作业（tagengine-executor/dcp-tagstream）──▶ dcp-tag-kie
```

**依赖纪律（三条铁律）**：
1. 业务 jar 只 `provided` 依赖 api/outlet-sdk，其余依赖全打进 fat jar（child-first 加载，白名单强制 parent-first：契约包 + slf4j 绑定，防 ClassCastException）；
2. dcp-worker pom 不出现任何业务 jar 坐标——装配靠运行时 MinIO 拉取（jar_release 版本登记 + sha256 校验 + 版本绑定）；
3. 控制面不引 EtcdStore——TaskSpec 提交走 dcp-worker REST（POST /tasks、DELETE /tasks/{id}、PUT /tasks/{id}/phase），namespace/规则/审计 API 随 core 迁入 dcp-worker。这是"控制面无 etcd"的代码落点。

### 7.2 执行体（dcp-worker + 业务 jar）

| 维度 | 设计 | 为什么 |
|---|---|---|
| 形态 | **一镜像一骨架多 ns**：ExecutorProvider 注册 sync-writer/anchor-sampler/outlet-task/filesync-runner；env 声明 ns 集合与容量 | 框架 `InstanceConfig` 原生支持一实例多 ns、每 ns 独立容量/租约/竞选资格——池化是框架设计原意 |
| 来源 | **纯宿主零业务代码**：业务 jar（dcp-synclink/dcp-indexer-rt/dcp-outlet-rt/dcp-filesync-rt）独立仓库 fat jar，SPI 装载 | 代码组织与运行形态分离：业务逻辑属于业务维度仓库，运行时合体在宿主 |
| 依赖 | etcd、Kafka、MinIO（拉 jar） | etcd 仅此一服务依赖 |
| 集群形态 | 框架分派（etcd 选主+归属键）；**按池部署**：写库池/采样池/出口池/filesync 池，池间物理隔离、池内框架分派 | 池间隔离故障半径与资源，池内框架自动均衡 |
| 扩展轴 | 每 ns 按分区数/写吞吐独立扩（capacity 槽位+实例上下架） | 10万 qps 写路径的独立扩展轴 |

### 7.3 作业集群与边缘

- **frontend**：nginx 静态 + Gateway 反代，独立部署；
- **SeaTunnel Zeta 集群**：加节点组网（hazelcast member-list）+ checkpoint 共享存储（NFS/S3）——节点宕机作业自动迁移续跑（引擎自带能力，平台侧无分派设计）；
- **Spark 集群**：湖批全量/打标批/出口批快照；
- **Flink 集群**：dcp-tagstream 打标流作业（过渡形态，P2 后由消费底座任务取代）；
- **agent**：业务机侧部署，长轮询 backend，非集群服务。

### 7.4 文件同步框架化（ns=filesync，仅 platform 端到端任务）

文件同步任务按 execHost 分两条通道：
- **platform（端到端直连）**：源=服务端文件系统（MinIO/S3/HDFS/SFTP），目标=平台 MinIO。任务提交 TaskSpec（ns=filesync，partId=taskId#runId），filesync 池实例起 rclone 子进程直连两个 remote 搬运，数据不落业务机——防双/判死/池化由框架统一；
- **agent（业务机本地文件）**：保持长轮询通道，agent 本地跑 rclone、runId 幂等上报。

PB 级端到端部署要点：三级并发（filesync 池 × capacity 槽位 × --transfers/--checkers）；执行体实例高带宽并就近源端或目标端部署；源目标同 S3 端点走 server-side copy（数据不流经执行体）；--bwlimit 逐任务限速 + 调度器错峰；判死重派 + rclone 比较式幂等 = 中断无损续传。

框架最小改造（F1-F3）：一次性任务终态（执行器上报 done→SUCCEEDED 释放槽位）；非 Kafka 任务约定（虚拟 topic，lag 探针跳过）；重试上限（判死重派 N 次→FAILED）。

## 八、调度框架装载机制

### 8.1 契约清单

| 契约 | 定义处 | 使用方 |
|---|---|---|
| PartitionExecutor/Factory/ExecutorContext/ExecutorSnapshot | scheduler-api | 一级业务 jar 实现 |
| ExecutorEnvironment{ kafkaBootstrap(ns), metaDataSource()→javax.sql.DataSource, env() } | scheduler-api | 宿主实现、业务 jar 使用（元库访问不新建连接池） |
| Factory.init(ExecutorEnvironment) 钩子 + @ExecutorPlugin(name) 稳定插件名 | scheduler-api | 装配期注册 |
| ConsumerLogic/LoadedLogic/LogicRef（消费底座任务契约） | outlet-sdk | 二级业务 jar（打标/订阅推送/湖增量/入站） |

### 8.2 装配流程

```
worker.bundles 配置（ns@jar:version）→ MinIO 拉取 → sha256 校验
→ 白名单 ClassLoader（child-first）→ ServiceLoader 发现 Factory
→ Factory.init(ExecutorEnvironment) → 注册 ExecutorProvider（插件名=@ExecutorPlugin）
→ 骨架启动 → resubmitAll（对账遗留任务）
```

### 8.3 两级 SPI

- **一级 SPI（宿主 ← 平台业务 jar）**：dcp-synclink/dcp-indexer-rt/dcp-outlet-rt/dcp-filesync-rt 实现 PartitionExecutor.Factory，框架执行器；
- **二级 SPI（计算面 ← 业务任务 jar）**：dcp-tag-task/dcp-sub-push/dcp-lake-task 实现 outlet-sdk ConsumerLogic，由 UnitRunner 加载（现有 JarLogicLoader 泛化）。

### 8.4 新业务接入（零感知）

新数据作业（如同步 ES）接入 = 新仓 fat jar（依赖 outlet-sdk）+ 发布 jar_release + worker.bundles 加一行 + 滚动重启。宿主/框架/契约零改动。

## 九、任务提交链路（两类）

```
① 平台内建执行器（同步写库）：
backend → dcp-worker REST POST /tasks → etcd → ns=sync 分派 → dcp-synclink 执行

② 消费底座业务任务（打标示例）：
tagengine-service（创建打标任务）
 → outlet-service（规划：批阶段登记/起点表计算）
   → dcp-worker REST → ns=outlet 分派
     → dcp-outlet-rt.UnitRunner → 二级 SPI 加载 dcp-tag-task → TagLogic 求值 → Redis/MySQL
```

## 十、微服务管理框架（部署形态按分支 A）

**前提**：6 个控制面 + 1 执行体服务、Java/Spring Boot 3 栈、当前 Docker Compose（未来可选 K8s）。服务数量少，不上服务网格。

| 能力 | 选型 | 理由与落点 |
|---|---|---|
| 注册发现 | Nacos（Spring Cloud Alibaba） | Java 栈最贴合；六控制面 + dcp-worker 全部注册 |
| 配置中心 | Nacos Config | 多环境配置、动态刷新；worker.bundles/etcd 地址等敏感项移入 |
| API 网关 | Spring Cloud Gateway | 统一鉴权/路由/限流；nginx 退化为前端静态+第一层 LB |
| 熔断限流降级 | Sentinel（或 Resilience4j） | 防级联（目标库故障→控制面不可用）；控制面接口限流 |
| 链路追踪 | Micrometer Tracing + Zipkin（或 SkyWalking） | 跨服务调用链（backend→outlet-service 提交、控制面→dcp-worker REST） |
| 监控 | Prometheus + Grafana | 执行器四计数器→框架快照→采集器→Prometheus；控制面 JVM/接口指标 |
| 日志 | Loki（配 Grafana）或 ELK | 统一日志检索 |
| 定时任务互斥 | ShedLock | 元库锁表单条 SQL 原子抢锁（backend cronTrigger/filesync autoTick/lakesync flush） |
| **不引入** | Seata（分布式事务） | 唯一键+幂等替代分布式事务，元库跨域更新走"写 API+对账"而非 2PC |
| **不引入** | Istio/Linkerd（服务网格） | 7 个服务的规模上服务网格是负资产 |
| **不引入** | xxl-job（调度中心） | 引入新组件+新 DB+改造大，ShedLock 已覆盖互斥需求 |

**引入顺序**（按价值）：① Nacos（拆分后第一天就要）→ ② Gateway（统一入口+鉴权）→ ③ ShedLock → ④ Sentinel（有级联风险后）→ ⑤ Prometheus/Grafana（已有埋点）→ ⑥ 追踪/日志。

## 十四、设计如何支撑 PB 级 / 10万+ qps

| 目标要求 | 设计支撑 |
|---|---|
| 10万 qps 写路径 | dcp-worker 独立扩展轴：按分区/吞吐扩槽位与实例，不与 API 层耦合；框架分派实现分区级并行 |
| PB 级存量 | 批流分离：批全量走 Spark/SeaTunnel 批作业，流增量走框架执行器；湖仓作为数据作业任务（批 Spark + 增量消费底座任务） |
| 写读互不干扰 | 故障隔离+扩展轴分离：写路径雪崩不拖死控制面 API，API 弹性扩缩不连带写路径 |
| 未来作业形态统一 | 消费底座任务通道：新数据作业（ES/数湖仓）只写业务 jar，分派/防双/扩缩容/判死复用 |
| HA | 每服务明确集群形态：控制面 LB 多活（幂等前提）、执行体框架分派、作业引擎自带迁移、etcd 3 节点 raft |
| 协调底座不成为瓶颈 | etcd 只承载调度/选主/分派（低流量协调面），不承载数据路径（数据走 Kafka） |
