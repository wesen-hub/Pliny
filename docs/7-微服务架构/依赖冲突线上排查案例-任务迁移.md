# 线上排查案例:任务迁移引发的多业务 jar 依赖冲突

> 面试案例(口径定稿 2026-10-06):适用于「遇到过哪些线上问题/依赖冲突/疑难杂症怎么排查」类提问。
> 背景锚点:消费底座逻辑仓库惰性加载机制(JarLogicLoader)+ 多业务 jar 共宿主进程。
> 配套设计见《微服务架构方案.md》§8 类加载隔离(白名单 ClassLoader 三层方案)。

## 一句话定位

一次典型的「多 jar 共宿主依赖冲突」事故:两个业务 jar 打包了不同版本的 Jackson,在任务迁移后首次共存于同一实例进程,同名类「谁先加载谁赢」导致打标任务编译期与运行期版本不一致——表现为单实例报错、部分正常、代码与部署均无变更的诡异形态。

## 场景

平台消费底座通过逻辑仓库惰性加载业务 jar:jar 不进任何实例的进程,**直到任务被调度到该实例时才加载**。业务方新增「用户画像同步 ES」任务(es-sync@1.0.0,自带 Jackson 2.13.4),上线后调度到实例 A 运行,一切正常。

运行了几天后,运维接到告警:某个实例的打标任务开始大面积报错,但**其他实例的打标任务都正常**。

## 问题现象

异常实例上打标任务两类报错:

**显性:随机 NoSuchMethodError**

```
java.lang.NoSuchMethodError:
  com.fasterxml.jackson.databind.ObjectMapper.someNewApi()...
  at com.dcp.tagengine.logic.TagLogic.process(TagLogic.java:112)
```

打标代码几个月没动过,编译期一切正常,运行时却报「方法不存在」。

**隐性:字段名策略静默变化**

打标结果里个别字段名的驼峰转下划线策略失效,下游按字段名查询时**查得到数据但值对不上**——没有报错,是静默的数据错乱,比报错更隐蔽。

三个诡异点:① 打标代码几个月没动;② 部署没有变更;③ 同样的打标任务,一部分实例正常、一部分异常。

## 问题定位(四步)

**第一步:排除代码与配置差异。** 对比异常实例与正常实例的打标逻辑版本、配置——完全一致,排除「版本不同步」。

**第二步:打印异常实例进程内的类加载来源(转折点)。**

```
ObjectMapper 来自:es-sync-1.0.0.jar!/com/fasterxml/jackson/databind/ObjectMapper.class
实现版本:2.13.4(打标编译用的是平台统一 2.15.x)
```

**为什么这个实例的进程里会有 es-sync 的 jar?** 其他正常实例进程里没有。

**第三步:查任务调度记录。** 几天前该实例做过一次维护下架,调度框架把它上面的任务重新分配——**es-sync 任务正是这次迁移漂移过来的**。该实例在启动 es-sync 任务时,按逻辑仓库惰性加载机制把 es-sync jar 装进了进程,其自带的 Jackson 2.13.4 在类路径中排在前面,抢占了 Jackson 类加载。

**第四步:对照验证。** 正常实例进程里没有 es-sync jar,Jackson 只有平台 2.15 一份——解释了「部分正常」。临时把 es-sync 任务漂走(或重启实例),异常实例恢复——锁定根因。

## 问题原因

```
① 两个业务 jar(tag-engine、es-sync)共存于同一实例进程,共用同一类加载器
② 双亲委派 + 类路径顺序:同名类「谁排前面谁加载」,es-sync 自带的 Jackson 2.13.4 抢占加载
③ 打标编译期 2.15 vs 运行期 2.13 → 方法签名不一致(NoSuchMethodError)+ 默认行为差异(字段名策略)
④ 冲突的触发条件不是「部署」,而是「两个 jar 首次同实例共存」——
   任务迁移恰好创造了这个条件,所以表现为「运行几天后、单实例、部分正常」的诡异形态
```

一句话根因:**多业务 jar 共宿主时,同名三方库版本冲突,编译期版本与运行期版本不一致,而冲突由任务调度产生的 jar 组合动态决定,不可预测。**

## 问题修复

**止血**:把 es-sync 任务从该实例漂走,实例恢复(分钟级)。

**根治(三层方案,即微服务架构方案 §8.2)**:

1. **加载隔离**:白名单 ClassLoader——业务包 child-first 各加载各的 jar,三方库 parent-first 统一走宿主一份。不管任务怎么迁移、jar 怎么组合,同名三方类都不会再互相抢占;
2. **版本对齐**:宿主显式声明与所有业务 jar 同版本的三方依赖,es-sync 升级到平台统一版本(编译期 = 运行期);
3. **发布管控**:业务 jar 发布带 sha256 校验;新 jar 上线前检查自带三方库版本清单,与宿主不一致的不允许上线。

修复后任务任意迁移、任意组合部署,不再出现版本冲突。

## 复盘沉淀

这个事故暴露的是「**任务迁移会创造新的 jar 共存组合**」:在惰性加载架构下,类路径的构成随调度动态变化,而类加载行为依赖类路径顺序,等于依赖运气。

沉淀的规则:

- 多 jar 共宿主的进程,**加载规则必须确定**(按包前缀分流),不能依赖「哪两个 jar 恰好分到同一个实例」;
- **隔离的粒度按冲突代价决定**:业务代码各用各的(child-first 隔离),底层库必须全局一致(parent-first 统一 + 版本对齐)——JDBC/Kafka 这类有全局状态、跨边界传对象的库不能多版本并存;
- 把「碰运气的部署顺序」换成「确定的加载规则」。

### 追问预案

| 追问 | 回答要点 |
|---|---|
| 为什么运行几天后才炸? | 惰性加载:jar 进进程的时机 = 任务被调度到该实例的时机,不是部署的时机;几天后维护下架触发任务再分配 |
| 为什么部分实例正常? | 只有发生迁移的那个实例进程里同时存在两个 jar;正常实例只有 Jackson 2.15 一份 |
| 方法名差异具体是什么? | 描述为「2.15 新增的 API」即可,不必点死具体签名 |
| 你们隔离怎么做的? | 直接答三层方案:白名单 child-first/parent-first、宿主版本对齐、sha256 发布管控(与《微服务架构方案.md》§8 一致) |

## 附:技术背景速查(面试前复习)

**为什么会发生(两个铁律)**:

- 铁律 1:类的唯一性 = 类加载器实例 + 全限定名;
- 铁律 2:双亲委派(parent-first)——同名类「谁排在类路径前面谁加载」,而类路径顺序由部署/调度行为决定,是运气不是代码。

**三层方案与层级关系**:

- 第 1 层(打包发布):Fat Jar 自包含 + 排除 api 契约 + sha256 校验——决定「字节码放哪、可信吗」;
- 第 2 层(加载分流):覆写 loadClass 按包前缀分流——业务包 child-first(各用各的)、三方库 parent-first(全进程统一)。第 1 层是第 2 层查找规则的物理前提(打进业务类才找得到、排除 api 回落才落得对);
- 第 3 层(版本对齐):宿主显式声明与业务 jar 同版本依赖——保证 parent-first 命中的版本 = 编译版本,NoSuchMethodError 根除。

**与平台真实机制的对应**:逻辑仓库惰性加载(JarLogicLoader.load 按 ref 定位 → sha256 校验 → 独立 ClassLoader → ServiceLoader 发现)、白名单 ClassLoader(WhitelistClassLoader,白名单包前缀 com.dcp.synclink./indexer./outlet.rt./outlet.sdk.)、宿主版本对齐(worker pom 显式声明与业务 jar 同版本三方依赖)。
