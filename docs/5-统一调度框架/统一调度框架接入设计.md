# 统一调度框架 · 三场景接入与 TaskSpec 契约设计

> 状态:设计稿。承接《统一调度框架设计.md》,回答两个问题:① 三种消费场景(同步链路/索引器/数据消费)怎么接入框架;② TaskSpec 契约的精确设计与业务层感知框架的机制。消费底座(数据消费)与现有控制面的结合是重点。

## 一、接入点总览

```
                        ┌─────────────────────────────────────────┐
 同步链路                │ 业务外壳(各自领域代码)                    │
 LogicalTableConfig     │  ① 逻辑表保存事件 → 提交 TaskSpec          │
 Service                │  ② 流扫描新 topic → 提交 TaskSpec          │
                        │  ③ 单元规划/批打底/起点计算 → 提交 TaskSpec │
 索引器                  └──────────────────┬──────────────────────┘
 KafkaAdminStream                            │ 写 TaskSpec + PENDING
 Scanner(流扫描)                             ▼
                        ┌─────────────────────────────────────────┐
 消费底座                │ 统一调度框架(ns 隔离,每 ns 独立选主)        │
 UnitPlanner/           │  ns=sync     ns=indexer    ns=outlet      │
 TaskScheduler/          │  分配/迁移/再平衡/扩缩容/监控/运维           │
 Supervisor             └──────────────────┬──────────────────────┘
 (拆分为外壳+被收编)                        │ watch 对账 → 起/停执行器
                                            ▼
                        执行器(业务实现 PartitionExecutor)
                          sync:embedded 写库 | indexer:embedded 锚点
                          outlet:spi 业务 logic(原 UnitRunner)
```

三场景的差异全部收敛为"业务外壳提交什么 TaskSpec + 执行器里跑什么逻辑",框架本体零改动。

## 二、TaskSpec 契约详细设计

### 2.1 字段模型(五组)

```
① 基础标识(必填)
   namespace      String   sync|indexer|outlet —— 决定任务进哪个 ns 前缀
   taskId         String   业务任务标识(逻辑表名/单元ID/表名),框架仅展示与关联
   topic          String   Kafka topic —— 同 ns 内唯一键(重复提交 = 更新)
   partitions     int      初始分区数 = 初始并发度(框架照此写 N 条 PENDING)
② 并发边界(必填,扩缩容决策域)
   minPartitions  int      缩容下限
   maxPartitions  int      扩容上限 = 最大并发度(业务知识:下游能力)
   targetRps      long     单分区目标吞吐(扩缩容基准:期望分区数 = 流量/targetRps)
③ 执行契约(必填)
   handlerRef     HandlerRef  {type: EMBEDDED|SPI, ref: 执行器名/插件名}
   handover       Handover    AGGRESSIVE(幂等吸收) | CONSERVATIVE(租约双确认)
④ 协作与规则(可选)
   scaleDownHooks HookRef|null  null = 只扩不缩(框架禁用缩容规则)
   scaleRules     ScaleRules    缺省继承 ns 默认值
⑤ 业务元数据(框架不解释,原样透传给执行器)
   bizMeta        Map<String,String>  outlet: 起点偏移表/startTso/logic 版本
```

子结构:

```
HandlerRef { type, ref }   EMBEDDED: ref=框架内置执行器名(sync-writer/anchor-sampler)
                           SPI: ref=插件名(tag-logic-v2.3),实例启动期校验存在
ScaleRules { up:0.8, upPeriods:3, down:0.4, downPeriods:6, cooldownMinutes:10, maxStep:double }
```

### 2.2 etcd 存储形态(key 空间与所有权)

```
/dcp/{ns}/tasks/{taskId}/spec           TaskSpec(JSON)    业务外壳写,框架只读
/dcp/{ns}/tasks/{taskId}/status         任务状态           调度主写,业务外壳可选 watch
   { state: SUBMITTED|RUNNING|DRAINING|GONE, since, reason }
/dcp/{ns}/tasks/{taskId}/parts/{partId} 分区归属记录        调度主写(CAS+epoch),实例骨架 watch
   { partId, owner, state: PENDING|ASSIGNED|MIGRATING|DELETING, epoch,
     handover: { confirmDeadline, sourceOwner } }   // 保守交接判死窗口(持久化,换主可续)
```

### 2.3 变更语义(SOFT/HARD 分级)

| 变更字段 | 语义 | 框架动作 |
|---|---|---|
| min/max/targetRps/scaleRules/hooks | SOFT(决策输入) | 热更新决策,运行中执行器不动 |
| handlerRef / bizMeta / partitions | HARD(执行内容) | 按交接模式重启执行器:停旧线程 → 起新线程(新 ctx) |

handlerRef 运行时更换先校验新执行器可装载(spi 存在性),失败拒绝变更并保留旧版本运行。

## 三、业务层感知机制(含换主)

### 3.1 感知原则:业务层只认 etcd,不认调度主

调度主从不主动通知业务层(拒绝推模式);主只写 etcd,业务层 watch etcd(拉模式)。业务层从头到尾不需要知道主是谁、主换了没有。

### 3.2 业务外壳的感知:可选、窄、只 watch 自己的任务

大部分场景 fire-and-forget(写完 TaskSpec 即结束)。只有三个事件需要订阅:

| 事件 | 用途 | 方式 |
|---|---|---|
| 任务 DRAINING→GONE | outlet 重规划:确认旧单元彻底回收才提交新 epoch 单元(防新旧双跑) | watch 自己任务 status 键 |
| 任务注销完成 | 释放业务侧资源(logic 卸载/扫描条目删除) | 同上 |
| 分区 ASSIGNED(可选) | 上层展示(血缘等) | watch parts 键(只读) |

```java
interface TaskStatusListener {
    void onTaskDraining(String taskId);
    void onTaskGone(String taskId);
    void onPartitionAssigned(String taskId, int partId, String owner);
}
```

容错:外壳对框架事件的 watch 可重试、可容忍秒~分钟级延迟(不在数据面关键路径);etcd watch 按 revision 续传不丢事件。

### 3.3 执行器的感知:start/stop 回调,零 etcd 依赖

执行器是业务代码,不碰 etcd、不 watch 任何东西,只被实例骨架(框架代码)回调:

```java
interface PartitionExecutor {
    void start(ExecutorContext ctx);   // ctx = {taskId, topic, partId, spec 子集(handlerRef+bizMeta+handover)}
    void stop();                       // 迁移/缩容/注销/硬变更重启
    ExecutorSnapshot metrics();        // 框架周期拉取 4 个原始计数器
}
```

框架动作与执行器感知的映射:新分配→start(ctx);迁走/回收/注销→stop();硬变更→stop()+start(新ctx);指标收集→metrics();**换主→无感知**。

### 3.4 调度框架换主:业务层无感的依据(三条不变式)

1. **主无内存态**:决策结果都先落 etcd 再生效,主挂只丢"未决决策",不丢"已生效状态";
2. **归属键写幂等且带 epoch**:新主全量读后基于当前状态 CAS,不可能覆盖旧主已写入结果;
3. **业务层与主零连接**:唯一交互面是 etcd watch,watch 的是"状态"不是"主"。

保守交接窗口内换主:交接中间态(`parts.handover:{confirmDeadline, sourceOwner}`)持久化在 etcd,新主读到期继续判定,交接不中断、不重做、不误判。

## 四、同步链路接入

**改造**:消费线程生命周期从"backend 进程自管"改为"框架托管",写库逻辑原样搬入执行器。

```
① 建逻辑表 → logical_table 落库(不变)
② 外壳(LogicalTableConfigService)提交 TaskSpec(ns=sync, handover=AGGRESSIVE, hooks=bucket_map)
③ sync 调度主打分 → CAS 归属 sync 实例
④ 实例对账 → 起执行器(原 SyncConsumer 逻辑):
   assign → poll → 解包/写者判定/主键拆对 → 路由分表 → 攒批多值 INSERT ODKU
   → 已写游标+1 提交
⑤ 快照上报 → 框架算指标
⑥ 自动扩缩:扩容=Kafka 扩分区+bucket_map 重算+新 PENDING;
   缩容=钩子切路由 → 追平 → 停线程
⑦ 逻辑表删除 → 任务注销 → 回收线程与归属
```

**代码映射**:SyncTopicRegistry 的"一组一 topic 注册+消费组自治"被框架 assign 取代(消费者组保留为位点记账单位);SyncConsumer 收编为 sync-writer 执行器;AtomicUpsertDao/RouteUtil 留在执行器内不变。

## 五、索引器接入(大组 subscribe → 每表一任务 assign)

```
① 流扫描(KafkaAdminStreamScanner/TiCDC 元数据)发现出口新 topic
② 外壳提交 TaskSpec(ns=indexer, handover=AGGRESSIVE, hooks=null 只扩不缩)
③ indexer 调度主分配分区 → 索引器实例起线程
④ 执行器(原 IndexerRunner 解析采样逻辑):
   poll → 提取 commitTs → 单调判定 → 稀疏采样写锚点 → 污染兜底
⑤ 新 topic 自动纳入、停采 topic 注销——走框架任务生命周期
```

收益:大组模式"每表并行度无差别"变为"每表独立并行度/扩缩容/迁移",3 台实例负载框架统一均衡。

## 六、消费底座接入(控制面与框架的结合,重点)

### 6.1 控制面现有组件命运表

| 原组件 | 职责 | 去向 |
|---|---|---|
| UnitPlanner | 按分区数比例(最大余数法)规划单元,单元=分区子集,ID 带 epoch 可重规划 | 留业务外壳:规划结果转 TaskSpec |
| TaskScheduler.onCreated/onBatchDone | 批打底决策、批流交接 T0 | 留业务外壳(业务时序,框架不碰) |
| handover 的"算起点" | StartOffsetService:每分区第一个 commitTs>T0 | 留业务外壳(塞进单元 bizMeta) |
| handover 的"授租约+下发" | 选 worker、独占下发 | 框架收编:归属分配=调度主打分+CAS |
| Supervisor 租约巡检 | 租约过期释放+告警 | 框架收编:实例 lease 判死+快照活性检测 |
| Supervisor 停滞/失联巡检 | UNIT_MISSING 等告警 | 框架收编:快照收不到=卡死 |
| LeaseManager/LeaseGrant | 单元租约授发续约 | 框架收编:合并进"归属+判死窗口" |
| UnitDispatcher | 单元下发(推模式) | 框架收编:改拉模式(watch 对账) |
| UnitRunner(worker) | assign+seek 起点→裁剪→logic.process→提交 | 收编为 spi 执行器(PartitionExecutor) |
| LeaseGuard/Heartbeat | 租约续期/心跳 | 框架替代:实例 lease keepalive+快照上报 |
| MonotonicityGuard/T0Selector/AnchorIndexer | 单调守卫/T0 选择/锚点索引 | 留执行器内部(框架不感知) |
| TaskStore/UnitStore/UnitStatusStore | 元库存储 | 拆分:业务字段留元库;调度状态迁 etcd |
| KafkaAdminStreamScanner | 出口流扫描 | 留业务外壳(索引器/出口任务来源) |

### 6.2 角色划分

```
业务外壳(原控制面保留):任务生命周期/批打底/批流交接 T0/单元规划/起点计算/契约生成
调度框架 ns=outlet(收编):单元归属分配/故障迁移/判死双窗口/交接模式 CONSERVATIVE
worker 执行器(UnitRunner 收编):assign→seek 起点→裁剪→logic.process→提交→快照上报
```

### 6.3 完整流程(端到端)

```
① 任务创建(外壳):TaskRecord 落元库 → startPolicy=snapshot 判断
② 批打底(外壳):BATCH_RUNNING → BatchRunner → 回调 t0
   (失败 → BATCH_FAILED,不猜起点,人工重做批换新 T0——原语义不变)
③ 单元规划(外壳):UnitPlanner.plan(taskId, streams, instances, epoch) → PlannedUnit 列表
④ 起点计算(外壳):StartOffsetService 算每分区"第一个 commitTs > t0 的偏移"
⑤ 契约提交(外壳 → etcd):每 PlannedUnit 一个 TaskSpec(ns=outlet,分区=单元子集,
   min=max 固定,handover=CONSERVATIVE,bizMeta=起点表+startTso+logic 版本)+ PENDING
⑥ 调度(框架):outlet 调度主打分 → CAS 归属 worker → watch 推送
⑦ 执行(worker):对账 → 起执行器:assign 单元分区 → seek 注入起点(不从组位点续)
   → 契约裁剪 → logic.process → 提交 → 快照上报
⑧ 稳态监控(框架):差值算指标 → 单元级自动扩缩禁用(min=max),扩缩由规划驱动
⑨ 故障(框架):worker 挂 → lease 过期 → 保守交接(lease+快照双窗口确认)→ 新 worker 起单元
⑩ 单元级扩缩(规划驱动):重规划(epoch+1)→ 新单元 TaskSpec + 旧单元注销 → 旧单元 DRAINING 回收
⑪ 任务结束(外壳):注销全部单元 → 框架回收线程与 etcd 记录
```

### 6.4 租约机制融合

| 原租约用途 | 框架对应物 |
|---|---|
| 独占下发(防双消费) | 归属唯一性(CAS 单归属) |
| 失联检测(停滞告警) | 快照活性检测(收不到=卡死) |
| 判死确认 | 双窗口:实例 lease 过期(30s)+ 快照 TTL 失效(30s)都满足才改归属 |

框架保守交接比原租约更严格:原方案"租约过期即释放+告警"(可能只是平台没续上),框架"双确认才迁移",避免误判双消费;Supervisor 的 dispatchGraceMillis 语义并入对账 diff 宽限期。

### 6.5 时序图(任务创建 → 单元跑起来 → 故障迁移)

```
控制面外壳        etcd            调度主(ns=outlet)      worker A       worker B
    │               │                    │                  │              │
 ① 批打底完成 t0    │                    │                  │              │
 ② 规划+算起点      │                    │                  │              │
 ③ 写 TaskSpec+PENDING →               │                  │              │
    │               │ ④ 扫到 PENDING    │                  │              │
    │               │ ⑤ CAS owner=A ──→ │                  │              │
    │               │                    │ ⑥ watch 事件     │              │
    │               │                    │────────────────→│              │
    │               │                    │ ⑦ 起执行器:assign│              │
    │               │                    │   +seek 起点     │              │
    │               │                    │   +logic.process │              │
    │               │                    │←──⑧ 快照(10s)───│              │
    │               │                    │ ⑨ 算指标聚合     │              │
    │               │ ⑩ A 宕机,lease 过期│ 双窗口确认死亡    │              │
    │               │ ⑪ CAS owner=B ────────────────────────────────→│ 起单元续跑
```

## 七、三场景接入差异对照

| 维度 | sync | indexer | outlet |
|---|---|---|---|
| 业务外壳 | LogicalTableConfigService | 流扫描 | 原控制面(规划/批流交接/起点) |
| 任务粒度 | 逻辑表(一表一任务) | 出口表(一表一任务) | 单元(分区子集,规划产物) |
| 调度单位 | 分区 | 分区 | 单元(一线程一单元) |
| 起点 | 消费组位点续 | 消费组位点续 | 单元精确起点(seek 注入) |
| 交接 | 激进(ODKU 幂等) | 激进(锚点幂等) | 保守(租约双确认) |
| 扩缩 | 分区级自动(有钩子) | 分区级自动(只扩不缩) | 单元级(规划驱动,epoch 重规划) |
| 执行器 | embedded 写库 | embedded 锚点采样 | spi 业务 logic |
| 批阶段 | 无(批在采集/湖侧) | 无 | BatchRunner 留业务外壳,框架不参与 |

## 八、落地改造清单(按依赖顺序)

1. 框架内核 + etcd 层(纯新):分配/迁移/再平衡纯库 → key 空间与 namespace → 实例骨架;
2. sync 接入(最易,验证最小闭环):SyncConsumer 收编执行器 → 外壳加提交 TaskSpec → sync 实例池;
3. indexer 接入(中等):大组拆每表一任务 → 流扫描外壳 → 3 台实例池;
4. outlet 接入(最难,改存量):UnitPlanner 输出接 TaskSpec → UnitRunner 收编执行器(起点注入保留)→ 控制面拆两角色 → Supervisor 巡检停用 → TaskStore 拆分 → 保守交接双窗口;
5. 监控 + 扩缩容 + 运维后台:三 ns 统一上报聚合,按场景开启规则(sync 自动/indexer 只扩/outlet 规划驱动)。

**边界铁律**:outlet 接入时,控制面的任务级批流交接(BATCH_RUNNING→BATCH_DONE→handover)必须完整保留在业务外壳——框架只负责"交接之后单元怎么跑",永远不知道批阶段的存在。
