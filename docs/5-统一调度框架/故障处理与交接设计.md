# 故障处理与交接设计

> 承接总纲 §八/§十三。细节级:判死双窗口时序、保守交接状态机、换主可续、etcd 故障与脑裂。状态:初版,随讨论迭代。

## 一、判死双窗口(保守交接的核心)

### 1.1 为什么双确认

| 单信号判死的缺陷 | 后果 |
|---|---|
| 只看实例 lease | 平台 GC 停顿/网络抖动导致"没续上"≠实例真死 → 误判 → **双消费** |
| 只看快照 TTL | 执行器忙到 30s 没写快照 ≠ 卡死 → 误判 → **双消费** |

双窗口要求两者**同时**满足,把误判概率压到"实例真死"级别:

```
确认死亡(两条件同时满足):
  ① 实例 lease 已过期(实例 30s 未续租)
  ② 该分区快照 TTL 失效(分区 30s 无快照,且无 stopped 帧)
```

### 1.2 精确时序

```
t0    实例 A 宕机(最后一次续租/快照停在 t0)
t0+30s lease 过期:主在决策循环发现 A 失联 → A 标 SUSPECT
      快照 TTL 亦在 t0+30s 失效
t0+30s 双条件满足 → 主发起保守交接(阶段一):
        parts 改 MIGRATING, handover={sourceOwner:A, confirmDeadline:t0+90s}
       (confirmDeadline = 兜底截止:即便中间态下又换主,交接也必须在此时限内收口)
t0+30s~90s 期间:
       · A 若复活续租:交接回滚(MIGRATING→ASSIGNED owner=A,handover=null),零迁移
       · A 持续死亡:双确认持续成立
t0+90s(或确认成立的下一决策周期):
       主执行阶段二:MIGRATING→ASSIGNED owner=B,handover=null
       实例 B watch 到 → 对账 → 起执行器(从提交位点续)
```

**为什么设 confirmDeadline 兜底**:交接窗口内若再次换主,新主读 handover 记录继续判定——但判定需要一个"最迟收口时间",否则交接态可能永久悬挂;deadline 到期即视为确认(此时即便 A 复活,也要先完成迁移,A 侧的线程由其 watch 到归属变更后自停,双消费风险由"deadline 时长 ≥ 双窗口时长"约束)。

### 1.3 交接状态机(PartRecord.handover)

```
ASSIGNED(owner=A)
   │ 双条件满足(主决策)
   ▼
MIGRATING(owner=A, handover={A, deadline})
   │
   ├─ A 复活续租且快照恢复 → 回滚:ASSIGNED(owner=A)      [亲和保留]
   ├─ 双确认持续 + deadline 到期 → ASSIGNED(owner=B)      [正常完成]
   └─ B 也失联(写入时发现)→ 改 PENDING → 重新分配          [退化路径]
```

## 二、保守交接 vs 激进交接

| 维度 | AGGRESSIVE | CONSERVATIVE |
|---|---|---|
| 判死要求 | lease 过期即可 | lease 过期 + 快照失效双确认 |
| 中间态 | 无(直接改归属) | MIGRATING + handover 记录 |
| 迁移时延 | ~30s(一个 lease 周期) | ~90s(双窗口+兜底) |
| 双消费窗口 | 存在(业务幂等吸收) | 无(确认死亡才转移) |
| 适用 | sync(ODKU)/indexer(锚点) | outlet(打标无幂等) |
| 交接态换主 | 无状态可丢 | handover 持久化,新主读到期续判 |

## 三、故障处置全表

| 故障 | 检测(时延) | 处置 | 恢复后行为 | 影响 |
|---|---|---|---|---|
| 实例宕机 | lease 过期(30s) | 判死(按模式)→ 分区迁移 | 复活后重新注册,按剩余归属对账 | 分区中断 ~1min |
| 执行器卡死 | 快照 TTL(30s) | 活性告警 → 按模式迁移该分区 | 实例不重启的话,该分区在别处跑 | 单分区中断 ~1min |
| 主宕机 | leader lease(30s) | 竞选换主 → 全量读恢复 | 旧主复活=普通实例(角色降级) | 决策停顿 10s 级 |
| 交接窗口内换主 | — | 新主读 handover → deadline 续判 | 交接不中断不重做 | 零影响 |
| etcd 不可用 | 写失败/watch 断开 | **执行器继续跑**(归属冻结),主暂停决策 | 恢复后:主重读、实例重连 watch,对账收敛 | 有吞吐无调度 |
| 网络分区(主侧) | lease 续不上 | 旧主退位,新主当选;旧主写因 CAS 失效 | 分区恢复后旧主发现已降级 | 短暂决策停顿 |
| 网络分区(实例侧) | lease 过期 | 按实例宕机处置(分区迁移) | 网络恢复后实例对账,发现自己不再持有 | 可能短时双消费窗口(保守模式无) |
| 缩容追平超时 | deadline(10min) | 告警 + 人工介入 | 人工决定继续等待或回滚路由 | 待缩分区悬置 |

## 四、etcd 故障的精确行为(保守策略)

```
检测:etcd 写失败(带重试退避)或 watch 流断开
主:   停止一切"改归属"类决策(分配/迁移/缩容推进);保留检测与日志
实例: 执行器线程继续跑(已 start 的不停);lease 续租/快照续写继续尝试(缓冲本地)
      对账 diff 冻结(不 stop 不 start——没有新的归属事实)
恢复: 主重连 → 全量读 → 决策恢复;实例重连 watch(带 revision 续传,不漏事件)
      → 对账 diff 重算 → 收敛到 etcd 最终态
不变式:任何时刻执行器只由"当前归属键"驱动;etcd 不可用期间归属键不变,故执行器安全。
```

**为什么不是"etcd 不可用就全停"**:消费链路的可用性依赖归属键的稳定性而非 etcd 的实时性;冻结决策即可保证"不双消费 + 不丢吞吐",全停反而把 etcd 的故障放大成整个数据面的故障。

## 五、脑裂防护(双层)

```
第一层(主层):leader lease 决定唯一主——旧主 lease 续不上自动退位,
  即便旧主不自知(网络分区),它的所有写事务都带 epoch 条件,
  新主已写入的键 epoch 已变,旧主写必然 CAS 失败。
第二层(执行层):实例启动执行器前检查"归属键 owner 是否仍是我"(start 前断言),
  归属已改则拒绝起线程——防御"实例与主之间网络分区,实例自以为仍持有"。
```

## 六、与存量控制面的差异点

| 场景 | 原控制面 | 框架 |
|---|---|---|
| 单元失联 | 租约过期 → 释放 + **告警人工处理** | 双窗口判死 → **自动迁移** |
| 停滞检测 | 5min 才告警 | 30s TTL 检测 + 自动迁移 |
| 主故障 | 单点(无选主) | 每 ns 独立选主,秒级恢复 |
| 下发通道 | 推模式(dispatcher) | 拉模式(watch 对账),断连自愈 |
| 交接状态 | 主内存(重启即丢) | 持久化在归属记录,换主可续 |
