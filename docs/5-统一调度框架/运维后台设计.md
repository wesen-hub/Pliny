# 运维后台设计

> 承接总纲 §十二。细节级:页面组织、操作语义、权限模型、与前端原型的对应。状态:初版,随讨论迭代。

## 一、页面组织维度

**根组织维度 = namespace**(不是实例、不是任务)。所有管理行为都从 ns 下钻:

```
菜单:总览 / Namespace / 任务与分区 / 扩缩容 / 监控 / 运维操作

Namespace 页
  ├─ ns 列表(场景/任务数/实例数/分区数/总 rps/总 lag)
  └─ 行展开:
      ├─ 实例管理 tab:该 ns 实例表(状态/负载/CPU/槽位)+ 下架/权重/暂停操作
      └─ 默认扩缩规则 tab:ScaleRules 表单 + ns 级缩容总开关

任务与分区页(列表逐级下钻 + 面包屑)
  ns 列表 → 任务列表 → 实例列表 → 分区列表
  每层带各自维度监控指标:
    ns 层:计数+总量;任务层:rps/lag/水位;实例层:聚合+机器指标(JVM 扩展位);
    分区层:rps/lag/latency/errorRate

扩缩容页
  ├─ ns 级默认规则卡(每 ns 一张)
  ├─ 任务级规则表(覆盖值 + 钩子标注"有(任务维度)/无(只扩不缩)")
  └─ 缩容三步演示 + 扩缩事件历史

监控页:ns/任务/实例/分区四级大盘 + 告警事件流
运维操作页:操作记录(审计)+ 待处理指令(扩容建议/追平超时)
```

## 二、操作语义(逐项精确化)

### 2.1 ns 管理

| 操作 | 前置 | 效果 | 边界 |
|---|---|---|---|
| 创建 ns | 无 | 初始化 rules 键 | ns 名即 etcd 前缀,创建后不可改 |
| 删除 ns | 无任务、无实例 | 清空前缀 | 有残留时拒绝并提示 |
| 改默认规则 | 无 | 更新 rules 键 | 只影响"未覆盖的任务" |
| 缩容总开关 | 无 | downEnabled | 关闭后所有任务缩容被闸住 |

### 2.2 任务管理

| 操作 | 前置 | 效果 | 边界 |
|---|---|---|---|
| 查看契约 | — | spec 全字段只读 | 业务元数据 bizMeta 对后台只读 |
| 注销任务 | 确认 | 删 spec → DRAINING | 业务资源释放由外壳 watch GONE 自行处理 |
| 立即扩容/缩容 | 冷却检查 | 走编排流程 | 缩容仍需双闸门 |

### 2.3 实例管理(ns 维度内)

| 操作 | 效果 | 语义 |
|---|---|---|
| DRAINING 下架 | 实例不再接单,已有分区逐步迁出 | 迁空后可安全关机 |
| 取消下架 | 恢复接单,已迁出的分区不回流 | 亲和项让回流低概率 |
| 调权重 | 0.5~2.0,影响迁移目标打分 | 用于流量倾向性调配 |
| 暂停接单 | paused=true,不影响已跑分区 | 维护窗口用 |

### 2.4 分区管理

| 操作 | 效果 |
|---|---|
| 手动迁移 | 选目标实例(对话框带目标负载/CPU/权重)→ 按任务交接模式迁移 |
| 钉住(PIN) | 分区固定在当前 owner,算法不再动它;可选 TTL(1h/1d/7d/永久),到期自动解锁 |
| 解锁(UNPIN) | 解除锁,恢复算法管理 |
| 定向迁移+钉住 | 迁移到指定实例并钉住(复用交接机制,详见子文档⑧ §五) |
| 观察 | 分区状态(PENDING/ASSIGNED/MIGRATING/DELETING)+ 四指标 + 锁标记 |

## 三、操作记录(ops 键与审计)

```json
/dcp/{ns}/ops/{opId} {
  type: MIGRATE | DRAIN_INSTANCE | PAUSE_INSTANCE | SET_WEIGHT
      | MANUAL_SCALE_UP | MANUAL_SCALE_DOWN | DELETE_TASK | SET_RULES
      | PIN | UNPIN | MIGRATE_PIN,
  target, params, operator, state: PENDING | DONE | FAILED | EXPIRED, detail
}
```

- 后台写 PENDING → 主消费执行 → 回写 DONE/FAILED;
- 钉住/解锁/定向迁移同样走 ops 队列,由主消费执行(归属键唯一写者是主,后台不直接写 parts);
- 全部操作落审计(不可变,保留 30 天):谁、何时、对什么、做了什么;
- 操作冲突:同一对象(如实例)同时有未完成的 op 时,后台拒绝新 op。

## 四、权限模型(ns 级)

```
角色:平台管理员(全 ns)/ ns 运维(单 ns 读+操作)/ 观察者(只读)
权限点:ns:view · ns:edit(rules/开关) · task:view · task:delete
       · inst:manage(下架/权重/暂停) · part:migrate · scale:trigger
最小原则:观察者看不到其他 ns 的任何数据(etcd 前缀即权限边界)
```

## 六、后台的三个边界(定论)

1. **实例的 ns 归属列表 = 部署属性**:后台不提供运行时改归属(改归属 = 改配置重启);实例管理(下架/权重/暂停)仍按 ns 维度逐个进行,互不影响;
2. **钩子 = 业务代码**:后台只能触发与观察,不能编写、不能模拟;
3. **后台管触发与观察**:决策权在框架(规则)+ 业务(钩子),后台是管理面不是决策面——人工操作本质是"给框架发 op",不是"替框架做决定"。
