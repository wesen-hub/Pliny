# 监控与告警设计

> 承接总纲 §十。细节级:指标协议、派生公式、聚合管线、活性检测、告警规则。状态:初版,随讨论迭代。

## 一、指标分工原则

**业务零指标概念**:业务只维护四个随手计数器(累计值),框架统一派生所有指标。业务侧唯一义务是"如实累计"——条数、位点、错误数、耗时;任何口径(什么是 rps、lag 怎么算)都由框架定义。

## 二、快照协议(数据入口)

```
执行器 → 实例骨架 → etcd /dcp/{ns}/tasks/{taskId}/parts/{partId}/snap

ExecutorSnapshot {
  ts, taskId, partId,
  processedCount,   // 累计处理条数(提交成功才算)
  committedOffset,  // 已提交位点(消费组语义由执行器维护)
  errorCount,       // 累计错误条数(业务定义:处理失败/污染丢弃等)
  totalLatencyMs    // 累计处理耗时(从 poll 到提交完成的墙钟时间)
}
周期:10s 续写一次;TTL 30s(续写行为本身=活性信号)
```

约定:

- 快照只续写**累计值**,框架做差值——累计值天然容错(丢一帧只影响一个窗口的精度,不影响趋势);
- 执行器停止时写最后一帧(带 `stopped=true`),主据此区分"主动停"与"卡死";
- 快照体积恒定(几十字节),etcd 压力 = 分区数 × 每 10s 一次写,可承受。

## 三、派生指标公式(精确化)

设相邻两帧快照 s1(ts1)、s2(ts2),Δt = ts2 − ts1(约 10s):

```
rps        = (s2.processedCount − s1.processedCount) / Δt          // 条/秒
lag        = endOffset(partId, 实查 Kafka) − s2.committedOffset     // 条
errorRate  = (s2.errorCount − s1.errorCount) / (s2.processedCount − s1.processedCount)
avgLatency = (s2.totalLatencyMs − s1.totalLatencyMs) / (s2.processedCount − s1.processedCount)
```

实现细节:

- `endOffset` 由主(或监控组件)以 Kafka Admin API 周期实查(60s 一次,或按需),lag 在快照帧之间线性插值;
- 分母为 0(无流量)时:errorRate/avgLatency 置 null(展示为"—"),rps=0;
- 窗口平滑:展示用 3 帧滑动平均(30s),判定(告警/扩缩)用原始窗口+持续期,不混用;
- 快照乱序/重复(重试写):取最大 ts 帧为准,差值按 ts 排序后计算。

## 四、聚合管线(四级)

```
分区快照(10s)
   │ 派生
   ▼
分区指标:rps/lag/latency/errorRate/状态             ← 分区维度(执行器直接产出)
   │ Σ(同一实例)
   ▼
实例指标:聚合 rps/Σlag/均值 latency/均值 errorRate
        + 机器指标(cpu/mem/load/jvmThreads,实例 meta 10s)   ← 实例维度
   │ Σ(同一任务)
   ▼
任务指标:总 rps/总 lag/容量水位(flow ÷ (parts×targetRps))   ← 任务维度
   │ Σ(同一 ns)
   ▼
ns 指标:任务数/实例数/分区数/总 rps/总 lag                  ← ns 维度大盘
```

**实例维度监控指标的构成**(与前端展示一致):

| 类别 | 指标 | 来源 |
|---|---|---|
| 业务聚合 | 聚合 rps、聚合 lag、平均 latency、平均 errorRate | 该实例所有执行器快照求和/求均 |
| 机器指标 | CPU%、内存%、负载、JVM 线程数 | 实例进程自报(meta) |
| JVM 级(扩展位) | GC 次数/GC 耗时/堆使用/线程池状态 | **后续扩展**,同样走快照/meta 通道,业务侧零感知 |

## 五、活性检测(三级)

```
① 执行器活性:分区 snap 键 TTL(30s)失效 = 执行器卡死(未写 stopped 帧)
   → 告警 + 按交接模式迁移该分区
② 实例活性:实例 lease(30s)过期 = 实例失联
   → 实例标 SUSPECT → 判死双窗口 → 迁移其全部分区
③ 主活性:leader lease 过期 = 主挂/假死
   → 其他实例竞选接管(业务层无感)
```

## 六、告警规则(缺省)

| # | 告警 | 条件 | 级别 | 处置建议 |
|---|---|---|---|---|
| 1 | 分区 lag 高位 | lag > rps×5,持续 3min | warning | 观察扩缩决策是否已触发 |
| 2 | 错误率超阈值 | errorRate > 1%,持续 3min | critical | 检查业务逻辑/数据质量 |
| 3 | 执行器卡死 | snap TTL 失效(无 stopped 帧) | critical | 框架自动迁移,告警留痕 |
| 4 | 实例失联 | lease 过期 | critical | 框架自动判死迁移 |
| 5 | 追平超时 | 缩容追平 > 10min | warning | 人工介入(不自动回滚) |
| 6 | 容量水位 | 任务水位 > 0.9 且 parts=max | critical | 业务上调 maxPartitions |
| 7 | 迁移失败 | MIGRATING 超 deadline 未完成 | critical | 检查双窗口条件/实例状态 |
| 8 | 无可用实例 | PENDING 积压 > 3 周期且无候选 | critical | 扩容实例池 |

告警实现:

- 分级与去重:同一告警对象(分区/实例/任务)同一级别 10min 内只发一次,状态变化(恢复)补发恢复通知;
- 告警通道:推送 AlertSink(外部告警系统)+ 写告警事件流(后台页面可见);
- 告警阈值除内置缺省外,支持 ns 级覆盖(规则键)。

## 七、指标存储与查询

| 数据 | 存储 | 保留 |
|---|---|---|
| 快照(原始) | etcd snap 键(滚动覆盖) | 仅当前帧(TTL 30s) |
| 分区级时序 | 监控组件内存 + 落盘(可插拔:Prometheus/自研) | 7 天(可配) |
| 聚合大盘 | 监控组件 | 7 天 |
| 告警事件 | 告警系统/后台库 | 30 天 |

## 八、与存量监控的对应(消费底座)

| 现存量 | 框架对应 |
|---|---|
| Heartbeat/LeaseBackedHeartbeat(worker 心跳) | 实例 lease + 快照续写(合并) |
| UnitStatusStore(单元状态) | parts 归属状态 + snap 活性 |
| Supervisor 停滞巡检(stall 5min) | 快照 TTL 失效检测(30s,更灵敏) |
| AlertSink | 框架告警事件流 → 同一 AlertSink |

**灵敏度对比**:原停滞检测 5min 才告警;框架活性检测 30s(TTL)即可发现执行器卡死,且可自动迁移——故障自愈能力显著提升。
