# 手动钉住与锁机制设计

> 承接总纲 §六(调度算法)与 §十二(运维后台)。细节级:Pin 数据模型、锁语义矩阵、冲突裁决、手动迁移编排、ops 通道。状态:初版,随讨论迭代。

## 一、为什么需要锁

自动调度算法回答"分区应该在哪个实例上"的稳态最优问题;但运维场景存在需要"违背算法、固定归属"的诉求:

| 场景 | 诉求 |
|---|---|
| 线上问题排查 | 把分区钉在指定实例上隔离观察 |
| 流量保障 | 重要分区固定在主力实例,免受再平衡/迁移扰动 |
| 版本灰度 | 新版本实例只跑被钉过来的分区 |

**锁的本质:运维意图优先于算法最优。** 算法在一切"动归属"的环节对锁让步;但锁不豁免故障语义——钉住的实例死了如何处置,见 §四 冲突裁决。

## 二、Pin 数据模型

钉住信息放在 **PartRecord 内**(归属键单键原子),而不是独立键——锁的生效与归属的变化必须原子一致,不存在"锁与归属不同步"的中间态:

```json
{
  "partId": 3, "owner": "inst-a", "state": "ASSIGNED", "epoch": 12,
  "handover": null,
  "pin": {
    "pinnedTo": "inst-a",
    "pinnedAt": 1790678148910,
    "expiresAt": null,
    "reason": "排查 p3 延迟毛刺,钉在 inst-a 观察"
  }
}
```

| 字段 | 含义 |
|---|---|
| `pin` | null = 无锁,受算法自动管理 |
| `pinnedTo` | 钉住目标实例 id |
| `pinnedAt` | 钉住时间 |
| `expiresAt` | null = 永久锁;有值 = TTL 锁,到期自动解锁 |
| `reason` | 运维备注(为什么钉) |

**为什么锁要带 TTL(可选)**:永久锁 + 目标实例死亡 = 分区永远卡死,只能靠人想起来解锁。TTL 锁把"钉死"变成"钉一段时间"(1h/1d/7d/永久),到期框架自动解锁回到算法管理——运维失误成本从"分区停摆"降为"短暂停摆后自愈"。

## 三、锁语义矩阵:算法各环节如何让步

| 决策环节 | 无锁分区 | 有锁分区 |
|---|---|---|
| 补全分配(PENDING) | 打分选实例 | **定向分配**:只允许给 `pin.pinnedTo`;目标不存活/不可接单 → 留 PENDING 并告警 |
| 判死交接(owner 死了) | 正常交接 | 按 §四 冲突裁决 |
| 负载再平衡 | 可被迁移 | **跳过**,不参与再平衡 |
| 逻辑缩容 | 可被选中回收 | 优先避开;缩无可缩(全是锁)→ 缩容失败告警 |
| 任务 DRAINING/GONE | 回收 | **锁自动失效**,任务下线优先于锁 |

实例侧行为不受锁影响:实例只认 `owner == self && state == ASSIGNED`,锁不改变实例对账逻辑。锁纯粹是**约束决策面**的东西。

## 四、关键冲突裁决:钉住的实例死了怎么办

### 4.1 锁已过期(TTL 到期)

主每轮扫到 `expiresAt < now` → CAS 清 pin → 分区回到自动管理,走正常判死交接。全自动,无人工。

### 4.2 锁未过期,死在钉住目标上(owner 死且 pinnedTo == owner)

不能自动交接(违背锁的承诺),也不能无限装死。策略:

1. 分区**保持 ASSIGNED 不动**,进入持续告警:"钉住实例失联,分区停摆,等待人工裁决";
2. 人工两个选择:解除锁(→ 自动交接)、改钉到别的实例(→ §五 定向交接);
3. TTL 锁的意义在此:当初若设了过期时间,最终落到 4.1 自愈,而不是永远卡死。

### 4.3 交接中间态与锁(手动迁移回滚)

迁移过程中 pin 指向**目标**实例,源死亡不影响推进;交接窗口内源实例复活 → 回滚 owner=源,**同时清 pin 并告警**(迁移失败,让运维重试)——不留"pin 指向 B 但 owner 是 A"的诡异状态。

## 五、手动迁移 = 定向交接 + 钉住(复用交接机制)

不发明新的迁移通道,复用判死交接的 MIGRATING 状态机,只是"目标"从算法打分改为人工指定:

```
1. 运维写 ops: { type: MIGRATE_PIN, taskId, partId, target: B, ttl }
2. 主消费 ops:
   - 校验 B 存活且可接单
   - CAS: state=MIGRATING, handover={sourceOwner: A, confirmDeadline},
          pin={pinnedTo: B, ...}          ← 交接中间态与锁同键原子落盘
3. 按任务声明的 handover 模式推进:
   - AGGRESSIVE:直接 owner=B(幂等兜底)
   - CONSERVATIVE:双窗口确认 A 已死后 owner=B
4. 完成:state=ASSIGNED, owner=B, pin 保留(钉在 B)
```

## 六、ops 通道与单写者模型

- 钉住/解锁/迁移全部走 **ops 队列**(`/dcp/{ns}/ops/{opId}`),由**主消费执行**——归属键唯一写者始终是主,运维后台不直接写 parts,避免多写者破坏 CAS 假设;
- ops 类型扩展(在子文档⑦基础上):

| 类型 | 语义 |
|---|---|
| `PIN` | 钉住当前 owner(可选 ttl/到期时间) |
| `UNPIN` | 解除锁,恢复算法管理 |
| `MIGRATE_PIN` | 定向迁移到指定实例并钉住(§五) |

- ops 带幂等 opId,主处理完回写 DONE/FAILED 并删除;同一分区存在未完成 op 时后台拒绝新 op(与子文档⑦冲突规则一致);
- 全部锁操作落审计(不可变):谁、何时、钉/解、理由。

## 七、与既有机制的交互

| 机制 | 交互 |
|---|---|
| SUSPECT(实例卡死) | 锁只管归属,活性问题照走双窗口;卡死且钉住 → 同 4.2 告警 |
| 暂停接单(paused,实例级) | 与锁正交:paused 是"不接新",锁是"分区不走",互不替代 |
| 优雅退出 | 归属 CAS 清理不检查锁;归属被清即锁随之失效,主补 PENDING 时不再定向(避免死分区指向已退实例) |
| 再平衡 | 跳过有锁分区(§三);锁分区计入实例负载(负载是事实)但不作为迁移候选(归属是决策) |

## 八、边界与告警

| 场景 | 行为 |
|---|---|
| 钉住目标不存在/已死 | PIN op 校验失败,FAILED 并提示 |
| 钉住分区 owner 死亡(锁未过期) | 持续告警 + 等人工(4.2) |
| TTL 锁到期 | 自动解锁,回到自动管理(4.1) |
| 迁移回滚 | 清 pin + 告警迁移失败(4.3) |
| 任务下线 | 锁随任务失效(§三) |
