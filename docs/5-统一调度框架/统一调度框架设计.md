# 统一调度框架设计(通用分布式消费调度)

> 状态:设计稿。适用于同步链路消费者、索引器、数据消费(计算面)三个消费场景的统一调度与线程托管;底层 etcd,namespace 隔离,框架除业务 handler 外零 MySQL 依赖。
>
> 文档体系:见《统一调度框架-文档体系.md》(总纲+子文档+图示三层结构)。配套:完整流程架构图《统一调度框架-完整流程.svg》;子文档《统一调度框架接入设计.md》——三场景接入流程、TaskSpec 契约精确设计、业务层感知机制与换主透明性。

**一句话定位**:统一调度框架是一个基于 etcd 的通用"分区调度与线程托管"系统——回答的唯一问题是"**哪个分区应该在哪个实例的哪个线程上跑**",并提供分配、迁移、扩缩容、监控与人工干预;线程里跑什么业务,框架一概不管。

---

## 一、框架边界

### 1.1 管三件事,其余外置

```
框架管:
  ① 分区归属决策(分配 / 迁移 / 再平衡 / 对账)
  ② 线程生命周期托管(起 / 停时机、交接时序)
  ③ 扩缩容编排(阈值决策、逻辑缩容流程)

框架不管(业务通过三个契约接口提交):
  TaskSpec          —— 任务参数(标识/并发边界/执行契约/规则/业务元数据)
  PartitionExecutor —— 执行器(内部:poll → 业务处理 → 提交位点,位点与提交节奏由执行器自定,框架不管理位点;上报四个原始计数器)
  ScaleDownHooks    —— 缩容钩子(业务侧切换生产端路由)
```

### 1.2 明确外置的业务知识(框架不感知)

| 业务知识 | 归属方 | 框架对应物 |
|---|---|---|
| 下游能扛多大流量(maxPartitions) | 业务(TaskSpec) | 并发上界 |
| 重复消费是否有害 | 业务(TaskSpec.handover) | 交接模式 |
| 消费起点怎么定(从组位点续/精确 seek) | 业务(bizMeta) | 透传执行器 |
| 分区路由怎么切(bucket_map 等) | 业务(ScaleDownHooks) | 缩容编排时回调 |
| 批阶段(批打底→批流交接 T0) | 业务外壳 | 框架不知道批的存在 |
| 线程里跑什么业务逻辑 | 业务(PartitionExecutor) | 回调执行 |

### 1.3 对 Kafka 的依赖边界

框架对 Kafka **只读**:仅通过 Admin API 读 `endOffset` 算 lag。扩分区、改路由等写操作一律由业务外壳执行,框架只发"建议"。

### 1.4 三大模块总览(任务接入 / 状态管理 / 调度机制)

整个框架由三个大模块组成,职责与依赖单向:

```
① 任务接入(契约层)    —— 回答"跑什么":TaskSpec 五组字段 + 执行器三方法契约 + EMBEDDED/SPI 装载
        │  外壳写 spec / 业务实现 PartitionExecutor
        ▼
② 框架自身状态管理(事实源层) —— 回答"看得见":etcd 唯一事实源,键空间六类;
        │  租约(活性)与持久(状态)分层;实例对账 + 主巡检双自愈;CAS+epoch+交接中间态换主可续
        ▼
③ 调度机制(决策层,核心) —— 回答"跑在哪、何时换":打分分配 / 判死交接 / 锁(钉住) /
          再平衡 / 扩缩容;周期 tick 兑底 + 事件驱动加速;决策纯逻辑、写走 CAS、永不阻塞
```

- **接入层定义"跑什么"**(契约):业务与框架的全部交界面只有三个(TaskSpec / PartitionExecutor / ScaleDownHooks),位点与提交节奏由执行器自管;
- **状态层保证"看得见"**(事实源+活性):一切状态落 etcd,注册/快照/leader 带租约做活性信号,spec/status/parts 持久做状态事实;任何时刻重读 etcd 即可重建全部决策上下文;
- **调度层决定"跑在哪、何时换"**(决策+锁):唯一写归属的一方,所有写带 CAS 条件;锁机制让运维意图优先于算法最优(详见子文档⑧)。

### 2.3 为什么是 etcd

| 需求 | etcd 能力 | 用途 |
|---|---|---|
| 归属决策的强一致 | CAS 事务写 | 分区归属唯一性(防双消费的根基) |
| 实例存活性 | lease 自动过期 | 实例注册保活、判死 |
| 事件驱动 | watch(带 revision 续传) | 实例感知归属变化(拉模式)、外壳感知任务状态 |
| 换主安全 | 状态全部落盘 | 主无内存态,新主全量读恢复 |
| 竞选 | lease campaign | 每 ns 选主 |

## 三、namespace 隔离模型

### 3.1 什么是 namespace

namespace 是框架的**隔离与自治单元**:每种消费场景(同步链路/索引器/数据消费)各占一个 ns,互相看不见对方的东西,却共用同一套调度内核。

| namespace | 场景 | 任务来源 | 执行器 |
|---|---|---|---|
| `sync` | 同步链路(出口→业务库) | LogicalTableConfigService | embedded:sync-writer |
| `indexer` | 索引器(出口→锚点) | 流扫描(新 topic 自动纳入) | embedded:anchor-sampler |
| `outlet` | 数据消费(计算面打标) | 原控制面(单元规划) | spi:业务 logic |

### 3.2 隔离维度(硬隔离清单)

| 维度 | 隔离方式 |
|---|---|
| 存储 | etcd key 前缀 `/dcp/{ns}/` 硬隔离 |
| 选主 | 每 ns 独立竞选,互不干扰 |
| 实例池 | 实例按启动参数归属 ns 列表(部署属性);每 ns 独立调度注册(capacity/weight)与独立 lease |
| watch | 实例/外壳只 watch 其归属的 ns 前缀(多 ns 实例 watch 多个前缀,按 ns 分组对账) |
| 指标 | 各 ns 独立聚合、独立大盘 |
| 扩缩容 | 各 ns 独立默认规则、独立开关 |
| 运维权限 | 后台权限按 ns 授予 |

### 3.3 为什么每 ns 独立选主(而非全局单主)

1. **故障隔离**:某 ns 的调度决策异常(如规则配置错误导致迁移风暴)只影响本 ns;
2. **决策负载独立**:任务多的 ns 不会饿死任务少的 ns(全局单主下,大 ns 的 PENDING 挤压小 ns 的决策时延);
3. **部署独立**:各 ns 实例池独立发布,选主与版本解耦。

代价:每 ns 多一份主 lease 开销(可忽略);跨 ns 决策(如全局资源池调配)由运维后台跨 ns 读取实现,不走调度主。

### 3.4 实例与 ns 的关系(实例可归属多 ns)

- 实例通过启动参数声明归属的 **namespace 列表**(如 `--namespaces=sync,indexer`),是**部署属性**;
- 一个实例可同时归属多个 ns;每个 ns 内独立声明调度属性(capacity/weight),互不影响;
- 实例在全局注册一次身份与机器指标,在**每个归属 ns 各注册一份调度记录 + 独立 lease**;
- 运维后台不提供运行时改 ns 归属(改归属 = 改配置重启);
- 实例池的进出调配(下架/权重/暂停)按 ns 维度独立进行:某 ns 下架该实例,不影响它在其他 ns 的运行;
- 机器指标(cpu/mem/load)是进程级的,放全局身份键一份;容量分账按 ns:总线程数 = Σ 各 ns capacity,由部署配置人工把关。

### 3.5 etcd key 空间(完整)

```
/dcp/instances/{id}                           实例全局身份(addr/namespaces 列表/机器指标 meta,lease 保活)
/dcp/{ns}/leader                             调度主竞选键(lease campaign)
/dcp/{ns}/instances/{id}                     该实例在本 ns 的调度注册(capacity/weight/status,独立 lease 30s)
/dcp/{ns}/rules                              本 ns 默认扩缩规则(ScaleRules)
/dcp/{ns}/tasks/{taskId}/spec                TaskSpec(业务外壳写,框架只读)
/dcp/{ns}/tasks/{taskId}/status              任务状态 SUBMITTED|RUNNING|DRAINING|GONE(调度主写)
/dcp/{ns}/tasks/{taskId}/parts/{partId}      分区归属记录(调度主写 CAS,实例 watch)
/dcp/{ns}/tasks/{taskId}/parts/{partId}/snap 执行器快照(执行器 10s 续写,TTL 30s)
/dcp/{ns}/ops/{opId}                         运维操作(迁移/下架/暂停等,后台写,主消费)
```

**写入方与读取方所有权表**(换主安全的基础):

| key | 写 | 读 |
|---|---|---|
| instances/{id}(全局) | 实例自己 | 各 ns 主(机器指标)、后台 |
| leader | 实例(竞选) | 所有实例 |
| instances/*(ns 内) | 实例自己 | 本 ns 主(决策)、后台 |
| rules | 后台/业务外壳 | 主 |
| tasks/*/spec | 业务外壳 | 主、实例骨架(透传执行器) |
| tasks/*/status | 主 | 业务外壳(可选)、后台 |
| tasks/*/parts | 主 | 实例骨架、后台 |
| tasks/*/parts/*/snap | 执行器(经实例骨架) | 主(算指标/活性) |
| ops/* | 后台 | 主(消费后推进状态) |

## 四、核心数据模型

### 4.1 完整字段结构总览

先给五类结构的完整字段定义(含子结构),4.2 起分段详解字段语义。

**① 任务契约 TaskSpec(业务外壳写,框架只读)**

```java
TaskSpec {
  // ① 基础标识
  namespace: string          // sync | indexer | outlet —— 决定任务进哪个 ns 前缀
  taskId: string             // 业务任务标识(逻辑表名/单元ID/表名),框架仅展示与关联
  topic: string              // Kafka topic —— 同 ns 内唯一键(重复提交 = 更新)
  partitions: int            // 初始分区数 = 初始并发度(框架照此写 N 条 PENDING)
  // ② 并发边界(扩缩容决策域)
  minPartitions: int         // 缩容下限
  maxPartitions: int         // 扩容上限 = 最大并发度(业务知识:下游能力)
  targetRps: long            // 单分区目标吞吐(扩缩容基准:期望分区数 = 流量/targetRps)
  // ③ 执行契约
  handlerRef: HandlerRef     // 执行器装载引用
  handover: Handover         // 交接模式
  // ④ 协作与规则(可选)
  scaleDownHooks: HookRef | null   // null = 该任务只扩不缩
  scaleRules: ScaleRules | null    // null = 继承 ns 默认规则
  // ⑤ 业务元数据(框架不解释,原样透传执行器)
  bizMeta: Map<String,String>      // outlet: 起点偏移表/startTso/logic 版本;sync: bucket_map 版本
}
HandlerRef { type: EMBEDDED | SPI, ref: string }   // 内置执行器名 | 插件名
HookRef    { ref: string }                          // 业务注册的钩子名
Handover   = AGGRESSIVE | CONSERVATIVE
```

**② 分区归属记录 PartRecord(主写 CAS,实例 watch)**

```java
PartRecord {
  partId: int
  owner: string | null       // 实例 id;null = PENDING
  state: PENDING | ASSIGNED | MIGRATING | DELETING
  epoch: long                // CAS 条件,防陈旧主/并发写
  handover: {                // 保守交接中间态(持久化,换主可续;激进交接为 null)
    sourceOwner: string      // 迁移前归属
    confirmDeadline: long    // 判死双窗口 deadline
  } | null
}
```

**③ 实例记录(全局身份一份 + 每 ns 调度注册一份)**

```java
InstanceRecord {              // 全局身份:/dcp/instances/{id}(进程级,只一份)
  id: string
  addr: string
  namespaces: List<string>    // 归属的 ns 列表(启动参数声明,部署属性)
  meta: {                     // 机器指标(进程级),10s 随 lease 续租刷新
    cpu: int, mem: int, load: int, jvmThreads: int
  }
}
NsInstanceRecord {            // 每 ns 调度注册:/dcp/{ns}/instances/{id}(每归属 ns 一份)
  id: string, ns: string
  status: ONLINE | DRAINING | SUSPECT
  capacity: int               // 本 ns 槽位(可承载最大线程数,按 ns 分账)
  weight: double              // 人工调权 0.5~2.0(迁移目标打分因子)
  paused: bool                // 暂停接单(维护窗口)
}
```

**④ 执行器快照 ExecutorSnapshot(执行器 10s 续写,TTL 30s)**

```java
ExecutorSnapshot {
  ts: long
  taskId: string, partId: int
  processedCount: long       // 累计处理条数
  committedOffset: long      // 已提交位点
  errorCount: long           // 累计错误数
  totalLatencyMs: long       // 累计处理耗时
}
```

**⑤ 扩缩规则 ScaleRules(ns 默认,任务可覆盖)**

```java
ScaleRules {
  up: double            // 扩容水位 0.8
  upPeriods: int        // 扩容持续周期 3
  down: double          // 缩容水位 0.4
  downPeriods: int      // 缩容持续周期 6
  cooldownMinutes: int  // 冷却 10
  maxStep: double       // 单次步长上限 2.0(翻倍/减半)
  downEnabled: bool     // 缩容总开关(ns 级)
}
```

### 4.2 分段详解

**4.2.1 TaskSpec(任务契约)**

- 五组字段的职责分工:① 告诉框架"这任务是谁、消费哪个 topic、初始多大"(标识);② 告诉框架"扩缩容的边界在哪"(并发边界,业务知识);③ 告诉框架"线程里装什么执行器、迁移怎么交接"(执行契约);④ 告诉框架"缩容时调用哪个业务钩子、按什么规则决策"(协作规则);⑤ 告诉执行器"业务上下文是什么"(业务元数据,框架不解释);
- 提交即创建:业务外壳写 spec + 同条数 PENDING 归属记录,框架扫到即进入分配;
- **变更语义分级**:SOFT(min/max/targetRps/规则/钩子 → 热更新决策,不动运行中执行器)/ HARD(handlerRef/bizMeta/partitions → 按交接模式重启执行器:停旧线程 → 起新线程携带新 ctx);
- handlerRef 运行时更换先校验新执行器可装载(spi 存在性),失败拒绝变更、保留旧版本运行;
- 删除即注销:业务外壳删 spec,框架推进 DRAINING → GONE(§7 阶段八)。

**4.2.2 PartRecord(分区归属记录)**

- `PENDING`:无归属,等待主分配(任务创建/迁移中/实例失联判死后);
- `ASSIGNED`:归属确定,owner 实例应起线程(实例对账的输入);
- `MIGRATING`:保守交接中间态(判死窗口内,双确认未完成);
- `DELETING`:缩容追平/注销中,等 lag 归零后清记录;
- `epoch`:每次归属变更递增,CAS 写条件(读到的 epoch 与写入时一致才生效)——防陈旧主与并发写;
- `handover`:交接中间态**持久化在归属记录而非主内存**——保守交接窗口内换主,新主读到期继续判定,交接不中断、不重做、不误判。

**4.2.3 实例记录(全局身份 + 每 ns 调度注册)**

- 全局身份一份:addr/namespaces/meta(机器指标是进程级的,跨 ns 共享);每归属 ns 各一份调度注册;
- `capacity`(槽位)按 ns 分账:调度打分只用本 ns 注册键的槽位,实例在两个 ns 各自独立接单,总线程数 = Σ 各 ns capacity 由部署配置把关(防机器超载);
- `weight`:运维人工调权,影响迁移目标选择(按 ns 独立可调);
- `paused`:维护窗口,暂停接单但不影响已跑分区(按 ns 独立);
- `status=DRAINING`:本 ns 内下架中——不再接新分区,已有分区逐步迁空;不影响其他 ns 的运行;
- 存活语义:每个 ns 独立 lease 保活(30s,10s 续租),全局 meta 随续租刷新;某 ns 的 lease 过期 = 该 ns 判死入口(各 ns 独立判死)。

**4.2.4 ExecutorSnapshot(执行器快照)**

- 业务侧只维护这四个**随手计数器**,零指标概念、零计算(累计值天然无口径歧义);
- 所有指标由框架对相邻快照做差值派生(§10.2);
- 快照 10s 续写一次(TTL 30s),**续写行为本身即活性信号**:TTL 失效 = 执行器卡死;
- 快照是"拉"的:执行器经实例骨架写 snap 键,主(或监控组件)读键算指标,无直连通道。

**4.2.5 ScaleRules(扩缩规则)**

- 生效层级:**ns 默认规则 < 任务级覆盖**(TaskSpec.scaleRules 非空时逐字段覆盖);
- 缩容双闸门:ns 级 `downEnabled` 总开关 + 任务级"只扩不缩"声明(hooks=null 视为无缩容能力),两者都满足才允许缩容;
- 参数语义:up/down 是水位(相对 targetRps 的负载率),upPeriods/downPeriods 是防抖持续期,cooldown 是决策冷却,maxStep 是单次步长护栏(§9)。

## 五、执行器装载(ExecutorProvider)

### 5.1 两种装载方式

| 方式 | 适用 | 机制 |
|---|---|---|
| EMBEDDED | 平台自有逻辑(sync-writer 写库/anchor-sampler 锚点) | 随框架编译,按名注册,启动期自检存在性 |
| SPI | 计算面业务 logic | 业务按接口打 jar 进实例 classpath,`ServiceLoader` 发现,按插件名实例化 |

### 5.2 装载流程与失败处置

```
任务分配到我 → 实例骨架 lookup(handlerRef)
  ├─ EMBEDDED:查内置注册表 → 命中:newExecutor 起线程
  │            └─ 未命中:启动期框架自检已拦(拒绝启动),运行期几乎不可能
  └─ SPI:ServiceLoader 按插件名找实现
       └─ 缺失:拒绝创建任务(任务状态记 FAILED,告警"插件未装载"),不影响其他任务
```

**前置校验**:任务提交时(业务外壳)与任务分配时(实例骨架)各校验一次装载可用性;handlerRef 运行时变更(HARD 变更)先校验新执行器可装载,失败则拒绝变更、保留旧版本运行。

## 六、调度算法

### 6.1 目标

1. **负载均衡**:分区吞吐在实例间大致均匀;
2. **亲和保留**:已归属的分区尽量不迁移(迁移=停线+交接成本);
3. **最少迁移**:再平衡时以最小移动量达到均衡;
4. **防抖动**:规则持续期 + 冷却期,避免指标毛刺引发迁移风暴。

### 6.2 实例打分公式

```
score(i) = α · (1 − cpu_i / 100)              ← 机器余量
         + β · (1 − assigned_i / capacity_i)  ← 槽位余量(该实例已跑分区数)
         + γ · affinity(i, part)              ← 亲和(原归属=1,否则 0)
         + δ · weight_i                       ← 人工权重(0.5~2.0)
候选过滤:status=ONLINE 且 未暂停 且 assigned_i < capacity_i
```

(α/β/γ/δ 缺省 0.4/0.3/0.2/0.1,可配;亲和项使"原地不动"天然胜出,天然抑制无谓迁移。)

### 6.3 分配流程(PENDING → ASSIGNED)

```
决策循环(每 10s 一轮):
① 读本 ns:全部任务 parts + 实例表(过滤可接单)
② 收集 state=PENDING 的分区集合
③ 对每个 PENDING 分区:
    按打分公式选最高分实例
    → CAS 写归属 {owner, state:ASSIGNED, epoch+1}(条件:仍 PENDING 且 epoch 未变)
    → CAS 失败(被并发改写/陈旧):下轮重试
④ 不主动"通知"实例——实例 watch 到归属变化后自己对账(拉模式)
```

### 6.4 再平衡(迁移决策)

触发条件(任一):

1. 新实例入池(注册上线);
2. 实例下架(DRAINING 完成后腾出的分区);
3. 负载失衡超过阈值(实例间吞吐极差 > 30%,持续 6 个周期);
4. 人工触发(后台"一键均衡")。

约束:再平衡与自动扩缩共用冷却期;单轮迁移上限(如每轮最多迁 5% 分区);迁移逐分区走交接模式(§8)。

### 6.5 epoch 与防陈旧写

- 每条件归属记录带 `epoch`,主写归属时必须 CAS(条件:epoch 与读时一致);
- 新主上任全量读后,基于最新 epoch 决策,不可能覆盖旧主已写入结果;
- 双主窗口(旧主网络分区未退位)下:旧主的任何写因 epoch/CAS 失效,天然无效。

### 6.7 调度时机(何时调度)与锁(钉住)

**触发时机 = 周期 tick 兑底 + 事件驱动加速**。周期循环(10s 全量扫描)是正确性底线——漏掉任何事件,10s 后状态必收敛;事件驱动把关键场景从"10s 级"降到"秒级":

| 事件 | 感知 | 立即触发的决策 |
|---|---|---|
| 任务提交/变更 | watch spec | 校验执行器 → 补 PENDING → 分配 |
| 任务下线(status → DRAINING/GONE) | watch status | 回收分区 |
| 实例上线 | watch instances | 更新候选集,有 PENDING 立即分配 |
| 实例下线(租约过期) | watch instances | 判死交接(不依赖 tick) |
| 运维指令(钉/解/迁移) | watch ops | 定向执行 |
| 负载失衡 / rps 超水位(运行中) | 周期扫快照 | 再平衡 / 扩缩容规则 |

**手动钉住(锁)**:运维意图优先于算法最优。PartRecord 内嵌 `pin`(pinnedTo/expiresAt/reason),锁与归属同键原子;算法各环节让步矩阵、钉住实例死亡裁决、手动迁移(=定向交接+钉住)、ops 单写者通道,详见**子文档⑧《手动钉住与锁机制设计》**。

### 6.8 关键参数(缺省值)

| 参数 | 值 | 说明 |
|---|---|---|
| 决策周期 | 10s | 主扫描 PENDING/扩缩判定的节拍 |
| 主 lease | 30s | 实例每 10s 续租 |
| 实例 lease | 30s | 实例每 10s 续租 |
| 快照周期/TTL | 10s / 30s | 执行器上报节拍 |
| 判死窗口 | lease 过期 + 快照失效双确认 | 保守交接 |
| 再平衡失衡阈值 | 30% · 持续 6 周期 | 防抖动 |

## 七、完整生命周期(八阶段)

### 阶段一:框架启动(实例上线)

```
① 实例启动 → 读启动参数(ns 绑定、capacity)
② 注册 /dcp/{ns}/instances/{id} + lease 30s → 状态 ONLINE
③ watch 本 ns 前缀(tasks parts / ops / rules)
④ 候选竞选主(campaign /dcp/{ns}/leader):
   当选 → 切换为"主+实例"双角色:启动决策循环
   未当选 → 仅实例角色,等 watch 事件
```

### 阶段二:任务创建(业务外壳)

```
① 业务外壳组装 TaskSpec(五组字段)+ 校验执行器可装载
② 写 /dcp/{ns}/tasks/{taskId}/spec
③ 写 status=SUBMITTED + partitions 条 parts{state:PENDING}
④ (可选)watch 自己任务的 status/parts,收状态事件
```

### 阶段三:调度决策(主)

```
① 决策循环扫到 PENDING 分区
② 候选实例过滤 + 打分(§6.2)
③ CAS 写归属 → state=ASSIGNED
```

### 阶段四:执行(实例+执行器)

```
① 实例骨架 watch 到归属变化 → 对账 diff:
   diff 新增(owner=我) → 装载执行器(§5)→ start(ctx) 起线程
   diff 消失(归属迁走) → stop() 停线程(按交接模式定节奏)
② 执行器循环:
   poll(batch) → 业务处理(handlerRef 逻辑) → 提交位点
   → 周期续写快照(四个计数器)+ 续实例 lease
```

### 阶段五:稳态监控

```
① 主(或独立监控组件)读快照:Kafka Admin endOffset 算 lag → 四派生指标(§10)
② 指标按分区→任务→实例→ns 逐级聚合
③ 告警规则巡检(§10.6)
④ 活性检测:快照续写行为 + 实例 lease
```

### 阶段六:自动扩缩容

```
① 决策循环读聚合指标 → 水位判定(持续期 + 冷却期,§9)
② 扩容:期望分区数 → 建议业务外壳 Kafka 扩分区 → 外壳更新 spec → 新 PENDING → 分配
③ 缩容:三步编排(钩子切路由 → 追平判定 → 停线程清归属,§9.3)
```

### 阶段七:故障迁移

```
① 实例宕机 → lease 过期 → 主在决策循环中发现
② 判死(按交接模式,§8):
   激进:直接改归属 → 新实例起线程(幂等吸收重叠段)
   保守:双窗口确认(lease 过期 + 快照 TTL 失效)→ 改归属 → 新实例起线程
③ 迁移后进入稳态,重新对账
```

### 阶段八:任务注销

```
① 业务外壳删 spec(或后台发起注销)
② 主推进 status=DRAINING → 各分区 state=DELETING
③ 实例对账:stop() 停线程(激进停;保守追平后停)
④ lag 归零(按需)→ 主清 parts 记录 → status=GONE
⑤ 外壳 watch 到 GONE → 释放业务资源(logic 卸载/扫描条目删除)
```

### 7.9 三种重启场景的行为

| 场景 | 行为 | 关键 |
|---|---|---|
| 实例 30s TTL 内重启 | lease 未过期 → 归属不变 → 重启后按 etcd 归属对账恢复线程 | **不触发重分配**,避免无谓迁移 |
| 调度主重启 | 新主全量读 etcd 恢复决策上下文(实例/任务/归属/规则/ops),从当前状态继续 | 不做从零重放,不做无谓对账 |
| 全集群重启 | 所有实例重新注册 → 主照常决策 → 各实例对账起线程 | 收敛到 etcd 里的持久状态 |

## 八、交接模式(handover)

### 8.1 两种模式语义

| 模式 | 语义 | 迁移时序 | 适用 |
|---|---|---|---|
| AGGRESSIVE | 直接接管:新线程立即起,旧线程(若还活着)靠业务幂等吸收重叠段 | 改归属 → 起新 → 停旧 | 重复消费无害:sync(ODKU 幂等)、indexer(锚点幂等) |
| CONSERVATIVE | 确认旧执行器死亡才转移:判死双窗口满足后改归属 | 判死 → 改归属 → 起新 | 重复消费有害:outlet(打标无幂等) |

### 8.2 保守交接的判死双窗口

```
确认死亡条件(两者同时满足):
  ① 实例 lease 已过期(实例 30s 未续租)
  ② 执行器快照 TTL 失效(分区 30s 无快照)
→ 双确认防误判:单看 lease 可能只是"平台没续上"(原控制面经验);
  单看快照可能只是"执行器忙到没上报"。
```

交接中间态(`parts.handover:{confirmDeadline, sourceOwner}`)**持久化在归属记录**,而非主内存——保守交接窗口内主挂掉,新主读到期继续判定,交接不中断、不重做、不误判。

### 8.3 选择指引

业务提交 TaskSpec 时自报:重复处理是否有副作用?可幂等吸收 → AGGRESSIVE(迁移快、实现简单);不能幂等 → CONSERVATIVE(迁移慢一个判死窗口)。

**边界声明**:无论哪种模式,执行器 crash 后新实例从提交位点续,未提交段必然重放——**重放幂等由消费者自处理**(全链路本身面对多种重放场景),框架只负责缩小"双实例同时消费"的窗口,不承诺恰好一次。

## 九、自动扩缩容体系

### 9.1 四个维度的分工(定论)

| 维度 | 归属 | 说明 |
|---|---|---|
| **钩子** | 任务维度 | 是业务代码(bucket_map 收缩等),TaskSpec 提交时声明;后台只能触发与观察,不能编写 |
| **规则** | ns 默认 + 任务覆盖 | ns 设默认水位/持续期/冷却;任务用 TaskSpec.scaleRules 覆盖 |
| **缩容开关** | ns 总开关 + 任务声明 | ns 级 `downEnabled`;任务 hooks=null = "只扩不缩" |
| **触发/观察** | 后台提供 | 人工触发(立即扩容/强制均衡)、进度观察(追平中/已切路由) |

### 9.2 扩容流程(Kafka 分区只增不减)

```
① 决策:任务水位 = 实际流量 / (分区数 × targetRps) > up,持续 upPeriods 周期
   → 期望分区数 = clamp(⌈流量 / targetRps⌉, min, max),步长 ≤ maxStep(缺省翻倍)
② 若期望 > 当前 Kafka 分区数:发"扩容建议"给业务外壳
   → 外壳执行 Kafka 扩分区(+ 业务路由重算,如 bucket_map 扩容)→ 更新 TaskSpec.partitions
③ 框架扫到新分区 → 写新 PENDING → 分配 → 新实例起线程
④ 冷却:任务级 cooldown 窗口内不再决策(防抖)
```

### 9.3 逻辑缩容三步(框架编排,钩子在任务维度)

```
① 调业务钩子切路由:框架回调 ScaleDownHooks(任务声明)
   → 业务切生产端路由(停止往待缩分区写 / bucket_map 收缩)→ 钩子返回"已切"
② 追平判定(框架):待缩分区 lag 持续归零(< 阈值)→ state=DELETING
③ 停线程 + 清归属(框架):实例骨架 stop() → 主清归属记录 → 缩容完成
护栏:追平超时(如 10min)→ 告警 + 人工介入(不自动回滚路由)
```

**为什么分区只减"逻辑"不减"物理"**:Kafka 分区不可删;缩容 = 回收线程 + 腾出实例槽位,分区保留在 topic 上(未来再扩容直接重新分配)。

### 9.4 规则参数与护栏

| 参数 | 缺省 | 说明 |
|---|---|---|
| up / upPeriods | 0.8 / 3 | 水位连续 3 周期超 0.8 才扩 |
| down / downPeriods | 0.4 / 6 | 水位连续 6 周期低于 0.4 才缩(更保守) |
| cooldown | 10min | 扩缩冷却 |
| maxStep | 2.0(翻倍/减半) | 单次步长上限,防雪崩 |

护栏:不缩到 minPartitions 以下;缩容不跨 min;DRAINING/追平超时告警;单任务同轮不既扩又缩。

## 十、监控体系

### 10.1 指标分工原则

**业务零指标概念**:业务只维护四个随手计数器(§4.4),所有"指标"都是框架派生的。业务负担最小化,指标口径全框架统一。

### 10.2 派生指标(全部由框架计算)

| 指标 | 公式 | 数据来源 |
|---|---|---|
| lag(积压) | `endOffset − committedOffset` | Kafka Admin(实时水位)+ 快照位点 |
| rps(流量) | `ΔprocessedCount / Δt` | 相邻快照差值 |
| errorRate(错误率) | `ΔerrorCount / ΔprocessedCount` | 相邻快照差值 |
| avgLatency(延迟) | `ΔtotalLatencyMs / ΔprocessedCount` | 相邻快照差值 |

### 10.3 指标维度(四级聚合)

| 维度 | 内容 |
|---|---|
| 分区维度 | 四派生指标 + 状态(执行器快照直接产出) |
| 实例维度 | 聚合快照(Σ 该实例所有分区)+ 机器指标(CPU/内存/负载,实例进程自报);**JVM 级指标(GC/堆/线程池)后续扩展,走同一快照通道** |
| 任务维度 | 分区聚合 + 容量水位(实际/期望分区数) |
| ns 维度 | 任务/实例/分区计数 + 总 rps/总 lag 大盘 |

### 10.4 活性检测

1. 快照续写行为:分区快照 30s 无更新 = 执行器卡死 → 告警 + 按交接模式迁移;
2. 实例 lease:30s 不续租 = 实例失联 → 判死(§8);
3. 两者合一即"判死双窗口"。

### 10.5 告警规则(缺省)

| 告警 | 条件 | 级别 |
|---|---|---|
| 分区 lag 高位 | lag > rps × 5,持续 3min | warning |
| 错误率超阈值 | errorRate > 1%,持续 3min | critical |
| 执行器卡死 | 快照 TTL 失效 | critical |
| 实例失联 | lease 过期 | critical |
| 追平超时 | 缩容追平 > 10min | warning(人工介入) |
| 容量水位 | 任务水位 > 0.9 且分区数=max | critical(无扩空间) |
| 迁移失败 | 交接未完成且超时 | critical |

## 十一、业务层感知机制

### 11.1 拉模式原则

调度主从不主动"通知"业务层(拒绝推模式):主只写 etcd,业务层 watch etcd。业务层从头到尾**不知道主是谁、主换了没有**。

### 11.2 业务外壳的感知(可选、窄)

大部分场景 fire-and-forget(写完 TaskSpec 即结束)。仅订阅:任务 DRAINING→GONE(outlet 重规划前提:旧单元彻底回收才提交新 epoch)、注销完成(释放业务资源)、分区 ASSIGNED(可选,上层展示)。实现:watch 自己任务的 status/parts 键,可重试、可容忍秒~分钟级延迟。

### 11.3 执行器的感知(回调,零 etcd)

```java
interface PartitionExecutor {
    void start(ExecutorContext ctx);   // ctx={taskId, topic, partId, spec 子集}
    void stop();                       // 迁移/缩容/注销/硬变更重启
    ExecutorSnapshot metrics();        // 框架周期拉取四个计数器
}
```

执行器不碰 etcd、不 watch;框架动作全部通过回调表达:**换主对执行器无感知**。

### 11.4 换主透明性(三条不变式)

1. **主无内存态**:决策结果都先落 etcd 再生效,主挂只丢"未决决策";
2. **归属键写幂等且带 epoch**:新主基于当前状态 CAS,不可能覆盖旧主结果;
3. **业务层与主零连接**:唯一交互面是 etcd watch,watch 的是"状态"不是"主"。

(完整机制见接入设计文档 §3。)

## 十二、运维后台

### 12.1 组织维度

页面按 **ns → 任务 → 实例 → 分区** 列表逐级下钻(面包屑导航),每层带各自维度指标;扩缩容页区分"ns 级默认规则卡 + 任务级规则与钩子声明";监控页按维度大盘。

### 12.2 四类能力

| 能力 | 内容 |
|---|---|
| ns 管理 | 创建/删除 ns、设默认扩缩规则、缩容总开关 |
| 任务管理 | 任务列表(下钻)、契约查看、注销、扩缩触发 |
| 实例管理 | 上线确认、DRAINING 下架、权重调参、暂停接单(实例在 ns 维度内管理) |
| 分区管理 | 手动迁移、**钉住/解锁(可设 TTL 到期)、定向迁移+钉住**、状态观察(迁移对话框带目标实例负载/CPU/权重) |

### 12.3 三个边界(后台不能做的事)

1. **实例的 ns 归属列表 = 部署属性**:后台不提供运行时改归属(改归属 = 改配置重启);
2. **钩子 = 业务代码**:后台只能触发与观察,不能编写钩子;
3. **后台管触发与观察**:决策权在框架(规则)+业务(钩子),后台是管理面不是决策面。

## 十三、故障处理全景

| 故障 | 检测 | 处置 | 影响 |
|---|---|---|---|
| 实例宕机 | lease 过期(30s) | 判死(按交接模式)→ 分区改 PENDING → 重分配 | 该实例分区中断 ~1min |
| 执行器卡死 | 快照 TTL 失效 | 活性告警 → 按交接模式迁移该分区 | 单分区中断 ~1min |
| 调度主宕机 | leader lease 过期 | 实例群重新竞选 → 新主全量读恢复 → 继续决策 | 决策停顿 10s 级,数据面零影响 |
| 保守交接窗口内换主 | — | 交接中间态持久化在归属记录,新主读到期继续判定 | 交接不中断、不重做 |
| etcd 故障 | watch 断开/写失败 | 框架保守策略:执行器**继续跑**(归属不再变),主暂停决策;恢复后对账收敛 | 有吞吐无调度,不双消费不丢数据 |
| 网络分区(脑裂) | lease 机制 | 旧主退位(lease 续不上),新主当选;旧主写因 CAS/epoch 失效 | 短暂决策停顿 |
| 缩容追平超时 | 追平 deadline | 告警 + 人工介入(不自动回滚路由) | 待缩分区悬置,数据面无损 |

## 十四、接入方式(三场景)

| 维度 | sync | indexer | outlet |
|---|---|---|---|
| 业务外壳 | LogicalTableConfigService | 流扫描 | 原控制面(规划/批流交接/起点) |
| 任务粒度 | 逻辑表(一表一任务) | 出口表(一表一任务) | 单元(分区子集,规划产物) |
| 调度单位 | 分区 | 分区 | 单元(一线程一单元) |
| 起点 | 消费组位点续 | 消费组位点续 | 单元精确起点(seek 注入) |
| 交接 | 激进(ODKU 幂等) | 激进(锚点幂等) | 保守(租约双确认) |
| 扩缩 | 分区级自动(有钩子) | 分区级自动(只扩不缩) | 单元级(规划驱动,epoch 重规划) |
| 执行器 | embedded 写库 | embedded 锚点采样 | spi 业务 logic |
| 批阶段 | 无(在采集/湖侧) | 无 | BatchRunner 留业务外壳,框架不参与 |

**消费底座与控制面的结合要点**:控制面拆为"业务外壳(任务生命周期/批打底/批流交接 T0/单元规划/起点计算)+ 被框架收编(授租约下发→归属分配、推模式→watch 对账、Supervisor 巡检→活性检测)+ 执行器收编(UnitRunner → PartitionExecutor,起点注入保留)"。边界铁律:**批流交接完整保留在业务外壳,框架永远不知道批阶段的存在**。

(完整流程与代码映射见《统一调度框架接入设计.md》。)

## 十六、关键设计决策记录(ADR)

| # | 决策 | 权衡 | 被否方案 |
|---|---|---|---|
| 1 | 每 ns 独立选主 | 故障隔离 + 决策负载独立,代价每 ns 一份 lease | 全局单主(大 ns 挤压小 ns) |
| 2 | 拉模式(watch 对账) | 换主透明、状态一致,代价事件延迟 1 个 watch 周期 | 推模式(换主要重连、丢消息) |
| 3 | 批流交接留业务外壳 | 框架零业务语义,代价外壳多一处职责 | 框架接管批阶段(框架必须理解 T0/批语义) |
| 4 | 保守交接双窗口(lease+快照) | 绝不双消费,代价迁移慢一个判死窗口 | 单 lease 判死(平台没续上会误判) |
| 5 | 交接中间态持久化到归属记录 | 换主可续交接,代价记录结构复杂 | 放主内存(换主丢交接态) |
| 6 | EMBEDDED + SPI 双装载 | 平台自有零成本,业务灵活,代价两套校验路径 | 纯 SPI(平台逻辑也要打 jar)/ 纯 embedded(业务逻辑进框架) |
| 7 | 指标全部框架派生 | 业务零指标概念、口径统一,代价框架依赖 Kafka Admin | 业务上报指标(口径乱、负担重) |
| 8 | Kafka 分区只增不减(逻辑缩容) | 缩容可逆、成本低,代价分区槽位残留 | 物理删分区(Kafka 不支持) |
| 9 | 钩子=任务维度/规则=ns 默认+任务覆盖 | 业务代码与运行参数分离,代价两个配置位 | 钩子挂 ns(多任务混装) |
| 10 | 实例可归属多 ns,归属列表=部署属性 | 一进程服务多场景,每 ns 独立槽位防超额分配,ns 隔离不破坏 | 一实例一 ns(浪费进程)/运行时换 ns(状态迁移复杂) |
