# 扩缩容体系设计

> 承接总纲 §九。细节级:规则引擎计算、扩容/缩容编排时序、钩子协议、护栏。状态:初版,随讨论迭代。

## 一、四维度分工(定论回顾)

| 维度 | 归属 | 说明 |
|---|---|---|
| 钩子 | **任务维度** | 业务代码(bucket_map 收缩等),TaskSpec 提交时声明;后台只能触发与观察 |
| 规则 | ns 默认 + 任务覆盖 | ns 设默认水位/持续期/冷却;任务用 TaskSpec.scaleRules 逐字段覆盖 |
| 缩容开关 | ns 总开关 + 任务声明 | ns 级 `downEnabled`;任务 hooks=null = 只扩不缩 |
| 触发/观察 | 后台提供 | 人工触发(立即扩容/强制均衡)、进度观察 |

## 二、规则引擎计算

```
每决策周期,对每个 RUNNING 任务:
  flow      = Σ 该任务各分区 rps(快照派生)
  curParts  = 当前分区数(spec.partitions 或实际分配数)
  capacity  = curParts × targetRps
  waterLevel = flow / capacity

  扩容判定:waterLevel > up 连续 upPeriods 个周期
            AND 距上次扩容/缩容 > cooldown
            AND curParts < maxPartitions
     期望分区数 desire = clamp(⌈flow / targetRps⌉, curParts+1, maxPartitions)
     实际步长 = min(desire − curParts, ⌈curParts × (maxStep−1)⌉)   // 最多翻倍
     需要 Kafka 扩分区时(desire > kafkaPartitions)→ 发扩容建议给业务外壳

  缩容判定:waterLevel < down 连续 downPeriods 个周期
            AND 距上次决策 > cooldown
            AND curParts > minPartitions
            AND ns.downEnabled AND 任务 hooks ≠ null
     缩容目标 target = max(⌊flow / targetRps⌋, minPartitions)
     实际步长 = min(curParts − target, ⌊curParts / 2⌋)             // 最多减半
     缩容方式:逻辑缩容三步(§四)
```

**边界语义**:

- `curParts` 用**框架实际分配的分区数**(以 parts 记录为准),`kafkaPartitions` 用 Kafka Admin 实际分区数——两者对账发现 Kafka 分区多于 spec 时,视为"待纳入的新分区",直接补 PENDING(不经外壳);
- 水位分母用 `curParts × targetRps` 而非历史峰值——缩容后分母变小,水位回升,天然形成负反馈防抖。

## 三、扩容编排时序

```
主                   etcd                业务外壳              实例
 │─决策:waterLevel>up 持续3周期─▶│             │                │
 │─desire > kafkaPartitions?───▶│─"扩容建议"事件─▶│               │
 │                             │             │─Kafka 扩分区+路由重算─▶│
 │                             │◀─更新 TaskSpec.partitions──│               │
 │─扫到新分区 → 写 PENDING────▶│             │                │
 │─CAS 分配──────────────────▶│─watch───────────────────────▶│─起新线程─▶
```

要点:

1. Kafka 扩分区是**管理操作**,只能由业务外壳执行(框架对 Kafka 只读);
2. 框架发的是"建议"不是"命令"——外壳可以拒绝(如物理分表未就绪),拒绝对应"回写规则覆盖:maxPartitions 临时下调"或"标记任务扩容暂停";
3. 建议带 desire 值,外壳按需执行(可能一次扩到 desire 或分多步);
4. 若 Kafka 分区已够(历史遗留分区多),框架直接补 PENDING,不走外壳。

## 四、逻辑缩容三步编排时序

```
主                          etcd                    业务(钩子)         实例/执行器
 │─决策:waterLevel<down 持续6周期─▶│                   │                │
 │─选待缩分区(负载最低者)──▶│                   │                │
 │─调钩子 hooks.routeCut(分区列表)───────────────▶│                │
 │                          │                   │─切生产路由(停写) │
 │                          │◀─返回"已切"─────────────────│                │
 │─parts 待缩区 → DELETING─▶│                   │                │
 │                          │                   │                │─线程继续跑追平─▶
 │─每周期判 lag 归零(连续2周期 < 阈值)──▶│                   │                │
 │─清 parts 归属记录──────▶│─watch──────────────│                │─stop───▶
 │─缩容完成事件──────────▶│                   │                │
护栏:
  · 追平 deadline(缺省 10min)超时 → 告警 + 人工介入(不自动回滚路由);
  · 钩子调用失败/超时 → 中止缩容,告警,冷却期重置;
  · 一次缩容涉及的 partitions 数受 maxStep 约束(最多减半)。
```

## 五、钩子协议(ScaleDownHooks)

```java
interface ScaleDownHooks {
    /** 切路由:生产端停止向指定分区写。返回 true=已切;false/异常=缩容中止。 */
    boolean routeCut(String taskId, List<Integer> partIds);

    /** 可选:追平期观察(业务侧确认无在途数据)。返回 true=可停线程。 */
    default boolean drainReady(String taskId, List<Integer> partIds) { return true; }
}
```

约定:

- 钩子由业务实现并注册(引用名写在 TaskSpec.scaleDownHooks),框架按名调用;
- 钩子必须**幂等**(框架可能因超时重调);
- 钩子执行超时(缺省 30s)→ 视为失败;
- 钩子属于任务(不是 ns):多任务共享同名钩子实现,但注册与声明都以任务为单位。

## 六、单元级扩缩(outlet 特例:规划驱动)

消费底座任务(单元)min=max,禁用分区级自动扩缩,扩缩 = **控制面重新规划**:

```
① 控制面(业务外壳)判断需要更多/更少并发(如:打标任务规模变化)
② UnitPlanner 重新规划:epoch+1 → 新单元集(newUnits)
③ 外壳提交:新单元 TaskSpec(新 taskId,epoch 变化)+ 旧单元注销(删 spec)
④ 框架对旧单元走 DRAINING(追平→GONE),新单元走分配→执行
⑤ 外壳 watch 旧单元 GONE 后才算规划完成(防新旧双跑)
```

与框架分区级扩缩的差异:粒度是"单元"(分区子集)、决策方是业务外壳而非框架规则引擎、步长由规划算法决定。

## 七、护栏汇总

| 护栏 | 规则 |
|---|---|
| 下限 | 不缩到 minPartitions 以下 |
| 上限 | 不扩到 maxPartitions 以上 |
| 步长 | 单次最多翻倍/减半(maxStep) |
| 冷却 | 决策间隔 ≥ cooldown(10min) |
| 防抖 | 水位连续 upPeriods/downPeriods 周期才触发 |
| 缩容双闸门 | ns.downEnabled AND 任务 hooks 非空 |
| 追平超时 | 10min 未追平 → 告警 + 人工介入 |
| 同轮互斥 | 单任务同轮不既扩又缩 |
| 并发限量 | 全 ns 同轮缩容任务数 ≤ 2(防路由切换风暴) |

## 八、人工触发(运维后台)

| 操作 | 语义 |
|---|---|
| 立即扩容 | 跳过水位判定,直接走扩容编排(仍需冷却检查) |
| 立即缩容 | 跳过水位判定,走缩容三步(仍需双闸门) |
| 强制均衡 | 触发再平衡(非扩缩容) |
| 观察 | 缩容进度(待切路由/追平中/已回收)、扩容建议状态(待外壳执行/已扩) |
