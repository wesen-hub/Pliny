## 四、问题清单

### 高危（1 项）

**1. T0Selector GC 安全余量单位 bug——待办 7 的落地存在单位错误，实际余量约 0.46ms**

- 位置：`outlet-control/.../T0Selector.java` 新 R2：`long gcFloor = gc + gcSafeMarginMs;`（margin 默认 120,000）
- 根因：`TiDbGcSafePoint.gcSafePointTs()` 返回 **TSO**（`ms << 18`），TiCDC start_ts、latest 同为 TSO。TSO 数值 1ms ≈ 2^18 ≈ 262,144 个 tick，**直接 +120,000 只抬升约 0.46ms**，注释声称的"2 分钟余量"完全没生效——紧贴 GC safe point 取 T0 的风险依旧
- 修法：`gc + (gcSafeMarginMs << 18)`（margin 保持毫秒语义），或 margin 定义改为 TSO 单位并改名
- 逃逸原因：T0AdaptersCheck 测试未覆盖 margin 行为，无断言约束
- 修复后建议补一条离线断言：margin=2min 时 T0 至少比 GC safe point 大 2min（按 TSO tick 折算）

### 中危（4 项）

**2. ProductionMessageDecoder tso 三域混用**

- TiCDC 走 `_tidb.commitTs`（TSO 域），缺失回退顶层 `ts`（**millis 域**，代码注释自认）——单位不一致的静默回退会让 T0 过滤系统性错位
- 打标事件 ts 是 epoch millis、入站 ts 也是 millis，同一底座运行时三域混用
- 打标事件 `ts` 缺失时 tso=0（无兜底 → 被 T0 过滤静默丢弃），而入站分支有 `System.currentTimeMillis()` 兜底——两分支口径不一致
- 建议：底座激活前明确各流 ts 域契约（信封流加 commitTs 决策已拍板，需同步对齐打标事件流与 TiCDC 回退路径）

**3. TagV2Deployer 迁移 RestClient 丢失超时保护**

- 原 HttpClient 版有 `Duration.ofSeconds(15)`；改 @LoadBalanced RestClient 后无 requestFactory 超时配置
- backend WorkerClient 的 `JdkClientHttpRequestFactory` 同样无 readTimeout
- 控制面 HTTP 调用存在无限挂起风险，建议统一配置 read/connect timeout

**4. `/api/ingest/**` permitAll 与 @PreAuthorize 矛盾**

- SecurityConfig 认证层放行 `/api/ingest/**`，但 IngestAppController 7 个端点全部 `@PreAuthorize("@perm.has('ingest:app:manage')")`
- 实际效果：匿名请求得 403 而非 401（fail-closed 安全，但报错形态误导前端跳登录）
- 建议：改为 authenticated，或明确 ingest 通道身份（如 Agent secret 自校验同款机制）

**5. ContractViewCodec null→"*" 全放行**

- 契约列白名单 null 编码为 `"*"`（整行透传），与"宁可中断绝不无裁剪放行"的 fail-closed 精神存在张力
- null 的语义靠契约管理方保证；建议在契约写入侧强制显式白名单或显式 `"*"`，不用 null 隐式表达

### 低危/提示（5 项）

| # | 项 | 说明 |
