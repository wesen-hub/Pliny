## 一、修复清单(7 项)

### H1(高):ingest 应用列表/状态接口未鉴权 + appKey 泄露

- **缺陷**:`IngestAppController.list()/status()` 无 `@PreAuthorize`,且 SecurityConfig 对 `/api/ingest/**` permitAll,未登录者可枚举全部 appKey(数据提交凭证),可冒充业务系统写数据
- **修复**:
  - `list()`/`status()` 补 `@PreAuthorize("@perm.has('ingest:app:manage')")`(方法级安全在 URL permitAll 之上仍生效,匿名请求直接被拒)
  - `KafkaIngestEngine` 增 `maskKey()`:列表/详情回显脱敏(≥8 位留头尾各 4,短 key 全掩),仅 `createApp` 回显一次完整 key
- **文件**:`backend/.../sync/ingest/IngestAppController.java`、`KafkaIngestEngine.java`
- **遗留(第一期报告中危-4,本期未处理)**:`/api/ingest/**` permitAll 与 @PreAuthorize 并存导致匿名请求报 403 而非 401,报错形态误导前端跳登录;建议后续改 authenticated 或明确 ingest 通道身份(Agent secret 自校验同款机制)

### H2(高):快照批未按写者列分组

- **缺陷**:`AtomicUpsertDao.applySnapshotBatch` 攒批桶键仅 (table, snapshot),不含 writer;多表合并(多源→同一宽表)全量快照时不同源 op 混批,共用首个 op 的写者列做裁判,他源写者列永不推进,字段并集缺失补 "" 静默清空他源列
- **修复**:快照路径先按 writer 分组(写者缺失抛 `IllegalStateException`,与增量路径 `applyMultiValue` 同口径),组内再按 500 条分 chunk 执行 `snapshotInsert`
- **文件**:`dcp-synclink/.../core/AtomicUpsertDao.java`

### H3(高):JWT 签名密钥/数据源加密密钥硬编码兜底

- **缺陷**:`application.yml` 中 `jwt-secret`/`enc-key` 带源码公开兜底默认值,知道默认值即可伪造 ADMIN token、解密数据源密码
- **修复**:
  - backend + asset/sub/tag 四服务 `JwtAuthFilter` 不再信任 token roles claim,每请求从 DB 回查角色(用户已删/角色已回收 → 不设认证);`JwtUtil.generate` 只带身份不带 roles
  - asset/sub 无 SysUserMapper → `SysRoleMapper` 增 `selectRolesByUserId` @Select 注解方法(与 backend 同 SQL)
  - 新增 `backend/.../config/SecurityKeyGuard.java` 启动守卫:jwt-secret <32 字节或等于旧公开默认值、enc-key 为空或等于旧公开默认值 → 拒绝启动
  - 四服务 application.yml 密钥去兜底(`${JWT_SECRET}` 缺失即启动失败);docker-compose 7 处 JWT_SECRET/PLATFORM_ENC_KEY 改必填 `${VAR:?}` 语法;新增 `.env.example`,`.gitignore` 忽略 `.env`
- **注意**:角色回查每请求一次 DB 查询(控制面量级可接受,未加缓存)
- **文件**:backend/asset/sub/tag 四服务 security 包、SysRoleMapper×2、backend application.yml、docker-compose.yml、.env.example、.gitignore

### M1(中):Autoscaler 任务级规则不继承 ns 基础规则

- **缺陷**:`effectiveRules` 在 `spec.scaleRules != null` 时新建对象逐字段复制,基本类型字段缺省退回 0/false,会静默清零水位、禁用缩容
- **修复**:`ScaleRules` 字段装箱化(null=未配置,JSON 反序列化缺字段为 null,解决「显式关缩容 false」与「未配置」无法区分);`effectiveRules` 三层继承(系统默认 0.8/3/0.4/6/10/2.0/true ← ns 规则 ← 任务规则,只覆盖非 null 字段);`MasterLoop.doSetRules` 整包覆盖语义补全字段 null 校验
- **文件**:`dcp-scheduler/.../model/ScaleRules.java`、`alloc/Autoscaler.java`、`master/MasterLoop.java`

### M2(中):beforeKeyOf 与 businessKey 键空间不一致

- **缺陷**:businessKey 取映射后模型字段,而 beforeKeyOf 从 before 镜像 JSON(按源列名构建)同名取值,业务键被重命名/做值转换时取 null → 空串 → 主键修改误报停任务
- **修复**:`FieldMappingExecutor` 增 `beforeKeySourceColumn()`(field-map→源列名;未声明映射→字段名本身;compute/uuid/system→null)与 `applyBeforeSteps()`(确定性加工链重放);`beforeKeyOf` 按源列名取旧值后重放加工链,与 businessKey 同变换口径;任一业务键为生成列(不可比对)→ 整体跳过检测(宁漏检不误停)
- **文件**:`seatunnel/cdc-seq-transform-src/.../transform/CdcSeqTransform.java`、`FieldMappingExecutor.java`

### M3(中):数据库口令 root123 五处硬编码兜底

- **缺陷**:backend application.yml 五处 `:root123` 兜底(SPRING_DATASOURCE_PASSWORD/SYNC_TARGET_PASSWORD/SYNC_CDCST_ALERT_DB_PASSWORD/INGEST_META_PASSWORD/LAKESYNC_META_PASSWORD),生产漏配时静默用弱口令
- **修复**:backend + dcp-worker(另 2 处)共七处去兜底(缺失即启动失败);docker-compose 全部 MySQL 连接口令统一为 `MYSQL_ROOT_PASSWORD` 单一事实源必填(`${MYSQL_ROOT_PASSWORD:?}`),含两个 mysql 容器 MYSQL_ROOT_PASSWORD 与 mysqladmin 健康检查(`-p$$MYSQL_ROOT_PASSWORD`);backend 容器段补传 SYNC_TARGET_PASSWORD/SYNC_CDCST_ALERT_DB_PASSWORD/LAKESYNC_META_PASSWORD
- **文件**:backend/dcp-worker application.yml、docker-compose.yml、.env.example

### L1(低):SyncConsumer 异常回退整批重放

- **缺陷**:handleBatch catch 回退分支对整批 records 全部 `processOne`,主路径已跳过(不落死信)的水位事件被逐条重放 → NPE 落死信无限增长
- **修复**:回退路径复用主路径过滤——isWatermark 跳过、parseLogicalTable 为 null 落死信,两者仅推进 offset;其余才走 `processOne`
- **文件**:`dcp-synclink/.../core/SyncConsumer.java`
