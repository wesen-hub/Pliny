## 一、高危(MUST FIX,2 项)

### 高危-1:T0Selector GC 安全余量单位错——毫秒直接加 TSO(一期遗留,仍未修复)

- 位置:`outlet-control/.../T0Selector.java`(R2 新增 `long gcFloor = gc + gcSafeMarginMs;`)、`outlet-adapters/.../TiDbGcSafePoint.java`(L68 `toTso`: `ms << 18`)
- 实查证据:`TiDbGcSafePoint.gcSafePointTs()` 返回 TSO(`ms << 18`),T0Selector 直接 `gc + gcSafeMarginMs`(margin 默认 120000 毫秒)
- 影响:TSO 中 1ms ≈ 2^18 tick,`+120000` 实际只抬升约 **0.46ms**,注释宣称的「2 分钟余量」完全失效,紧贴 GC safe point 取 T0 时快照读窗口内版本仍可能被 GC 回收
- 修法:`gc + (gcSafeMarginMs << 18)`(margin 保持毫秒语义),并补一条离线断言约束 margin 生效(如 margin=2min 时 T0 至少比 GC safe point 大 2min 折算 tick)
- 逃逸原因:T0AdaptersCheck 未覆盖 margin 行为

### 高危-2:dcp-gateway 把无鉴权服务暴露为公网唯一入口

- 位置:`dcp-gateway/src/main/resources/application.yml`(路由 delivery-chg→`lb://delivery-service`、outlet-control→`lb://dcp-outlet-control`、scheduler-admin→`lb://dcp-worker`)、`frontend/nginx.conf` L25-28(`location /api/` 全量转发 `dcp-gateway:8088`)
- 实查证据:delivery-service、outlet-service、dcp-worker 三服务 **均无 spring-boot-starter-security 依赖、无 SecurityFilterChain、无 @PreAuthorize**;delivery-service OutletController 注释自认「鉴权(骨架):X-Dcp-Token 头(required=false)不做校验」;outlet-service TasksController/StreamsController 无任何鉴权
- 影响:拆分时迁出域未携带鉴权层,此前未收敛到统一公网入口;新网关把它们变成公网可达——匿名可调 POST /api/outlet/tasks(建/停任务)、/api/outlet/streams/scan、读 /api/outlet/contracts/{ref}(泄露列白名单+脱敏规则)、/api/chg/{stream}/changes(变更流数据)
- 修法(二选一):①三服务补 Spring Security + 复用 JwtAuthFilter(至少 `anyRequest().authenticated()`);②网关统一 JWT 校验并仅放行白名单路径
- **需确认**:这三个服务是否本意只内网可达(若是,网关不暴露其路由即可;若是管理面/数据面要公网,则必须补鉴权)

## 二、中危(SHOULD FIX,4 项)

### 中危-1:ProductionMessageDecoder 单一 tso 字段混用三个时间域

- 位置:`dcp-outlet-rt/.../ProductionMessageDecoder.java` L91/L145(CDC 分支 `tso=commitTsOf(root)` TSO 域 ~4.5e17;打标分支 `tso=ts` epoch millis;入站分支 `tso=inboundTso` millis)、`UnitRunner.java` L211/L215(统一 `d.tso() > t0` 过滤 + `Math.max(lastTso, d.tso())` 水位推进)
- 影响:任一打标/入站任务若被配 TSO 域 startTso,millis 值恒小于 TSO → 全部事件被静默过滤;跨域比较污染 lastTso/水位。当前入站靠「startTso=0」隐式约定,无代码兜底
- 修法:`DecodedMessage` 增时间域枚举(TSO/MILLIS),过滤/水位前按域归一
- **需确认**:打标/入站任务是否只可能配 startTso=0

### 中危-2:ContractViewCodec null→"*" 全放行与「安全默认」自相矛盾(一期遗留)

- 位置:`delivery-service/.../outlet/adapters/ContractViewCodec.java` L39(`allowedColumns==null` 编码为 `"*"`)、L81(`"*"` 解码回 null → DefaultContractFilter 不裁剪)
- 影响:列白名单为 null 即整行透传,与「宁可中断绝不无裁剪放行」fail-closed 精神相悖;若管理面误配或外部消费方契约配成 `"*"`,数据整行放行
- 修法:契约写入侧校验 `"*"` 仅允许 internal 消费者,否则下发空视图;或 decode 端对非 internal 场景拒绝 `"*"`
- **需确认**:`"*"` 契约是否仅限 internal 创建路径(代码中未见 consumer_type 门禁)

### 中危-3:SecurityConfig `/api/ingest/**` permitAll 与 @PreAuthorize 并存(一期遗留)

- 位置:`backend/.../config/SecurityConfig.java` L52(`.requestMatchers("/api/ingest/**").permitAll()`)+ `IngestAppController` 7 端点全部 `@PreAuthorize`
- 影响:匿名请求通过过滤链后触发方法级鉴权 → 403 而非 401,前端「过期跳登录」逻辑失效;且未来新增 ingest 端点若忘写 @PreAuthorize 即裸奔(纵深防御削弱)
- 修法:删除该 permitAll 改 `anyRequest().authenticated()`(现无 ingest 端点依赖匿名访问;若未来有 appKey 提交端点再单独白名单)

### 中危-4:RestClient 无 connect/read 超时(WorkerClient + TagV2Deployer)

- 位置:`backend/.../schedulerbridge/WorkerClient.java`(L51 `new JdkClientHttpRequestFactory()` 无超时)、`tagengine-service/.../TagV2Deployer.java`(同构,一期遗留)、outlet-service 同名 WorkerClient(同构)
- 影响:dcp-worker/TiCDC 挂死或网络黑洞时,提交 TaskSpec、建任务、流扫描调用长时间阻塞,累积拖垮线程/请求队列
- 修法:`JdkClientHttpRequestFactory#setReadTimeout(5s)` + `HttpClient.newBuilder().connectTimeout(3s)`;另 `GovernanceConfig` 自定义 RestClient.Builder bean 未声明 `@Scope("prototype")`(与 Boot 自动配置原型语义不同,baseUrl 共享隐患),建议补 prototype
