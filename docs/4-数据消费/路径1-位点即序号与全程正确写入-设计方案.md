# 数据同步链路设计方案:位点即序号 + 全程正确写入

- 版本: v1.0
- 日期: 2026-09-27
- 状态: 设计定稿,逐步落地中
- 定位: 以 TiDB 为目标库、以 TiCDC 消费底座为下游的全量同步链路(先批后流)一致性设计
- 结论先行: 链路层允许重放;重放在 TiDB 写入层被"裁判"吸收;TiCDC 只见单向前进事件

---

## 1. 背景与目标

### 1.1 要解决的问题

SeaTunnel 全量同步(先批后流)在故障恢复时会重放"已写入但 checkpoint 未记录"的数据。历史问题:

- 重放数据以"新号"写入 → 目标库出现**短暂倒退**(旧值覆盖新值);
- TiCDC 监听到非单调的变更事件 → 消费底座的窗口聚合(如"十分钟总和")被重复/回退扰动;
- 号段模式下,重放不可识别,回退窗口内下游可能已消费错误事件。

### 1.2 目标:全程正确(all-time correctness)

**重放必须在 TiDB 写入层截止**。验收口径:

1. 允许链路层重放(渠道语义不变);
2. 重放事件到达 TiDB 时被**确定性拒绝**(零写入,不依赖引擎隐式行为);
3. TiCDC 感知到的事件序列**单调前进**,不存在"内容重演"与"倒退";
4. 最终数据一致(重放不影响终态)。

### 1.3 关键洞察

TiCDC 的 commitTs 天然单调(每次写入领新 TSO)——**"内容重演"才是问题**,所以必须在 TiDB 写入前挡住,而不是在事件层补救。

## 2. 号码体系(路径 1:位点即序号)

### 2.1 核心思想

**seq = f(源端位点)**。位点在源端生成,与内容天然绑定;同一事件无论重放多少次、经过多少代任务,得到的号恒定——重放因此可被目标端识别。

**四判据**(数据源是否适用路径 1):

| 判据 | 含义 |
|---|---|
| 源端生成 | 位点由源库产生(不是采集端自增) |
| 内容绑定 | 位点与事件内容一一对应(Debezium 已采集) |
| 单主流内单调 | 单源单主库内位点严格递增 |
| 逐行可得 | 每条事件(含快照行)都能拿到位点字段 |

### 2.2 两种号

| | 事件级号 P | 快照级号 S |
|---|---|---|
| 适用 | 流阶段(增量事件) | 批阶段(全量快照) |
| 取值 | f(事件位点),逐事件不同 | f(快照起点位点),**全批同号** |
| 语义 | "这行内容最后一次实际变化的时刻坐标" | "这批基线的一致性时刻坐标" |
| 关系 | 流号恒 > S(流从快照起点之后读) | 与流号同源同构,同一号码空间 |

### 2.3 六条不变式

1. **重放恒定**:同一位点的事件,任何时刻、任何代任务编码出的 seq 相同;
2. **单源单调**:单源内位点递增 ⇒ seq 递增(含快照段 → 增量段的衔接);
3. **下游零改动**:消费底座不加任何去重/窗口修补逻辑,正确性靠写入层吸收;
4. **per-source 序列**:号码只在各自源内可比;多源合流禁止跨源 seq 行级裁判;
5. **fail-fast**:位点缺失/格式未知/位宽溢出 → 立即失败,不降级、不猜;
6. **体系重置必检测**:源端位点体系重置(换主、binlog 重建)→ 必须告警并停止增量接续判断。

### 2.4 编码器:逐源公式(实证字段 + 真实演算)

统一形态:`seq = 高位段 × 基数^k + 中位段 × 基数^j + 低位段`,各源基数/位移见下表(低位段宽度按实测上限预留):

| 源 | 位点字段(已 javap 实证) | 编码公式 | 实例 |
|---|---|---|---|
| MySQL | `file` / `pos` / `row` | `fileNo<<44 \| pos<<12 \| row` | `42/12345678/2` → **738,922,381,762,562** |
| PostgreSQL | `lsn`(logid/offset) | `(logid<<32\|offset) << 10` | `1/16B37420` → **4,788,046,561,280** |
| Oracle | `commit_scn` / `lcr_position` | `commit_scn<<12 \| lcr_position` | `253772415887/3` → **1,039,451,815,473,155** |
| SQLServer | `commit_lsn` / `event_serial_no` | `lsn_num ×10^6 + serial` | **48,378,511,714,305**(= 48,378,511×10⁶ + 714,305) |
| MongoDB | `ts_sec` / `ts_inc` / `order` | `平移后ts_sec ×10^9 + ts_inc` | **7,683,696,492,544,000,005**(= 7,683,696,492×10⁹ + 544,000,005) |
| TiDB | TSO(输出字段待实测) | TSO 天然 64 位有序,直接透传 | — |
| OpenGauss | LSN | 与 PG 同族(接入结构待源码核实) | — |

**快照段**:`S = f(快照起点位点)`(低水位,快照开始前的位点)。例:MySQL 快照起点 `42/12345678/0` → `S = 738,922,381,762,560`。

### 2.5 满位源治理与守卫

- **满位源**(Mongo/TiDB,位点接近 64 位上限):时间基准平移、低位裁剪,或回退号段模式(逐源评估);
- **守卫四件套**:位宽溢出检测、未知格式 fail-fast、新旧号混发检测、体系重置告警(如 MySQL `server_uuid` 变化)。

## 3. 链路改造

### 3.1 Connector 补丁层(已 jar 级实证)

**做什么**:把 Debezium `SourceRecord` 中现成、但被 SeaTunnel 反序列化丢弃的位点字段,作为额外一列 `__src_pos` 透传到行数据。**不引入对源库的任何额外查询**。

**集成点**(对 `connector-cdc-base-2.3.12.jar` javap 实证):

```java
// 现成接口
public interface MetadataConverter extends Serializable {
    Object read(SourceRecord record);          // 位点就在入参
}
// 现成装配链:SeaTunnelRowDebeziumDeserializationConverters(…, MetadataConverter[] metadataConverters, …)
// 现成注入点:SeaTunnelRowDebeziumDeserializeSchema$Builder.setMetadataConverters(MetadataConverter[])
```

**改动清单**:新增 `PositionMetadataConverter`(读 `sourceOffset()/sourcePartition()`,按源分派键名)+ 在构建点注册(开关 `emit.position=true`)+ schema 追加 `__src_pos` STRING 列。

**构建面**:已实证 5 个 connector jar 均不含 base 类(各 0 个),base 独立(97 类)——**只重打 `connector-cdc-base-2.3.12.jar` 一个 jar**,复用现有"patch 源码 → 编译 → 替换 jar → 进镜像"管线。

**7 源分派**:机制 1 处;提取规则按源一张映射表;TiDB/OpenGauss 的接入结构(是否复用 base)拉源码核实后,同思路各接一处。

### 3.2 Transform 层(cdc-seq-transform)

- 输入:含 `__src_pos` 的行 + snapshot 标志;
- 处理:解析位点字符串 → 按源编码器算 `seq = f(位点)` → 注入 seq 列;快照行自动得到批号 S;
- 纪律:删除对元库 `seq_counter` 的依赖;无法解析 → fail-fast;UPDATE 的前后镜像行内序利用 `row/lcr_position` 区分。

### 3.3 数据源范围

| 档 | 范围 | 结论 |
|---|---|---|
| **A 档(一期)** | MySQL、PG、Oracle、SQLServer、MongoDB、TiDB、OpenGauss(CDC);DB2-CDC(未发布) | 路径 1 原生可行 |
| B 档 | Kafka/Pulsar/RocketMQ/Sls/Iceberg/Paimon/Tablestore、9 类文件源 | 部分可走(如 Iceberg snapshotId),二期评估;Sls 需自研 cursor 映射 |
| C 档 | JDBC 查询式(~17)、OLAP(~8)、NoSQL(~12)、SaaS/消息 API(~18) | 非 CDC,不适用路径 1 |

## 4. 写入裁判设计(TiDB 侧)

### 4.1 双条件语义

| 条件 | 作用 | 适用 |
|---|---|---|
| **号条件**:新号 > 存量号 | 防倒退(重放、乱序、慢批覆盖) | 批 + 流 |
| **值条件**:业务列有实际差异 | 降噪(同值不写,零事件) | 批(流为可选项) |

`seq` 列语义 = **"行内容最后一次实际变化的来源号"**。

### 4.2 流路径模板(保持现状,零改动)

单条 upsert + 号条件,重放时 `IF(false)` 赋回原值:

```sql
INSERT INTO t (pk, c1, c2, seq) VALUES (?, ?, ?, ?)
ON DUPLICATE KEY UPDATE
  c1  = IF(VALUES(seq) > seq, VALUES(c1),  c1),
  c2  = IF(VALUES(seq) > seq, VALUES(c2),  c2),
  seq = IF(VALUES(seq) > seq, VALUES(seq), seq);
```

> **唯一待实测**:TiDB 对"no-change 的 ON DUP 赋回原值"是否零 TiKV 写/零 TiCDC 事件。若否 → 流路径改为条件 UPDATE 前置判断(模板参考 4.3)。

### 4.3 批路径模板(三步式,推荐)

```sql
-- ① 轻探存在(每批一次,JDBC batch)
SELECT pk FROM t WHERE pk IN (?, ?, ...);

-- ② 已存在行:带双条件的条件 UPDATE
UPDATE t SET c1 = ?, c2 = ?, seq = ?
WHERE pk = ?
  AND ? > seq                          -- 号条件
  AND (c1 <> ? OR c2 <> ? ...);        -- 值条件(按 schema 生成列清单, NULL 用 <=> 判等)
-- 0 行 = 确定性零写入,不依赖引擎隐式行为

-- ③ 不存在行:批量 INSERT(seq = S;并发安全可用双条件 upsert 形态)
INSERT INTO t (pk, c1, c2, seq) VALUES (?,?,?,?), ...;
```

备选:形态 B(应用端 diff,大表对账)、形态 C(单条 upsert+IF,依赖实测)。首版用形态 A。

### 4.4 模板分派

按消息 `snapshot` 标志分派:**流模板**(4.2)/ **批模板**(4.3)——两条写入路径独立,性能零损耗。补丁落地前标志为 null → 默认走流模板(向后兼容)。

### 4.5 关联机制(既有,保持)

- **删除闸门**:DELETE 事件参与闸门,防"删除后迟到旧写入复活";
- **多源合流**:writer 列隔离 + 权威合并;严禁跨源 seq 比较。

## 5. 批阶段完整设计

### 5.1 批号 S

`S = f(快照起点位点)`(来源:Debezium 低水位/快照行 offset 透传);全批同号;同空间下流号恒 > S。

### 5.2 已存在行必须逐行裁决

目标行三种来源,一条"号条件+值条件"的 UPDATE 统一裁决:

| 目标行来源 | 存量号 | 裁决 |
|---|---|---|
| 本批重跑残留 | = S | 不写(同号) |
| 上一代任务遗留 | < S′ | 值变才写(基线重建) |
| 流事件已写过(交错) | > S | 不写(防倒退) |

### 5.3 六场景验收矩阵(实际数字)

批号 `S = 738,922,381,762,560`;流事件 `P = 738,922,381,852,674`:

| # | 场景 | 行状态 | 行为 | TiCDC |
|---|---|---|---|---|
| A | 首次同步,行不存在 | 无 | INSERT(seq=S) | 1 条(正常基线) |
| B | 批重跑,值未变 | (500,'PAID',S) | 号条件 false → 0 行 | **0** |
| C | 批重跑,源值已变 | (500,'PAID',S) | 批不写;流事件 P 补 (800,'SHIPPED') | 仅流 1 条 |
| D | 全量重发 S′,值变 | (300,'NEW',旧号) | 号进+值变 → UPDATE | 1 条(基线重建) |
| E | 全量重发 S′,值同 | (800,'SHIPPED',旧号) | 号进但值同 → 0 行 | **0** |
| F | 批流交错 | (800, P)(流已写) | S < P → 0 行 | **0** |

**C 场景是本设计的核心演示:批 skip ≠ 丢数据——差异由流段补。**

### 5.4 批阶段四道防线

1. split 完成度进 checkpoint(重跑只涉未完成 split);
2. 主键 upsert 幂等(行不重复)+ 后读晚写(值方向正确);
3. 快照号 < 增量号(慢快照不覆盖增量;号段模式此场景有永久错风险,路径 1 天然免疫);
4. 全量重发新起点 S′ 截流(见过的拒、没见过的补)。

## 6. 故障恢复语义

### 6.1 重放场景矩阵

| 场景 | 触发 | 吸收机制 | 目标/事件表现 |
|---|---|---|---|
| 批部分失败重跑 | checkpoint 未记录 | 批模板(同号/值条件) | 零写入、零事件 |
| 流重放 | checkpoint 回退 | 流模板号条件 | 零写入、零事件 |
| 全量重发 | checkpoint 丢失等 | S′ + 批模板 | 仅值变行重建 |
| 批流交错 | 慢分片 | 号域不等式 | 零写入、零事件 |

### 6.2 全量重发触发条件(需监控)

- **高危**:checkpoint 容器本地存储(容器重启即丢);启停不带 savepoint(默认不带);任务删除重建(jobId 变化);
- 中低:拓扑变更/引擎升级(savepoint 不兼容)、源端位点体系重置、人工重刷;
- **必须杜绝**:`无 savepoint + startup.mode=latest`(跳过快照直接追流 = 丢全量,比全量重发严重);
- 防护:checkpoint 持久化(最高优先)→ 启停规范化(总带 savepoint + 启动前断言)→ 全量重发演练验收。

### 6.3 主键语义边界

- 同主键 = 同一行:同 seq 丢弃(幂等)、号大者赢(防倒退)、删除+重建走闸门;
- **无主键/不可唯一定位的表不入链路**(全列键遇物理重复行会撞键丢行)。

## 7. 性能设计

| 路径 | 每事件/每批写入成本 | 说明 |
|---|---|---|
| 流 | 每事件 1 条 upsert(与现状一致) | 重放时 IF false 赋回原值;实测项决定是否需调整 |
| 批 | 每批 1 轻读 + 2 组 batch 写(更新组+插入组) | 用"一次轻 SELECT"换掉"所有同值写入与事件" |

净收益:批路径批量执行(JDBC batch,判定逻辑仍逐行独立);消除的同值事件量 = 全量重发/重跑规模 × 值同比例。流路径零损耗。

## 8. 迁移与切换(号段 → 位点)

1. 先迁移 checkpoint 到**持久化存储**;
2. 新增补丁 jar 进镜像(新任务默认启用路径 1,开关隔离);
3. 存量任务:停 → 带 savepoint 重启 → 校验"同事件同号";
4. 双向验证:双跑比对(位点号 vs 旧号段号的行为差异);灰度按源/表推进。

## 9. 测试与验收

### 9.1 验收口径

- 恢复窗口内:重放事件到达 TiDB → 零写入、TiCDC 零事件;
- 六场景矩阵(A–F)全部符合;
- 全量重发演练:值变行重建、值同行静默、流衔接正常;
- 体系重置/未知格式/溢出:fail-fast 生效。

### 9.2 待实测清单(实施前置)

1. **TiDB no-change ON DUP 行为**(决定流路径形态)——最高优先;
2. 各源快照行的位点字段取值(低水位形态);
3. PG sequence 单调性;Mongo 事务内 timestamp/order 行为;
4. TiDB CDC 输出字段(TSO 精度);OpenGauss/TiDB 是否复用 cdc-base;
5. Oracle `lcr_position` 范围;SQLServer `event_serial_no` 上限;MySQL gtid 透传。

## 附录:一句话速查

- **目标**:重放截止在 TiDB 写入层,TiCDC 只见单向前进;
- **号**:`seq = f(位点)`;批号 S 快照级、流号 P 事件级、流恒 > 批;
- **批**:不存在 → INSERT;已存在 → `S > 存量号 且 值变` 才 UPDATE,否则零写入;
- **流**:单条 upsert 号条件,重放赋回原值;
- **补丁**:cdc-base 挂 `MetadataConverter`,重打 1 个 jar;
- **验收**:恢复窗口 TiCDC 零事件;全量重发只重建"值变行"。
