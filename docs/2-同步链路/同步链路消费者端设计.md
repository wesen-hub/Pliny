# 同步链路消费者端设计(SeaTunnel → Kafka → TiDB)

> 状态:设计与实现对照文档(2026-10-09 修订)。本次修订补全:加载链路、线程与队列模型、批阶段的号与代次、两套写入模板完整 SQL 示例、写者分组条件与关键设计问答;快照写入从「三步式 probe」演进为 N4 双条件 ODKU,容量规划对齐正式上线定案口径。适用形态:PB 级流量下的 CDC 同步链路写库环节。

## 一、定位与链路

数据同步链路:`源库 → SeaTunnel CDC 采集 → Kafka → 消费者 → TiDB 目标库`。本设计覆盖消费者端(Kafka 之后):从 Kafka 拉取变更数据、解析与路由、写入 TiDB 分片表、提交消费位点。正确性基石是**目标端幂等**(单条 SQL 同时承载新旧裁判与字段级部分更新),它使得整条链路可以用"至少一次投递 + 重放幂等吸收"的语义运行,并发、重试、故障恢复都以此为底座。

## 二、消费者与 topic/分区的对应关系

**一个消费者(线程)监听多少 topic?**

1. **逻辑表与 topic 一一对应**:一张逻辑表一个 Kafka topic;一份消费者任务只监听一个 topic(不做多 topic 混合消费,简化路由与隔离);
2. **一组一 topic**:每个 topic 属于独立的消费组,消费组之间互不影响(位点、故障、扩容各自独立);
3. **组内分工**:一个消费组内可部署多个消费者实例、多个消费线程,**每个线程负责该 topic 的若干分区**;同一分区在同一时刻只属于组内一个线程(由 Kafka 保证);
4. **线程与分区**:实现形态为**每分区一线程**——一个线程 assign 一个分区并串行处理,分区内顺序天然保持,分区间并行。线程数 = 该 topic 的分区数,实例数 ≤ 分区数(超出空转);
5. **一个实例承载多份任务**:一台消费者实例可同时运行多个逻辑表的消费线程,按吞吐需求组合分配;
6. **新逻辑表动态接入**:新表上线时动态注册消费监听,不需要重启实例、不需要改配置。

## 三、加载链路:框架如何装载消费者

消费者业务逻辑(jar 内)不自己起进程,由调度框架装载到 dcp-worker 宿主。完整链路:

```
调度框架(dcp-scheduler-core)
  InstanceSkeleton.reconcile:期望态 vs 实际态 diff → startExecutor(分区任务)
    → ExecutorProvider.load(SPI,ServiceLoader 发现 @ExecutorPlugin 插件)
      → SyncWriterFactory.init(environment)          ── 每工厂一次(幂等)
          new SynclinkComponents(env):组装 TargetDbRegistry / DltService
            / BatchWriteService(读 dcp.sync.buffer.* 参数) / LogicalTableReader / SyncConsumer
            ── 构造末尾 batchWriteService.init()     ← 写线程池在此启动(每工厂一次)
      → SyncWriterFactory.create() → new SyncWriterExecutor(ctx)  ── 每分区一个
    → executor.start(ctx):执行器五阶段生命周期
```

**每分区执行器(SyncWriterExecutor)启动五阶段**(新迁移一个分区任务到某实例时):

| 阶段 | 动作 |
|---|---|
| ① 状态置位 | INIT → RUNNING(调度框架记录) |
| ② 消费者初始化 | `kafka.assign(List.of(TopicPartition))` 单分区固定绑定;groupId = `dcp-sync-{taskId}`(缺省);关闭自动提交 |
| ③ 启动拉取线程 | `worker = Thread(..., "sync-writer-{taskId}-{partId}")` |
| ④ 常态循环 | `poll(500ms)`(max.poll.records=500)→ handleBatch 解析/校验/路由 → 投递逻辑表队列 → commitAfterOffer / 无记录时 commitIdle |
| ⑤ 停止 | 框架调用 stop():退出循环 + 上报最后一帧快照(stopped=true),位点留在 Kafka 侧,重启后从提交位点重放、幂等吸收 |

**关键分工**:框架只管调度与生命周期(心跳/对账/交接),**位点管理、消费逻辑、提交节奏全部由执行器自控**——框架只透传 committedOffset 派生 lag 指标,不干预提交。

## 四、线程与队列模型

### 4.1 线程分工

| 线程 | 数量 | 职责 |
|---|---|---|
| 分区消费线程 | 每分区一线程(每实例 ~15 个) | assign 单分区、poll、解析、路由、投递队列、提交位点 |
| 共享写线程池 | 每工厂 4 个(writeThreads=4) | 轮询所有逻辑表队列、攒批、写库、推进已写游标 |

消费线程与写线程完全解耦:消费线程只做「拉取+处理+投递」,写库由共享写线程池完成,两者之间是有界队列。

### 4.2 逻辑表队列的初始化(消费线程之间共享吗?)

**按逻辑表隔离:每逻辑表一条有界队列,同一实例内同表的多分区消费线程共享这一条表队列,跨表隔离。**

```java
// BatchWriteService.ensureQueue:第一次投递时惰性创建,线程安全
public ArrayBlockingQueue<BatchEntry> ensureQueue(String logicalTable) {
    return queues.computeIfAbsent(logicalTable, k -> new ArrayBlockingQueue<>(queueCapacity));
}
```

- 队列容量 `dcp.sync.buffer.queue-capacity = 2000`(每逻辑表);
- 消费者线程投递满 → `offer` 返回 false → sleep 20ms 重试(**不 pause consumer**,避免容器接口耦合;max.poll.interval 内队列必被消化);
- 背压传导链:队列满 → 消费线程投递停顿 → poll 停顿 → Kafka 侧自然积压。

### 4.3 写线程池的创建(谁启动的?)

**SynclinkComponents 构造函数末尾的 `batchWriteService.init()` 启动**,即「第一个分区任务装载触发 Factory.init → 组装组件 → 启动写线程池」,**每工厂一次**,不是每分区一次:

```java
public void init() {
    writerPool = Executors.newFixedThreadPool(Math.max(1, writeThreads),
            r -> { Thread t = new Thread(r, "dcp-batch-writer"); t.setDaemon(true); return t; });
    for (int i = 0; i < writeThreads; i++) writerPool.submit(this::writeLoop);
}
```

### 4.4 写线程行为与攒桶(同物理表由谁写?)

每个写线程独立执行 writeLoop:**轮询所有逻辑表队列**(每队列 `drainTo(drainPerQueue=200)` 限流,避免单队列独占写线程)→ 按 `BucketKey = (物理表, 批流模板)` 攒桶 → 够批(batchSize=500)或够时(batchTimeoutMs=100)flush。

注意两个实现事实:
1. **攒桶(buckets)是每个写线程的局部变量** → 同一物理表的 op 可能被不同写线程各自攒桶、并发 flush,即**同物理表允许并发写**(不再要求"一表一线程");
2. 正确性不依赖写串行:原子 upsert 的号裁判在**单条 SQL 内、行锁下**完成,跨写线程并发写同一行也只会「大号胜」——这正是原子 SQL 兜底取代串行约束的设计取舍(吞吐优先,正确性交给裁判)。

### 4.5 三层分组体系(从队列到 SQL)

```
① 队列层:按逻辑表隔离(ArrayBlockingQueue 2000/表)
      ↓ 写线程轮询所有队列,drainTo(200) 限流
② 攒桶层:BucketKey = (物理表 table, 批流模板 snapshot)
      快照批与增量批分开攒、分开 flush
      ↓ flush 时调 DAO
③ SQL 层:桶内按写者列 writer 二次分组
      每组一条 SQL,各自比各自的号
```

### 4.6 写者分组条件(写入按什么分组?)

**写者列名(writer column),即「任务实例 × 数据源 × 库 × 表」四元组的编码:**

```java
// AtomicUpsertDao.writerColOf:同一四元组的流共用一列,各自比各自的 seq
String raw = "_s" + taskId + "_d" + datasourceId + "_" + sourceDb + "." + sourceTable;
// 非 [A-Za-z0-9_] 替换为 _;超 60 字符截前 43 位 + "_" + md5 前 16 位
// 例: _s101_d88_erp_orders
```

- **分组规则:四元组完全相同 → 同组;任一维度不同 → 不同组**;
- 一组生成一条多值 SQL,裁判条件只引用本组自己的写者列;
- **为什么必须分组**:一条 SQL 只能有一个裁判列。混批后果(实打实的 H2 缺陷):多源 op 共用首个 op 的裁判列 → 他源写者列永不推进(自己的号永远写不进自己的裁判列,后续写入全被误判)+ 字段并集补空串静默清列(清掉别的写者写的值);
- 分组后:**每条流独立比号、跨任务/跨源互不压制**——「写者列裁判是唯一裁判」的落点。

## 五、完整流程:拉取 → 处理 → 写库 → 提交 offset

### 阶段一:拉取

- 消费者线程批量拉取(每次一批,数百条),拉取动作由线程串行执行;
- 拉取配置:关闭自动提交(提交由"已写游标"控制,见阶段四);poll 500ms、max.poll.records=500;
- 一个 topic 一个消费组,分区由调度框架逐分区 assign(固定绑定,迁移时直接改 owner,AGGRESSIVE 交接,重复消费由目标端幂等吸收)。

### 阶段二:处理(解析、校验、路由、分流)

对拉到的每一批、每一条消息,依次:

1. **水位事件过滤**:TiCDC enable-tidb-extension 每秒一条水位事件(非数据行)→ 跳过,offset 直接推进游标(ackOffsets,不写库不落死信);
2. **解包**:仅 SeaTunnel 采集端信封格式 `{"__bucket":N,"__payload":"<CdcRecord JSON>"}`,解析 CdcRecord;缺 logicalTable 的坏消息 → 落死信留证(不阻断本批其余记录);
3. **写者身份判定**:每条消息携带写者身份(taskId/datasourceId/sourceDb/sourceTable)→ 编码写者列名。**身份缺失 → 落死信拦截**(新方案写者列裁判无法定位,不允许无身份写入);
4. **主键修改兑底拦截**:`beforeKey ≠ businessKey` → 落死信不写库(采集端已告警暂停任务,消费端兑底拦截,不再拆 DELETE+INSERT);
5. **路由**:对业务主键做哈希(固定算法、固定种子,跨环境一致):
   - 桶号 = hash(主键) % 4096(与 Kafka 分区键一致,保证同主键同分区、同分区顺序消费);
   - 物理表号 = hash(主键) % 分片表数 → 定位目标物理表;
   - 桶数、表数、种子一经上线不可变更(变更 = 同主键换桶换表 = 数据分裂);
6. **主键列回填**:源端字段映射可能不含主键列,而目标端定位行必须用主键 → 从消息的业务键回填(单主键直填,复合主键按分隔符拆分);
7. **快照/增量分流**:消息携带 snapshot 标志(采集端打标,见第六章)。`snapshot=true` → 快照写入流程(批路径);否则 → 增量写入流程(流路径);
8. **投递**:处理结果投入**该逻辑表的有界队列**(快照批与增量批各自成批投递);队列满则等待重试;主路径异常时逐条兜底处理,单条失败写入死信,不阻塞整批。

### 阶段三:写库

- **攒批**:写线程把投递进来的操作按「物理表 + 快照/增量」分桶攒批;**够量(500 条)或够时(100ms)**触发一次 flush——低流量靠时间触发保证及时性,高流量靠条数触发保证吞吐;
- **增量写入(流路径)**:桶内按写者列分组,每组一条**多值 INSERT...ODKU**,号进即覆盖(见 7.2);
- **快照写入(批路径)**:按写者列分组、子批 500 条,每组一条**双条件 INSERT...ODKU**,号进且值变才写(见 7.1);
- **失败处理**:整批 flush 失败 → **逐条隔离重试,重试仍失败逐条入死信**(记录失败原因),不整批丢弃、不原地无限重试;失败不影响位点推进策略(位点按"已写游标"推进,未写部分后续重放由幂等吸收);
- **事务粒度**:一表一批一事务,不跨表。

### 阶段四:提交 offset

提交语义核心:**提交的是"写库进度",不是"拉取进度",绝不超前**。

1. **已写游标**:写线程每成功落库一批,就把对应分区"已写到的位置"更新到游标(offsetCursor,取 max);
2. **追平等待**:消费线程在投递一批后,等待写线程把这一批全部写完(有界等待,默认 flush-wait 15s),然后执行提交(commitAfterOffer;commitSync 节流,commitIntervalMs=5s);
3. **提交值 = 已写游标**(commitSync 已写游标+1):即使出现"拉取了很多但写库没跟上",提交也只会停在写库进度之后——**可以滞后(多写由幂等吸收),绝不超前(超前即漏数据)**;
4. **追平超时**:等待超时则只提交已写完的部分,未写完的尾部由后续批次的追平检查兜底;无新记录时周期 commitIdle 补交尾部,避免"最后一批永远不提交"的假延迟;
5. **跳过记录的游标推进**:水位事件、已落死信的消息通过 ackOffsets 直接推进游标(已处理,不因批写库失败重放重复落死信);
6. **提交失败**:再平衡窗口期的提交失败属正常,下一轮重试;崩溃后从未提交位置重放,由目标端幂等吸收。

## 六、批阶段的号与代次

### 6.1 批号定义:S = f(快照起点位点)

```
增量行:seq = f(源端位点)                      ← PositionSeq,每行一个,严格递增(位点即序号)
快照行:seq = S = f(snapshot_start_position)   ← 整批同号,批级代次
```

**为什么快照行不能逐行发号**:SeaTunnel 快照阶段是源库全表 SELECT,行本身不携带逐行递增位点(实测 file=""、pos=0 空形态),全批只有一个恒定的「快照起点位点」。S 必须满足三个条件:
1. **重放恒定**——断点续采重放时 S 不变;
2. **小于一切增量位点号**——流号恒 > S,保证流能覆盖批;
3. **与增量号同源同构**——同一编码函数、同一号列(写者列),可统一比较。

**代次语义**:批号 S 就是代次标记。每次重新提交全量任务 = 新读一次起点位点 = 新 S = 新一代;目标行号列携带的存量号天然区分「本批重跑残留(同号不写)/上一代遗留(值变才更)/流已写(禁写)」。

### 6.2 snapshot_start_position 的获取(方案 A)

**后端在任务提交前主动直连源库读「当前位点」,持久化后下发:**

```
任务提交(needsSnapshot)→ 查 cdc_st_task.snapshot_start_position 存量
  ├─ 已有值(重启/重放)→ 复用(重放恒定)
  └─ 为空(首次)→ CurrentPositionReader.read(dsType, ds, pwd, sourceDb):
       mysql      SHOW MASTER STATUS              → "mysql:{file}:{pos}:0"
       postgresql SELECT pg_current_wal_lsn()::text → "pg:{lsn}"
       oracle     SELECT CURRENT_SCN FROM V$DATABASE → "oracle:{scn}:0"
       其余源未实现 → fail-fast(快照行无 S 无法编码,不允许静默降级)
  → UPDATE cdc_st_task SET snapshot_start_position = ?(持久化)
  → 进入 PreparedTask → 作业族 job 配置 → CdcSeqTransform.snapshot_start_position
     → 快照行 resolveSeq → snapshotSeq(PositionSeq.encode + 缓存,全批同号)
```

### 6.3 快照/增量判定(采集端打标,消费端只认标志)

```
采集端 CdcSeqTransform:
  ① 补丁透传 __snapshot 列 = "true" → 快照行
  ② 位点主段为空 → 快照行(实测 MySQL 快照行 sourceOffset = "mysql::0:",
     file=""、pos=0;增量行 file 必非空 → 主段空仅快照阶段出现)
  → rec.put("snapshot", isSnapshot) 写入 Kafka
消费端:Boolean.TRUE.equals(rec.getSnapshot()) → snapOps(批路径) / ops(流路径)
```

补丁落地前 snapshot 为 null → 默认走增量模板(兼容期)。

### 6.4 双位点体系与衔接不等式

SeaTunnel 快照期间内部另有**引擎自取**的衔接位点(全局 binlog 起点 + 每 split 的 low/high watermark),用于「快照期间变更不丢不重」,与平台批号位点是两套体系、互不传递。两者唯一的必然联系是**时序不等式**:

```
T1(后端读位点→S) ≤ T2(引擎启动自取位点) ≤ 一切增量位点
  ⇒ S < 一切增量号(恒成立)
  ⇒ 号裁判天然给出正确裁决:快照永远只能被增量覆盖,增量永远不会被快照倒退
```

- **小多少无实际影响**:号裁判只做大小比较(`存量号 < 新号 ? 写 : 拒`),S 的绝对值没有语义;
- **位点轴区间**:(T1, T2] 的源库变更不进增量流(引擎从 T2 拉 binlog),由快照全表扫描读到新值、以号 S 写一次——不丢不重;(T2, 快照完成] 的变更行会双写(快照行 + 增量事件),是「旧值一次、新值一次」的时间线重放,不违反精确一次(见 Q1);
- 设计取舍:后端**故意不追求**与引擎启动位点相等,只保证「小于」——对齐需要跨进程共享位点的强一致契约,而不等式已覆盖全部正确性(能用不等式解决的不做强一致)。

## 七、两套写入模板与完整 SQL 示例

> 示例背景:逻辑表 biz_orders,物理表 orders_0,业务键 order_id,写者列 `_s101_d88_erp_orders`(任务 101 × 源 88 × 库 erp.orders),批号 S=105553116909568。

### 7.1 快照写入(批路径):双条件 ODKU,号进且值变才写

**N4 定案:不做 probe 分组,全部走一条双条件 INSERT...ODKU,插入与条件更新原子完成。** 完整 SQL:

```sql
INSERT INTO `orders_0`
  (`order_id`, `amount`, `status`, `updated_at`, `_s101_d88_erp_orders`)
VALUES
  ('A1001', '300.00', 'PAID', '2026-10-01 10:00:00', 105553116909568),
  ('A1002', '150.00', 'NEW',  '2026-10-01 10:00:00', 105553116909568)
ON DUPLICATE KEY UPDATE
  `amount`     = IF(`_s101_d88_erp_orders` < VALUES(`_s101_d88_erp_orders`)
                    AND NOT(`amount` <=> VALUES(`amount`)),          -- 号进 且 值变
                    VALUES(`amount`), `amount`),
  `status`     = IF(`_s101_d88_erp_orders` < VALUES(`_s101_d88_erp_orders`)
                    AND NOT(`status` <=> VALUES(`status`)),
                    VALUES(`status`), `status`),
  `updated_at` = IF(`_s101_d88_erp_orders` < VALUES(`_s101_d88_erp_orders`)
                    AND NOT(`updated_at` <=> VALUES(`updated_at`)),
                    VALUES(`updated_at`), `updated_at`),
  `_s101_d88_erp_orders` = IF(`_s101_d88_erp_orders` < VALUES(`_s101_d88_erp_orders`)
                    AND (NOT(`amount` <=> VALUES(`amount`))
                      OR NOT(`status` <=> VALUES(`status`))
                      OR NOT(`updated_at` <=> VALUES(`updated_at`))),  -- 确有列变才推进号
                    VALUES(`_s101_d88_erp_orders`), `_s101_d88_erp_orders`)
```

判定矩阵:

| 目标行状态 | 条件①号进 | 条件②值变 | 结果 |
|---|---|---|---|
| 不存在 | — | — | INSERT 分支插入新行(号 S) |
| 存量号 < S(上一代遗留) | ✓ | 有列变 ✓ | 更新变化列,写者列推进到 S |
| 存量号 < S | ✓ | 全同 ✗ | 零写入(零同值写入),写者列不推进 |
| 存量号 = S(本批重跑残留) | ✗ | — | 拒写(幂等) |
| 存量号 > S(流已写新号) | ✗ | — | **拒写(防倒退,核心)** |

**为什么废除「先查一次库」的旧三步式**:旧版 `probe(探存在) → 已存在行条件 UPDATE → 不存在行 INSERT`,probe 与写入之间的竞态窗口无法原子化——probe 说「存在」→ 并发删除 → UPDATE 0 行匹配 = **静默漏写**;probe 说「不存在」→ 并发插入 → INSERT 撞唯一键。N4 改造后「行存在与否都由一条 ODKU 双条件覆盖,并发删除 → INSERT 重插,不丢行」,库自己当 probe,应用层不再查询。

**NULL 安全铁律**:值变判断用 `NOT(col <=> VALUES(col))`,严禁 `<>`——`NULL <> 新值` 恒为 NULL 被当「无变化」,NULL 变更会永久漏写。

### 7.2 增量写入(流路径):单条件多值 ODKU,号进即覆盖

```sql
INSERT INTO `orders_0`
  (`order_id`, `amount`, `status`, `updated_at`, `_s101_d88_erp_orders`, `seq`)
VALUES
  ('A1001', '310.00', 'SHIPPED', '2026-10-02 08:00:00', 105553117123456, 105553117123456),
  ('A1002', '150.00', 'PAID',    '2026-10-02 08:00:01', 105553117123457, 105553117123457)
ON DUPLICATE KEY UPDATE
  `amount`     = IF(`_s101_d88_erp_orders` < VALUES(`_s101_d88_erp_orders`),  -- 仅号进
                    VALUES(`amount`), `amount`),
  `status`     = IF(`_s101_d88_erp_orders` < VALUES(`_s101_d88_erp_orders`),
                    VALUES(`status`), `status`),
  `updated_at` = IF(`_s101_d88_erp_orders` < VALUES(`_s101_d88_erp_orders`),
                    VALUES(`updated_at`), `updated_at`),
  `_s101_d88_erp_orders` = GREATEST(`_s101_d88_erp_orders`, VALUES(`_s101_d88_erp_orders`)),
  `seq` = GREATEST(`seq`, VALUES(`seq`))
```

语义:号进即覆盖(不查值变——增量号严格递增,号进即代表源端新状态);写者列/seq 只增不减;同号或小号重放(断点续采、乱序)→ 条件 FALSE → 零写入,幂等。

**增量 DELETE(带号条件闸门)**:

```sql
DELETE FROM `orders_0`
WHERE `order_id` = 'A1003'
  AND `_s101_d88_erp_orders` < 105553117123458   -- 存量号 < 本次号才删,防旧删除重放误删新行
```

### 7.3 两条 SQL 的差异对照

| 维度 | 快照 SQL | 增量 SQL |
|---|---|---|
| 号来源 | 全批同号 S(起点位点编码) | 逐行位点号,严格递增 |
| 业务列条件 | `号进 AND NOT(<=>)` 双条件 | `号进` 单条件 |
| 写者列推进 | `号进 AND 任一列值变` | `GREATEST` 只增不减 |
| seq 列 | 不维护 | `GREATEST` 维护(行级展示) |
| 判据目标 | 防倒退 + 防重跑 + 零同值写入 | 防重放 + 防乱序 |
| 为什么条件不同 | 全批同号 S,「值变」承担防上一代遗留同值行被无意义更新 | 逐行递增号,号进即新数据,无需逐列比较(多值 SQL 里代价大) |

## 八、顺序性保障

```
分区内顺序(每分区一线程串行拉取处理)
  → 队列入队顺序(单队列先进先出,同表同队列)
  → 跨分区/跨表/跨写线程并发写 → 目标端原子 SQL 号裁判兜底(号大者赢)
```

写入端为了吞吐放弃「同表串行写」(4 个写线程各自攒桶,同物理表可能并发 flush),正确性交给单条 SQL 内的原子裁判(ODKU 行锁下 IF 判定,小号后落盘也覆盖不了大号)——这就是目标端 upsert 语义存在的意义。

## 九、为什么用消费组自治而不是租约下发

判断标准一句话:**"重复消费的代价"决定分布式控制的强度。**

1. **重读无害**:重复拉取同一批数据,重写一遍,目标端幂等吸收(同号丢弃、号大者赢)——没有副作用;
2. **状态可重建**:唯一进度状态是已写游标,持久化在 Kafka 侧;实例重启/再平衡后从提交位点继续,未提交部分重放、幂等吸收;
3. **不依赖精确起点**:快照行自带标志走快照流程,增量行靠序号裁判,不依赖"精确到哪一条"的起点。

三条全部成立 → 分区分配、故障转移全部交给 Kafka 消费组(平台侧按 AGGRESSIVE 交接直接改 owner),平台侧只需要"无状态 + 幂等兜底 + 背压"三件套,不需要租约、防双、精确起点下发。

**边界**:目标端不是幂等写(不支持 upsert 的库、通知类副作用)时,以上前提不成立,必须换用租约 + 防双 + 精确起点的重控制模式。

## 十、容量规划(正式上线定案口径)

> 详细推导见《正式上线部署方案》与《Kafka双栈部署模型与参数配置》。本节只列消费者端相关定案。

- **100 逻辑表**(Kafka 平台栈规划总数),采集全量段 50 万条/s、增量 10 万条/s(库限速 1 万条/s);
- **分区规划公式**:分区数 = max(3, ceil(表并发 ÷ 单分区能力线 1 万条/s));表并发 = 来源库数 × 单库贡献(库限速 ÷ 库内表数);下界 3 锚定 broker 数(防单分区流量钉死单 broker 热点),上界 50(单表 50 万 QPS ÷ 1 万);落地 **~300 分区**,理论上限 100×50=5000(受 Σ 表并发≡50 万守恒约束实际不可达);
- **20 台消费者实例**(设计值 25 万 QPS,每实例 1.25 万条/s、负载 62.5%;集群上限 30 万 = 1.5 万条/s/实例);
- **每实例线程**:300 分区 ÷ 20 ≈ **15 个分区任务线程 + 4 个共享写线程**;
- **写放大账**:快照窗口(全量段)内增量 ~20 亿行与快照行双写(时间线重放,+20% 写入次数),速率预算不受影响(25 万 QPS 已含增量实时消化口径);
- **瓶颈在写库端不在消费端**,设计重心是写库并发的每一分都用到刀刃上。

## 十三、关键设计问答(Q&A)

**Q1:快照行和增量行对同一行双写,会不会违反精确一次?**

不会。精确一次(effectively-once)的定义对象是「源端变更事件」:每条事件恰好生效一次。快照行不是事件,是初始装载的产物。快照窗口内发生变更的行,源端确实经历了「旧值 → 新值」两次状态变化,目标端写旧值(号 S)一次、写新值(号 > S)一次 = 每个源端状态恰好一次,是**时间线重放**,不是重复。真正的重复(同一事件同号生效两次)被号裁判拒之门外。顺序 1(快照先、增量后):旧值 → 新值,恰好一次且时间线完整;顺序 2(增量先、快照后):快照行号 S < 存量增量号 → 批模板条件拒绝,初始化基线被跳过,直接到终态。平台语义 = 至少一次投递 + 位点即序号 + 幂等裁判 = 每条变更恰好生效一次、终态不倒退。

**Q2:S 与增量号的差距有影响吗?**

无。号裁判只做大小比较(只比大小不比距离),S 的绝对值没有任何语义;小 1 和小 10^18 完全等价。后端只需要「读得比引擎启动更早」(时序天然保证),具体早多少无所谓——能用不等式解决的不做强一致对齐。

**Q3:snapshot_start_position 是怎么获取的?**

后端在任务提交前直连源库读当前位点(mysql SHOW MASTER STATUS / pg pg_current_wal_lsn / oracle CURRENT_SCN),持久化到 cdc_st_task(重放复用恒定),随作业配置下发采集端;采集端快照行统一编码 S=f(起点位点)并缓存全批同号。未实现源 fail-fast。详见 6.2。

**Q4:快照写入之前不是还要先查一次库吗?**

那是旧版三步式(probe 探存在 → 条件 UPDATE → INSERT),已因竞态窗口废除:probe 与写入之间不原子,并发删除导致 UPDATE 0 行匹配静默漏写。现行 N4 模板是无 probe 的双条件 INSERT...ODKU——「行存在与否」由 MySQL ODKU 语义天然分支,插入与条件更新原子完成,并发删除 → INSERT 重插不丢行。详见 7.1。

**Q5:共享写线程是谁启动的?**

SynclinkComponents 构造函数末尾的 `batchWriteService.init()`——第一个分区任务装载触发 Factory.init → 组装组件时启动,每工厂一次(writeThreads=4,线程名 dcp-batch-writer,daemon),不是每分区一次。详见 4.3。

**Q6:同一物理表被多个写线程并发写,安全吗?**

安全。4 个写线程各自局部攒桶,同物理表的 op 可能被不同线程并发 flush;但正确性由单条 SQL 内、行锁下的原子裁判保证(ODKU 的 IF 判定原子执行,小号后落盘也覆盖不了大号)。「同表串行写」是旧设计的吞吐牺牲,已被原子 SQL 兜底取代。

**Q7:消费者端怎么判断快照阶段和增量阶段?**

消费者不判断阶段,只认消息上的 snapshot 标志。判定发生在采集端 CdcSeqTransform:补丁透传的 `__snapshot` 列 = true,或位点主段为空(实测快照行 sourceOffset="mysql::0:",file=""、pos=0)→ 快照行,打标写入 Kafka;消费端 `Boolean.TRUE.equals(rec.getSnapshot())` 分流到批/流路径。详见 6.3。
