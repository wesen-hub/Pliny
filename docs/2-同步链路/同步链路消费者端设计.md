# 同步链路消费者端设计(SeaTunnel → Kafka → TiDB)

> 状态:开发前设计文档。适用形态:PB 级流量下的 CDC 同步链路写库环节。

## 一、定位与链路

数据同步链路:`源库 → SeaTunnel CDC 采集 → Kafka → 消费者 → TiDB 目标库`。本设计覆盖消费者端(Kafka 之后):从 Kafka 拉取变更数据、解析与路由、写入 TiDB 分片表、提交消费位点。正确性基石是**目标端幂等**(单条 SQL 同时承载新旧裁判与字段级部分更新),它使得整条链路可以用"至少一次投递 + 重放幂等吸收"的语义运行,并发、重试、故障恢复都以此为底座。

## 二、消费者与 topic/分区的对应关系

**一个消费者(线程)监听多少 topic?**

1. **逻辑表与 topic 一一对应**:一张逻辑表一个 Kafka topic;一份消费者任务只监听一个 topic(不做多 topic 混合消费,简化路由与隔离);
2. **一组一 topic**:每个 topic 属于独立的消费组,消费组之间互不影响(位点、故障、扩容各自独立);
3. **组内分工**:一个消费组内可部署多个消费者实例、多个消费线程,**每个线程负责该 topic 的若干分区**;同一分区在同一时刻只属于组内一个线程(由 Kafka 保证);
4. **线程与分区**:推荐形态为**每分区一线程**——一个线程串行处理一个分区,分区内顺序天然保持,分区间并行。线程数 = 该 topic 的分区数,实例数 ≤ 分区数(超出空转);
5. **一个实例承载多份任务**:一台消费者实例可同时运行多个逻辑表的消费线程,按吞吐需求组合分配;
6. **新逻辑表动态接入**:新表上线时动态注册消费监听,不需要重启实例、不需要改配置。

## 三、完整流程:拉取 → 处理 → 写库 → 提交 offset

### 阶段一:拉取

- 消费者线程批量拉取(每次一批,数百条),拉取动作由线程串行执行;
- 拉取配置要点:关闭自动提交(提交由"已写游标"控制,见阶段四);单次拉取条数调大(数百到上千),换取批量处理效率;
- 一个 topic 一个消费组,组内分区由 Kafka 自动分配;实例增减、故障转移由消费组的再平衡机制自动完成,平台不做额外调度。

### 阶段二:处理(解析、路由、分流)

对拉到的每一批、每一条消息,依次:

1. **解包**:兼容两种消息格式——采集端信封格式(路由信息 + 内层数据 JSON)与裸数据 JSON,自动识别;
2. **写者身份判定**:每条消息携带"写者身份"(任务、数据源、库、表)。身份完整 → 使用**该写者独立的序号列**做裁判;身份缺失(旧链路)→ 判定该逻辑表是否单源,单源才允许用整行序号裁判;
3. **主键变更检测**:消息携带变更前主键与变更后主键;两者不同 → 拆成两条操作:按旧主键删除 + 按新主键写入(删除时值列替换为旧主键值,避免删错行);
4. **路由**:对业务主键做哈希(固定算法、固定种子,跨环境一致):
   - 桶号 = hash(主键) % 桶数(与 Kafka 分区键一致,保证同主键同分区、同分区顺序消费);
   - 物理表号 = hash(主键) % 分片表数 → 定位目标物理表;
   - 桶数、表数、种子一经上线不可变更(变更 = 同主键换桶换表 = 数据分裂);
5. **主键列回填**:源端字段映射可能不含主键列(只映射了部分列),而目标端定位行必须用主键 → 从消息的主键字段回填(单主键直填,复合主键按分隔符拆分);
6. **快照/增量分流**:消息携带快照标志。快照行 → 走快照写入流程(批路径);增量行 → 走增量写入流程(流路径);
7. **投递**:处理结果投入**有界内存队列**,队列满则等待(背压传导回拉取,拉取停顿,上游 Kafka 自然积压);处理异常时逐条兜底处理,单条失败写入死信,不阻塞整批。

### 阶段三:写库

- **写线程与消费线程解耦**:消费线程只做"拉取+处理+投递",写库由独立的写线程池完成;两者之间是上述有界队列;
- **攒批**:写线程把投递进来的操作按"物理表 + 快照/增量"分桶攒批;**够量(数百条)或够时(百毫秒级)**触发一次写入——低流量靠时间触发保证及时性,高流量靠条数触发保证吞吐;
- **增量写入(流路径)**:同一物理表、同一写者的操作合并成**一条批量写入 SQL**:
  - 多组数据一次插入,冲突时执行更新(upsert 语义);
  - **新旧裁判**:比较条件只针对本写者自己的序号列——序号前进才接受新值、相同则丢弃(重放幂等)、倒退则拒绝(防乱序);
  - **字段级部分更新**:只更新本批携带的列,不触碰其他列(多源合流互不误伤);不同写者各自成组、各自比较各自序号;
  - 删除操作逐条执行(条件各不相同,不能合并);
  - 一个攒批一个事务,不跨表;
- **快照写入(批路径)**:三步式:
  - ① 轻量探测:批量查询哪些主键已存在;
  - ② 对已存在行:带条件更新(仅当快照序号大于存量序号**且**值有实际变化才写——避免批重跑重复写、避免覆盖更新的流数据);
  - ③ 对不存在行:批量插入(带快照序号);
- **失败处理**:整批写入失败 → 整批进死信 + 告警,**不原地重试**(目标库自身有重试机制,应用层重试会放大峰值);失败不影响位点推进策略(位点仍按"已写游标"推进,未写部分后续重放由幂等吸收)。

### 阶段四:提交 offset

提交语义核心:**提交的是"写库进度",不是"拉取进度",绝不超前**。

1. **已写游标**:写线程每成功落库一批,就把对应分区"已写到的位置"更新到游标;
2. **追平等待**:消费线程在拉取一批后,等待写线程把这一批全部写完(有界等待,秒级),然后执行提交;
3. **提交值 = 已写游标 + 1**(下一条要读的位置):即使出现"拉取了很多但写库没跟上",提交也只会停在写库进度之后——**可以滞后(多写由幂等吸收),绝不超前(超前即漏数据)**;
4. **追平超时**:等待超时则只提交已写完的部分,未写完的尾部由"空闲补交"机制兜底(没有新消息时也周期检查、补交尾部,避免"最后一批永远不提交"的假延迟);
5. **提交失败**:再平衡窗口期的提交失败属正常,下一轮重试;崩溃后从未提交位置重放,由目标端幂等吸收。

## 四、顺序性保障

```
分区内顺序(每分区一线程串行拉取处理)
  → 队列入队顺序(单队列先进先出)
  → 同表写入顺序(同一物理表由一个写线程串行落库)
  → 跨分区/跨表乱序 → 目标端序号裁判兜底(号大者赢)
```

写入端可以为了吞吐放弃全局顺序,正确性交给目标端裁判——这就是目标端 upsert 语义存在的意义。

## 五、为什么用消费组自治而不是租约下发

判断标准一句话:**"重复消费的代价"决定分布式控制的强度。**

1. **重读无害**:重复拉取同一批数据,重写一遍,目标端幂等吸收(同号丢弃、号大者赢)——没有副作用;
2. **状态可重建**:唯一进度状态是已写游标,持久化在 Kafka 侧;实例重启/再平衡后从提交位点继续,未提交部分重放、幂等吸收;
3. **不依赖精确起点**:快照行自带标志走快照流程,增量行靠序号裁判,不依赖"精确到哪一条"的起点。

三条全部成立 → 分区分配、故障转移全部交给 Kafka 消费组,平台侧只需要"无状态 + 幂等兜底 + 背压"三件套,不需要租约、防双、精确起点下发。

**边界**:目标端不是幂等写(不支持 upsert 的库、通知类副作用)时,以上前提不成立,必须换用租约 + 防双 + 精确起点的重控制模式。

## 六、容量规划(PB 级)

- 日增 10TB、平均行 1KB → 约 10^10 行/天 ≈ 11.5 万行/秒均值,峰值 3~5 倍 ≈ 35~60 万行/秒;
- 单消费线程吞吐(拉取+处理)5~10 万/秒 → 峰值需要 6~12 个消费线程;
- 单写线程吞吐(批量落库)1~2 万行/秒 → 峰值需要 30~60 个写线程(按 40 规划);
- 分片表数 = 峰值写入速率 / 单表单区域写入能力,一次规划到位(数百张),哈希路由契约不可改;
- 实例数:消费与写库同机部署,3~6 台实例覆盖峰值。

**瓶颈在写库端不在消费端**,设计重心是写库并发的每一分都用到刀刃上。

## 七、关键参数与约束汇总

| 项 | 取值/规则 | 说明 |
|---|---|---|
| 单次拉取条数 | 数百~上千 | 批量处理效率 |
| 队列容量 | 数千/逻辑表 | 有界,满则背压 |
| 攒批触发 | 数百条 或 百毫秒 | 双条件,兼顾吞吐与延迟 |
| 写线程数 | 按目标库带宽/单连接带宽 | 不按 CPU |
| 同表并发写 | 禁止(一表一线程) | 消除热点锁竞争 |
| 事务粒度 | 一表一批一事务 | 不跨表 |
| 提交语义 | 已写游标 + 1 | 滞后不超前 |
| 桶数/表数/哈希种子 | 上线即冻结 | 变更 = 数据分裂 |

## 八、异常处理路径汇总

| 异常 | 处理 |
|---|---|
| 消息解析失败 | 逐条兜底,仍失败进死信 |
| 队列投递失败 | 逐条直写兜底,失败进死信 |
| 整批写库失败 | 整批进死信 + 告警,不原地重试 |
| 追平等待超时 | 先提交已写部分,尾部空闲补交 |
| 提交失败(再平衡窗口) | 告警,下轮重试 |
| 实例崩溃/再平衡 | 从提交位点重放,幂等吸收 |
| 主键变更 | 拆删除 + 写入成对操作 |
| 序号倒退/重放 | 目标端裁判拒绝/丢弃,零写入 |
