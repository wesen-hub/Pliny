## 1. 链路全景与职责划分

### 1.1 五段式流水线

```
源库 → SeaTunnel CDC(补丁透传位点+快照标志)
     → CdcSeqTransform(列裁剪 + 位点发号 + 身份注入 + 桶路由)
     → Kafka(dcp.* topic,按 __bucket 分区保序)
     → SyncConsumer(解析 + 路由 + 攒批投递)
     → AtomicUpsertDao(写者列裁判落库)
     → TiDB 目标分表
```

### 1.2 平台两条链路(定论)

| 链路 | 位置 | 职责 |
|---|---|---|
| 同步链路 | 平台栈 kafka:9092 | 源库 → SeaTunnel CDC → dcp.* 主题 → SyncConsumer(sync ns) → TiDB 目标库分表 |
| 消费底座 V2 | 出口栈 outlet-kafka | TiDB 目标库 → TiCDC changefeed(chg-target-db) → 出口栈 → 下游任务(打标 tag/湖 lake/订阅 sub/入站 ingest) |

### 1.3 消费端并发模型

每分区一线程、assign 单分区、MANUAL ACK、提交位置 = 已写游标 + 1(滞后可接受,超前致命);崩溃重放由写者列幂等吸收。

## 2. 位点体系

### 2.1 位点即序号:六源编码公式

| 源 | 编码 |
|---|---|
| MySQL | `fileNo << 44 \| pos << 12 \| row`(file 为 binlog 文件名如 `binlog.000006`,取 '.' 末段数字为 fileNo) |
| PostgreSQL | `(logid << 32 \| offset) << 10` |
| Oracle | `commit_scn << 12 \| lcr_position` |
| SQLServer | `lsnNum * 10^6 + serial` |
| MongoDB | `ts_ms * 10^6 + ord` |
| TiDB | `(physical - TSO_EPOCH_MS) << 18 \| logical`(纪元基线 2020-01-01,满位源裁剪平移) |

- **位点粒度 = 行级**:PositionMetadataConverter 从 Debezium sourceOffset 提取(`type:k1:v1...`);MySQL 为 `file:pos:row`,row 为 event 内行号;file 实测形态为 binlog 文件名(`binlog.000006`),编码时取 '.' 末段数字为 fileNo(纯数字直取);快照行共享同一位点 → 统一编码为快照级号 S = f(snapshot_start_position)
- **MySQL binlog 实例级单流**:全实例所有库表变更写入同一 binlog 流,顺序 = 事务提交序(非墙钟序);单实例跨表 seq 可比,跨实例不可比(不可比正是写者列独立裁判的原因之一)

### 2.2 严格位点一态(唯一形态)

- 增量行必须有补丁透传位点,**缺位点 fail-fast**(防新旧号混发)
- 快照行统一为快照级号 S = f(snapshot_start_position),全批同号(重放恒定)
- S 的获取(**方案 A 定案, 2026-10-05 实测定案**):混合策略 B 优先 A 兜底,实测裁决结果:
  - 实测形态:MySQL 快照行 sourceOffset = `{transaction_id=null, ts_sec=…, file="", pos=0}`、**无 snapshot 键** → 补丁透传位点列为 `"mysql::0:"` 空形态、__snapshot 列恒 false → **方案 B 前提实质不成立**(无法从行内取起点编码 S)
  - 方案 A(已落地):后端 CurrentPositionReader(按源类型分派:mysql=SHOW MASTER STATUS/pg=pg_current_wal_lsn()/oracle=SELECT CURRENT_SCN)在任务提交前读源库当前位点下发 snapshot_start_position,并**持久化到 cdc_st_task 保证重放时 S 恒定**;未实现源 fail-fast
  - 快照行判定启发式:__snapshot 列="true"(未来 Debezium 带键)或位点主段为空(空形态,实测 MySQL) → 快照行;其余走位点编码
  - 端到端实证(2026-10-05):S = f("mysql:binlog.000006:157:0") = 105553116909568,快照批 22 行全同号;增量行 seq 更大,衔接不等式 S < seq 成立
- 快照与增量衔接:initial 模式 binlog 从快照起点回放,重叠窗口增量事件(位点号 > S)覆盖快照行,裁判自动收敛
- 纯号段/兼容三态、seq_counter 预领号段 = **旧残留,清理**

### 2.3 六条不变式

1. 重放恒定:seq = 位点确定性函数,同消息同号
2. 单源单调:每写者列单调递增
3. 下游零改动:消费底座读目标表,无感知
4. per-source 序列:写者列独立,跨源不可比
5. fail-fast:位点缺失/类型不符/裁剪违规 → 任务失败
6. 体系重置必检测:guardReset 告警(新 seq 回退超阈值 → 告警,下游裁判将拒绝新数据,人工裁决)

### 2.4 Kafka 消息实测形态(2026-10-05 端到端实测抓包)

链路:MySQL binlog → CDC connector(补丁透传三列)→ CdcSeqTransform → Kafka sink(format=json, partition_key_fields=[__bucket], topic=dcp.{logicalTable}, AT_LEAST_ONCE)。

**Kafka 记录三要素(console-consumer print.key=true 实测)**:
- key = `{"__bucket":2160}`(partition_key_fields 抽取子行按同 json format 序列化的字节; 默认 hash partitioner 按 key 分配 → 同 bucket 同分区, 同 businessKey 有序)
- value = `{"__bucket":2160,"__payload":"<CdcRecord JSON 字符串>"}`(JsonSerializationSchema 整行序列化为对象; __payload 是转义字符串, 消费端 asText() 后再反序列化)
- 无 headers; 无 watermark(消费端 isWatermark 兼容 TiCDC 链路, 本链路不产)

**__payload 内 CdcRecord 字段序(实测)**:
logicalTable, taskId, sourceDb, sourceTable, datasourceId, businessKey, (beforeKey), keyColumns, rowKind, seq, snapshot, fields。
- fields = field_mapping 白名单裁剪后(实测源表 8 列只发 6 列: created_at/discount 被裁), 值全部字符串化, null → JSON null
- seq: mysql = (binlog文件号<<44)|(pos<<12)|row; 快照行 = S = f(snapshot_start_position) 全批同号
- beforeKey: 仅 UPDATE/DELETE 带(=businessKey; INSERT 无); 若 ≠ businessKey 则 transform 内告警+抛异常, 不进 Kafka
- taskId/datasourceId 为字符串

**实测样例(原样)**:
快照行: `{"__bucket":2160,"__payload":"{\"logicalTable\":\"t_order_probe\",\"taskId\":\"56\",...,\"businessKey\":\"4\",\"keyColumns\":[\"id\"],\"rowKind\":\"INSERT\",\"seq\":105553116909568,\"snapshot\":true,\"fields\":{\"id\":\"4\",...,\"total_amount\":null}}"}`
增量 INSERT: seq=105553120006145=(6<<44)|(913<<12)|1 与 binlog sourceOffset {file=binlog.000006,pos=913,row=1} 完全吻合; snapshot=false。

**实测发现(需拍板, 缺陷 7 候选)**:一次源 UPDATE 产生**两条同 seq 消息**——Debezium UPDATE_BEFORE(旧值行)+ UPDATE(新值行)都按 UPDATE 发出, seq 完全相同(同 source record 位点透传相同)。设计注释曾假设 "UPDATE_BEFORE 序号小于 AFTER 天然收敛", 实测不成立。消费端写者列裁判 `IF(writer_col < VALUES(writer_col))` 同号拒写 → 新值行被拒 → 目标表停留旧值(变更丢失风险)。候选修法: transform 丢弃 UPDATE_BEFORE 行, 或消费端同号允许覆盖(号不推进)。

## 3. 写者列裁判机制(同步链路唯一裁判)

### 3.1 命名规则

```
_s{taskId}_d{datasourceId}_{sourceDb}.{sourceTable}
```

- 清洗:非 `[A-Za-z0-9_]` 字符全部替换为 `_`
- 防超长:总长 > 63 → 前 46 字符 + `_` + md5 摘要(16 位),共 63 字符
- 示例:`task_id=1, datasource_id=7, db=source_db, table=t_order` → `_s1_d7_source_db_t_order`
- 语义:一列 = 一个写者(任务实例 × 数据源 × 库 × 表)的独立 seq 序列;同(逻辑,源)多任务实例因 taskId 不同互不压制
- ID 唯一性(2026-10-04 拍板):任务 ID 与数据源 ID 全局唯一、永不复用(历史 ID 含已删除永久保留),防止新旧代写者列混比
- 列名查重(2026-10-04 拍板):写者列名注册时查重,范围含历史写者列与目标表现有业务列,冲突 fail-fast 拒绝注册

### 3.2 生命周期

- 身份注入:CdcSeqTransform 封装时恒注入 taskId/datasourceId/sourceDb/sourceTable(CdcRecord 恒带身份)
- 建列:首条消息触发幂等 `ALTER ADD`(已存在跳过),目标表恒有写者列

### 3.3 裁判 SQL 三式

**INSERT/UPDATE(ODKU)**:
```sql
业务字段 col = IF(writer_col < VALUES(writer_col), VALUES(col), col)   -- 裁判
writer_col   = GREATEST(writer_col, VALUES(writer_col))                -- 写者列单调递增
seq          = GREATEST(seq, VALUES(seq))                              -- 观测列,不参与裁判
```
**DELETE**:
```sql
DELETE FROM t WHERE key = ? AND writer_col < ?   -- 本写者的删除不压制其他写者的新值
```

### 3.4 裁判语义

| 语义 | 说明 |
|---|---|
| 单写者防重放/乱序 | 同一写者旧 seq 消息重放:writer_col < VALUES → 值被拒,幂等吸收 |
| 跨写者互不干扰 | 各比各的写者列;写者 A 更新不触碰写者 B 的字段 |
| 跨写者同字段 = LWW | 同一 modelField 多写者(拍板放行场景):同目标行时,写者列新者胜 |
| DELETE 不跨写者压制 | 写者 A 的删除只在 A 的写者列旧于消息时生效 |
| 行级 seq 仅观测 | GREATEST 保底(审计/排查用),裁判唯一依据是写者列 |
| 主键区分行 | 同 modelField 多来源绝大多数写不同行(主键不同),天然无冲突 |

### 3.5 成立前提

消息 fields = 声明映射的 modelField 集合(列裁剪,强校验保障)——保证"每写者只携带自己有权写的列"。前提由第 4 章的结构性保证成立,而非依赖配置别写错。

### 3.6 快照/批量路径

- 快照行:`snapshot=true` → 批路径三步式模板(值变行重建、值同行静默),全批同号 S
- 快照与增量各走各的模板,同一机制下自动收敛

### 3.7 幂等机制三阶段(防旧覆盖新定论,2026-10-04)

**总览:两个闸门 + 一个不等式**——快照批闸门(主键+值同不写,不依赖号)、增量批闸门(写者列裁判,号大才能覆盖)、衔接不等式(S < 一切流号)。

**阶段一:快照阶段(全量)**

- 数据形态:全表按主键分块 SELECT,每行带 snapshot=true、seq=S 全批恒定
- 写入模板三步式:探主键存在 → 已存在走条件 UPDATE(仅值有实际变化才写)→ 不存在 INSERT
- 幂等靠主键+值比较,不靠号:快照行值永远是读取时刻的源库最新值,此时目标表不可能存在比它更新的同 key 数据(增量还在 Debezium 内存缓存)
- 重启边界:Debezium 断点粒度是表级(不是行级)——已完成快照的表跳过,正在快照的表整表重扫;重放行值相同 → 值同不写吸收;重扫间隙源库又变 → 读到更新值 → 值变则写(正确)
- 条件 UPDATE 值比较必须 NULL 安全(`<=>` 取反语义,严禁 `<>`),否则 NULL 变更被误判无变化永久漏写

**阶段二:快照 → 增量衔接**

- Debezium 快照完成 → 内存缓存的增量事件按序回放(这些事件位点 ≥ 快照起点)
- 号序:S < 所有增量号;衔接"不紧密"(号有间隙)无害,seq 只要求大小关系不要求连续
- 回放事件走增量批模板:同 key 快照行(S)先落,增量行(号>S)后到 → 裁判通过 → 增量覆盖快照,方向不可逆
- 重启:checkpoint 含快照完成状态 → 恢复后直接续读增量,快照不重扫;checkpoint 丢失/无 savepoint → 强制 initial 重扫(新 jobId):新 S > 存量号 → 值变则更新、值同不写,依然正确

**阶段三:增量阶段(纯流)**

- 数据形态:binlog/redo 事件,seq = f(位点),源端位点单调 → 号单调
- 写入模板:ODKU + 写者列裁判;DELETE 闸门 WHERE key AND writer_col < ?
- 四种攻击场景全部拦截:消费端崩溃 offset 未提交重放(同号被裁判相等拒绝)、多实例并发写同 key(小号后落盘被拒)、位点体系重置(guardReset 告警人工裁决)、旧 DELETE 重放/迟到(writer 闸门拒绝)

**全局不变量**:同一写者列内 seq 严格单调;流号 > S;所有写操作携带号,裁判只允许号更大的数据生效;快照批不参与号竞争,与流数据的关系由不等式单向衔接。

## 4. 列裁剪(采集端字段映射)

### 4.1 目标不变式

1. 输出字段集恒等:每条消息 fields 键集合 = 任务 field_mapping 声明的 modelField 集合(去重),不多不少
2. 零泄漏:未声明映射的源列,任何情况下不得进入消息 fields
3. 前提恒成立:写者列裁判的字段级收敛前提由数据面结构保证
4. 空映射不存在:映射非空是任务存在的必要条件(注册即校验,启动再验)

### 4.2 白名单裁剪规则

裁剪 = 逐条声明求值,声明外全部丢弃:

| kind | 输入域 | 输出 |
|---|---|---|
| field-map | 源行字段全集(值已字符串化) | `modelField ← srcFields[srcField]` |
| compute | 源行字段全集 + 已算出的前置 modelField(拓扑序) | Aviator 表达式求值结果 |
| uuid | 无 | 生成值(v4/v7/snowflake) |
| system | seq / 时钟 | seq 值或当前时间戳 |

关键语义:

- **裁剪裁的是输出,不是计算输入域**(D1 拍板):compute 的 env = 源行全集 + 前置 modelField;例 `amount = price*qty`,price/qty 不被单独映射但被引用,合法——"零泄漏"指不落地、不出消息,不等于不可被计算引用
- 加工链(steps:null-fill/case/truncate/mask/json-parse/date/enum/split)**只改值不改集合**
- 系统保留列 seq 不进业务字段(由 CdcRecord 顶层携带,目标表独立列)
- **DELETE 事件走同一映射**(D3 拍板):完整字段集 + null 值(key 列直连可取到值,其余 modelField 为 null)——字段集对全部 rowKind 恒等,下游模板统一

### 4.3 modelField 重复声明边界(D2 定论)

| 场景 | 处置 |
|---|---|
| 同一任务、同一源表多列 → 同一 modelField | **拒绝注册**——同源行必撞,后者覆盖 = 前一条映射永远无效的死配置;真想表达"优先 c1 否则 c2"应改用 compute 显式写 |
| 同一任务、完全重复的映射行 | **拒绝注册** |
| 同一任务、跨源表 → 同一 modelField | **放行**(业务允许)——执行上每源表一个 job、映射按源表拆分,单 job 内不会撞;目标侧主键区分行,同主键撞行 LWW |
| 跨任务、同一源表不同源列 → 同一 modelField | **放行**——各写者各写各的,可能覆盖,不做校验拒绝(LWW 机制语义) |
| 跨任务、同一源表同一源列 → 同一 modelField | **拒绝**(uk_flow 源侧唯一:同一源列全局一条采集流) |

### 4.4 保留列冲突(D5 定论)

- modelField 禁止撞:`seq`、CdcRecord 顶层字段(logicalTable/taskId/sourceDb/sourceTable/datasourceId/businessKey/keyColumns/rowKind/snapshot/positionMode/fields)
- modelField 禁止 `_` 前缀(保留给 `_pk_id`、写者列 `_s*`)
- 冲突 = 注册拒绝

### 4.5 映射演进语义(D4 定论)

- 映射变更 = 重启任务生效
- 删除的 modelField 不再出流,**目标表存量列值保留不清理**
- 新增的 modelField 从重启后的事件开始写

### 4.6 源表列变化语义

| 变化 | 语义 |
|---|---|
| 源表加列(未声明映射) | 直接裁剪,对同步零影响;想让新列进目标表 = 编辑映射声明 + 重启任务 |
| 源表减列(运行中) | 对应 modelField 按 null 值继续更新(目标表该字段被冲 null 是预期语义) |
| 源表减列(启动/重启时检测到) | **不拦截**:写告警记录到 sync_alert + 继续按 null 更新。理由:在线减列后任务正常跑、重启后任务起不来是不可接受的矛盾;配置手误与源表演化统一按"告警 + null 更新"处置 |

## 5. 同步任务配置约束

### 5.1 铁律级约束(上线后不可变,违反 = 数据分裂)

| 约束 | 理由 |
|---|---|
| bucket_count(固定桶 4096)不可改 | 同 key 换桶 = 分区重排 |
| table_count(分表数)不可改 | 同 key 换表 = 实体分裂 |
| 路由种子(0x9747b28c)不可改 | hash 结果跨版本一致性 |
| business_key 构成不可变 | 键构成变 = 换桶换表 |
| key_columns(唯一键列)不可变 | 幂等收敛依据 |

### 5.2 注册时强校验(控制面,UI 与直建路径统一)

| # | 校验 | 失败动作 |
|---|---|---|
| 1 | field_mapping 非空 | 拒绝注册 |
| 2 | businessKeyFields / keyColumns 非空 | 拒绝注册 |
| 3 | 任务内同源表多列 → 同 modelField(D2-a) | 拒绝注册 |
| 4 | 完全重复的映射行(D2-b) | 拒绝注册 |
| 5 | modelField 撞保留名(seq/CdcRecord 顶层字段/`_` 前缀) | 拒绝注册 |
| 6 | kind=field-map 时 srcField 非空;kind=compute 时表达式可解析(Aviator 编译通过) | 拒绝注册 |
| 7 | 字段流源侧唯一:同一(数据源,库,源表,源列)全局一条采集流(uk_flow) | 拒绝注册 |
| 8 | 同 modelField 多写者(跨源表/跨任务) | 信息性提示,零阻断 |
| 9 | 直建路径(API/脚本)同样执行以上校验 | 拒绝注册 |
| 10 | 任务 ID/数据源 ID 不得与历史 ID(含已删除)重复(永不复用) | 拒绝注册 |
| 11 | 写者列名查重:与历史写者列、目标表现有业务列不冲突(md5 16 位) | 拒绝注册 |
| 12 | 源表列名不得含平台保留前缀 `__src_`(防与补丁透传列重名) | 拒绝注册 |

### 5.3 启动时分级校验(数据面,防御绕过注册)(D6 定论)

| 级别 | 校验项 | 动作 |
|---|---|---|
| 配置错误(fail-fast) | field_mapping 非空、保留列冲突、任务内同源表重复 modelField、compute 表达式不可解析 | 任务起不来 |
| 源表演化(告警) | 映射引用的 srcField 不存在于启动时探测的源列集(MySQL 表发现/PG/Oracle probeSchema) | sync_alert 告警 + 继续按 null 更新,不拦截 |

### 5.4 模式与位点约束

- sync_mode:full-cdc / full-once(+snapshot-only) / incremental / scheduled-batch
- start_mode:earliest / latest / timestamp / specific-offsets(MySQL file:pos)
- 启停纪律:无 savepoint 且 start_mode=latest → 强制降级 initial(防静默丢历史);restore 失败(无可用 checkpoint)→ 换新 jobId 全量重采;优雅停止 = checkpoint 落盘,重启同 jobId 续采
- server-id 每 job 唯一(5400 + taskId*10,防同实例互踢);PG slot 每 job 独立(`dcp_slot_{taskId}`)

## 6. 异常处置策略

### 6.1 源表减列

- 运行中:按 null 值继续更新(见 4.6)
- 重启时:sync_alert 告警(类型=缺列)+ 继续 null 更新,不拦截

### 6.2 主键列值修改(G1 定论)

**策略**:检测到源表主键值被修改 → 任务暂停 + 告警,要求用户重新建立任务或映射关系;不做自动拆解 DELETE+INSERT。

**第一步:检测(方案 A,before 主键透传补丁)**

- 同步链路 CDC 事件无 before image(SeaTunnel 2.3.12 限制),UPDATE 事件只有新主键,采集端当前无法区分普通 UPDATE 与主键修改 UPDATE
- 方案 A:与位点透传补丁同工艺(binlog 本身含有 before 行),给 CDC connector 注入"before 主键列"透传 → CdcSeqTransform 封装时把 before 主键拼成 beforeKey → 与 businessKey 比对,不等即主键修改。检测点在采集端,最准确
- 检测失效处理(2026-10-04 定论):beforeKey 解析失败必须 fail-fast + 写 sync_alert 告警,严禁吞异常静默返回 null;Mongo 链 before 行恒 null 属已知局限,走告警通道提示该源主键修改风险

**第二步:检测到之后的动作链(双层拦截,目标表零污染)**

| 层 | 动作 |
|---|---|
| 采集端 | 告警写 sync_alert(类型=主键修改)+ 任务停止(checkpoint 保留);异常标记为"主键修改",watchdog 巡检**不自动 restore**(防重启后同一条主键修改消息再次触发,死循环) |
| 消费端 | 同构兜底:消息若已流出 Kafka,发现 beforeKey ≠ businessKey → 落死信、不写目标表(不自动处理,人工裁决) |

**第三步:人工介入**

用户看到告警 → 确认业务事实 → 手动修复目标表(删旧行/补新行)→ 重建任务或改映射(若主键语义变了)→ 从 checkpoint 续采。期间该逻辑表暂停,数据不回退不丢;主键修改消息留在死信天然可追溯,恢复时从下一条续采。

### 6.3 写库失败(G2 定论)

**策略**:攒批写入失败 → 逐条重试隔离,失败单条(不止 data too long,含一切写失败原因)全部落死信,由人工处理,记录好失败原因;**不阻塞后续数据流更新**。

- 攒批中一条失败,其余正常写;失败那条落死信(原因分类:value_too_long / 其他 DB 错误详情)
- 复用逐条兜底路径,把可跳过异常识别为单条失败,而非整批阻塞

## 8. 目标表结构

- DDL 形态:业务主键列 `VARCHAR(255) NOT NULL`、业务字段列 `VARCHAR(255) NULL`、`seq BIGINT NOT NULL DEFAULT 0`(观测列)、`UNIQUE KEY uk_biz`(业务键唯一)、写者列(首条消息幂等 ALTER ADD)

## 12. 幂等机制边界与异常清单(2026-10-04 定论)

裁判闸门保守:失败方向偏向漏写 + 告警,不会静默错值。

### 12.1 旧覆盖新边界(B 类)

| # | 边界 | 结论 |
|---|---|---|
| B1 | 多源合流 LWW:不同写者列任务旧值晚到覆盖新值 | **拍板接受,不校验** |
| B2 | 写者列名碰撞(ID 复用/清洗碰撞/md5 截断) | 已闭环:ID 永不复用 + md5(16) + 注册查重 fail-fast |
| B3 | 位点编码混发(同写者列混入异源号) | 正常配置不出现(写者列粒度=任务×数据源×表,源类型生命周期固定);guardMix 告警守卫防 bug/配置错误 |
| B4 | 外部直写目标表(人工改库) | 治理域,链路不防 |
| B5 | 主键修改检测失效(before 行缺失/解析失败) | 已闭环:解析失败 fail-fast + 告警;Mongo before 恒 null 走告警提示 |

### 12.2 漏写边界(L 类)
