# 数据平台核心子系统设计总结

平台定位:多源异构数据一站式采集、同步、加工、治理、交付平台。数据在平台内走**两条物理隔离的链路**:同步链路(平台栈)把六类源库的变更实时搬进 TiDB 目标库;消费底座 V2(出口栈)再把目标库的变更交给下游业务。围绕两条链路,平台沉淀出四个核心子系统——**数据同步链路、数据消费底座、数据打标引擎、数据资产体系**,外加一个统一调度框架内核承载消费侧的通用调度,工程形态为微服务(6 个控制面 + 1 个执行体池 + 3 个独立作业)。

协作关系一句话:**同步链路把数据搬进来,消费底座把它交给业务,打标引擎产生标签,资产体系让这一切可视可管**。以下按统一结构(定位与核心问题 → 整体架构 → 关键机制 → 验证 → 收口)逐一总结。

---

## 一、数据同步链路:多源异构库的统一 CDC

**定位与核心问题。** 平台里有 MySQL、PostgreSQL、SQLServer、Oracle、MongoDB、TiDB 六类异构源库,变更数据都要实时汇聚到统一的目标库,而且要支持**多源合流**——多个源库的订单变更落到同一张物理表。过去每类源、每个任务各自实现一套采集配置、发号、幂等写入与重试,重复造轮子。V3 链路把"采集、发号、汇入"三件通用难题一次性收编进链路内核,任务侧只需配置:选哪个源、同步哪些表、落到哪张目标表。

**整体架构:五段式流水线。** 源库变更经 **SeaTunnel CDC** 采集(按源做方言适配,MySQL 独立 server-id、PG 独立复制槽、SQLServer 原生 CDC、Oracle LogMiner 含 CDB/PDB、Mongo 变更流、TiDB 兼容直采;位点由补丁透传)→ **CdcSeqTransform** 采集转换(列裁剪、位点发号、业务键归一、桶路由)→ **Kafka**(每张源表一个 `dcp.*` topic,按桶号分区保序)→ **SyncConsumer**(每分区一线程、assign 单分区、攒批投递)→ **AtomicUpsertDao**(写者列裁判)→ TiDB 目标分表。五段各司其职,边界之外没有第三种写入路径。

**关键设计之一:位点即序号,发号器废弃。** 早期方案用独立发号器生成全局流水号,后来废弃——全局序号跨源没有业务语义,会误拒合法更新,还会让快源饿死慢源。最终定论:**序号就是源库位点的确定性编码**(位点即序号),每源一套公式:MySQL 为 binlog 文件名号+位点+行号、PG 为 LSN、Oracle 为 SCN、SQLServer 为 LSN+serial、MongoDB 为 ts+ord、TiDB 为 TSO。位点粒度到行级,**重放恒定、单源单调**;快照行统一编码为快照级号 S = f(snapshot_start_position),由后端在任务提交前读源库当前位点下发并持久化,重放恒同号;缺位点 fail-fast,绝不新旧号混发。

**关键设计之二:写者列裁判。** 序号只用于机制用途(路由、重放检测、写序标记),**不裁决业务先后**。写入裁判以写者列为单位:每个物理列记住最后写它的采集流序号,更新逐列判断、序号更大者赢——多源合流时不同来源各自负责各自的列,互不踩踏;单源同步退化为整行裁判。删除同样用序号条件防护,重放不会误删。前提是一条窄行纪律:每个源只负责自己的列域,线上变更永远走链路。

**关键设计之三:攒批汇聚与已写游标。** 消费到的操作先进有界队列,队列满即背压减速;写线程按物理表分桶,凑够条数或等够时延触发一次落库,按写者分组拼多值 SQL、单事务提交;只有真正写库成功,消费位点才推进——**位点跟着操作走,而不是跟着消费走**,失败的消息进死信可查可标记重放。整条链路是至少一次投递加幂等写入,目标表业务唯一键兜底,重放不产生错误结果。

**关键设计之四:批流衔接。** 快照阶段与增量阶段可能重叠:快照级号 S 恒小于同源增量号,衔接不等式 S < 增量号恒成立;写入按双 ODKU 模板执行——批阶段已存在的行走条件 UPDATE(批号+seq 裁判),增量阶段走无条件覆盖+seq 裁判——后到的快照行永远不覆盖先到的增量行,批流重叠窗口收敛为精确一次。

**关键设计之五:桶路由与热点迁移。** 记录→桶永远不变(桶号 = hash(业务主键) % 桶数),桶→分区可变:扩容时重算映射并热更新,旧分区存量留在原地消费,新旧分居乱序由 seq 兜底。自定义迁移策略允许把热点桶按指定列表迁往新分区:**切换点 = 元库单条 UPDATE 原子切换**(带审计+消费端热更新),生产端自定义 Partitioner 以 60s TTL 缓存查元库映射、窗口内尾巴消息由消费端在旧分区照常消费完——分区级迁移**无存量搬运**,消息不重投,目标库分表路由不变。

**验证。** 三层工作:语义推演(列重叠、行重叠、行列都重叠三种合流语义逐一分析,明确哪种天然安全、哪种靠纪律、哪种无解);位点实测(快照行位点形态实测定案 S 获取方式,端到端实证衔接不等式成立);端到端演示与冒烟测试(真实多源库与 Kafka 验证采集、转换、合流、写入,含分片订单表多源合流场景)。

**一句话收口**:采集统一六种方言、序号即源库位点、写入攒批且位点跟操作走——多源异构库的变更靠"位点即序号加写者列裁判"安全合流,靠"至少一次加幂等写入"保证不重不乱,靠"桶路由原子切换"随热度迁移分区。

## 二、数据消费底座:统一调度框架承载的增量消费通道

**定位与核心问题。** 平台里有打标、湖同步、订阅交付、事件入站四类数据消费场景,每一类过去都要各自实现位点管理、调度、重试、死信与批流衔接,重复造轮子。消费底座把这些通用难题一次性收编进平台内核,业务侧只需要写一个业务逻辑、再加一份任务配置,就能获得完整的消费能力。

**整体架构:调度内核 + 业务外壳。** 底座由**统一调度框架**(dcp-scheduler,基于 etcd)承载。框架只回答一个问题——"**哪个分区应该在哪个实例的哪个线程上跑**",管三件事:分区归属决策(分配/迁移/再平衡/对账)、线程生命周期托管(起停时机与交接时序)、扩缩容编排(阈值决策、逻辑缩容流程)。业务知识全部外置,通过三个契约提交:**TaskSpec**(任务参数:标识/并发边界/执行契约/业务元数据)、**PartitionExecutor**(执行器:poll → 业务处理 → 提交位点,位点节奏自定)、**ScaleDownHooks**(缩容钩子,业务侧切换生产端路由)。框架内核按三模块组织:任务接入(契约层)、etcd 状态管理(事实源层,租约与持久分层,CAS+epoch 换主可续)、调度机制(决策层,打分分配/判死交接/再平衡/扩缩容,决策纯逻辑、写走 CAS、永不阻塞)。任务按 namespace 隔离(tag/lake/sub/ingest),每个场景一个业务外壳。

**数据面流转。** 目标库 TiDB 经 TiCDC changefeed 输出到出口栈 Kafka,每张表一个 topic,变更位置统一用 TSO 表达。控制面常驻索引器持续消费 Kafka,把提交时间戳到 Kafka offset 的映射按采样策略落成稀疏锚点索引,同时维护每个分区的最高水位。锚点只是加速器,丢了可以重建;没有锚点时退化为按时间粗定位加短扫,定位降级但正确性不变。

**关键设计之一:批流衔接,T0 三规则。** 一个消费任务启动时先跑批阶段:以统一边界时点 T0 为准把历史全量打底(Spark 回刷),同一份业务逻辑以快照模式执行。T0 取值被三条规则锁死:不能早于 changefeed 起点,否则增量段之前的数据没进 Kafka;不能早于 GC 回收点,而且这一条取不到值就直接失败、绝不静默跳过,因为那等于允许读已被回收的版本;不能晚于分区最新水位,否则会凭空跳过数据。批阶段完成后,增量段从"每个分区第一个提交时间戳大于 T0"的位置开始,靠锚点二分加短扫定位,不重不丢。

**关键设计之二:租约与防双消费。** 任务按分区规划成一个个消费单元,控制面给每个单元下发指令,内容包括起点位置、业务逻辑引用、租约和配额。etcd 租约保证每个单元同一时刻只有一个执行者,心跳续租;单元失联或换代时走离线返工流程,从已提交位点续跑,不猜位点。数据库单元分区表以主题、分区、代次为唯一键,两个执行者抢同一个分区时第二个直接违反唯一键——这是防双消费的最终兜底,不依赖分布式锁。

**关键设计之三:fail-closed 契约裁剪。** 计算面消费前要先拉取契约视图,按列投影、行条件、脱敏的顺序裁剪数据,顺序不能反;契约拉取失败就直接停住,**宁可中断也绝不无裁剪放行**。业务逻辑以 jar 形式存放在逻辑仓库,加载前做哈希校验,用独立类加载器隔离,防止篡改和冲突。写库失败的消息进死信,可查、可标记重放;进度按提交时间戳换算成滞后秒数和积压条数。

**验证。** 内核全部纯函数化,离线断言不碰 etcd、Kafka、数据库和框架,覆盖分配、交接、再平衡、扩缩容与端到端不丢不重;真栈检查在真实 etcd、Kafka、TiCDC、TiDB 上验证起点定位、T0 健康序和指令下发。

**一句话收口**:调度内核决定"跑在哪、何时换",业务外壳提交"跑什么";etcd 租约加数据库唯一键解决防双消费,T0 三规则加锚点二分解决批流衔接,fail-closed 契约裁剪守住数据安全。

## 三、数据打标引擎:批流一体的规则打标

**定位与核心问题。** 打标引擎要解决的核心问题是:业务方用配置(可视化/决策表/手写规则)表达"什么数据应该打上什么标签",而平台要在三种形态下执行同一份规则——**在线**单条实时求值、**流式**增量数据持续求值、**批式**全量历史回刷。如果三种形态各自实现一套规则解释器,规则语义必然漂移。引擎的答案是:**规则只写一次,三端共享同一套"生成 + 编译 + 动作"实现,只在执行承载上分化**。

**整体架构:三端一库。** 共享编译库承载唯一实现——把配置生成成 Fact 类源码与 DRL 文本、做 KieBase 编译、提供规则动作桥;三端各自承载执行:在线端在平台进程内按规则版本缓存编译产物、单条求值;流端跑在 Flink 上(dcp-tagstream),按实体键分区、事件级求值,派生字段用窗口状态累计;批端跑在 Spark 上(tagengine-executor),driver 装配执行计划并做编译校验,executor 逐分区求值并把结果写进标签事实表。Drools 统一采用 8.44.1 版本(Java 17 兼容),三端同源保证同一份规则在任何形态下行为一致。

**规则模型:定义三态,执行两层。** 规则定义支持三种方式——**可视化**(单条规则)、**决策表**(分档互斥:每行一条规则,行序决定优先级,外加兜底档)、**手写 DRL**(原样直跑,保底通道);三种方式统一走同一个生成器输出 DRL。执行分两层:**平铺规则**按配置顺序逐条执行,任一规则触发停止则跳过剩余;**规则流**是步骤编排——某一步命中或未命中后,可以继续、终止、结束或跳转,支持嵌套子流程(有递归深度防护)。规则里只写业务语义,动作只有两个:tag() 打标签、halt() 停止当前求值,由平台的动作桥承接,规则作者不需要懂执行细节。

**关键设计之一:生成式的 Fact 与 DRL。** 每个任务按自己的字段清单(数据集字段加派生字段)**动态生成 Fact 类源码**——字段全部用包装类型,保证规则里"字段为空"的判空可表达;包名按任务与版本隔离,避免任务间类名冲突。规则配置再生成 DRL 文本,每个资产生成独立包。**生成而非手写**,是"可视化配置能获得与手写规则同等执行性能"的关键;而保留手写 DRL 直跑,是给复杂场景留的逃生通道。

**关键设计之二:Drools 集成的"标准姿势"。** 集成最核心的取舍是**不用任何类加载器黑客**:Fact 源码以 Java 源文件形式写进 KieModule,和所有 DRL 一起交给 Drools 的标准编译器一并编译,编译错误带文件与行号明细返回;编译产物自带的类加载器就是 Fact 类与规则引用的"同一来源",无自定义加载器、无内存编译。**分发也走标准做法**:批端广播的是"计划文本"(Fact 源码加 DRL 文本),不广播编译产物——每个 executor 用同一套编译工厂在本地重建并缓存,彻底避开"跨 JVM 反序列化动态类"的经典坑。多资产共用一个编译基座,靠包隔离加规则包过滤保证互不串扰。规则动作经线程本地上下文桥接:每次求值前绑定行级接收器与当前会话,求值后立即清理,多线程互不泄漏。

**批端的完整流水。** 批任务从读数据集开始:按 schema 真相校验字段、派生聚合字段,装配可序列化的执行计划,driver 侧先做一次编译校验——**坏规则在任务开始前就失败,不会带到分布式执行里**;然后逐分区各起一个状态化会话,逐行把数据填进 Fact 求值,命中结果以行级标签落库,写入采用"当前值语义":按任务分区删旧后追加,依靠表格式的时间旅保留历史。批端还提供试跑能力:限制采样条数、输出命中矩阵,帮助业务方在正式运行前校准规则。

**验证与收口。** 引擎的正确性建立在"三端同源"上:生成器、编译器、动作桥三处只有一份实现,在线、流、批的差异仅在会话生命周期与并发承载;同一份规则配置在三端执行结果一致,靠版本化编译产物缓存与命中矩阵保证可回归。

**一句话收口**:配置生成源码、源码标准编译、三端同源执行——规则只写一遍,在线单条、流式增量、批式全量三种形态共享同一份语义,批端负责历史回刷、流端负责增量维护,规则作者只写业务、不碰执行。

## 四、数据资产体系:湖仓、血缘与目录

**定位与核心问题。** 前三个子系统让数据流动起来,这一层回答治理问题:**数据从哪来、到哪去、谁在消费、属于什么业务**。过去这些信息散落在同步作业配置、订阅契约、模型定义里,查一条链路要人工翻库。资产体系把它们收进统一治理视图,分三块:湖仓同步把变更沉淀成可分析的历史,血缘图谱回答"关系",资产目录回答"分类",三者共享同一份存量元数据。

**湖仓同步。** 目标库变更经消费底座 lake 通道流入湖仓作业(Spark Iceberg),把频繁变更的在线表沉淀为可回溯、可分析的湖上历史——数据"存"的形态与"用"的形态分离,在线表只管最新状态,历史分析走湖。

**血缘图谱。** 图数据库承载表、字段、源系统、作业、应用之间的多跳关系,支持溯源(上游)、影响(下游)、字段级链路和全图可视化。节点五类:**表**(逻辑表、模型表、物理落库表)、**字段**、**源系统**、**同步作业**、**应用**(订阅契约);边五类:表包含字段、源系统作为作业的来源、作业是表的来源、作业逐字段记录映射(来源字段、目标字段、转换方式)、应用消费表。模型的关键选择是**字段级**:多源合流时同一个目标字段会挂多条映射边,天然表达"一列被多个源写过"——合流场景的治理问题(某列到底谁写的)只有字段级才能回答。图谱的输入全部是**平台真实存量**——模型定义、逻辑表登记、同步作业定义与字段映射、数据源配置、订阅契约——不虚构任何关系;构建方式是**幂等全量重建**:启动就绪后自动重建一次,清图后按存量重新解析载入,任何时候可以手动触发,结果一致——配置改了,重建即同步,图谱永不过期。四类查询覆盖典型治理问题:上游溯源(多跳多路径)、下游影响(改表先看影响面)、字段链路(完整流转含消费方)、全图可视化。

**资产目录。** 目录由三部分组成。**资产台账**:目标库物理表加模型层/逻辑表标注加字段探测,回答"平台有哪些资产";**人工业务标签**:资产与标签路径的绑定(如"业务域/电商""项目/营销"),路径即标签、天然支持层级聚合,支持打标、去标、按标签查资产、标签树统计,全程审计留痕——这是业务治理的唯一录入点;**自动标签不落库**:分层、来源、类型等客观属性由血缘图实时推导,不重复存储、永不失效。人工标注表达"业务归属",自动推导表达"客观事实",两者在目录视图里合并呈现,互补而非重复。

**边界与演进。** 当前覆盖同步层与订阅消费(表级),即数据"进"和"出"的主干;规则/打标层与字段级消费列是下一步扩展——图模型已经预留了位置(应用节点与字段节点),扩展只是增加解析源,不需要改模型。

**一句话收口**:湖仓沉淀历史、血缘从真实存量推导字段级关系、幂等重建保证不过期;目录用台账加人工标签回答归属、用血缘推导回答属性——数据与标签因此可查、可溯源、可评估影响,治理有了统一入口。

## 附:两条链路与四个子系统的协作关系

```
┌─ 平台栈(同步链路)────────────────────────────────────────────────┐
│  六类源库 → SeaTunnel CDC(位点透传) → 采集转换(位点发号 + 桶路由)    │
│    → Kafka dcp.*(按桶分区保序) → SyncConsumer(写者列裁判) → TiDB 分表 │
└──────────────────────────────┬───────────────────────────────────┘
                               │ TiCDC changefeed
┌─ 出口栈(消费底座 V2)──────────▼───────────────────────────────────┐
│  出口栈 Kafka → 统一调度框架(etcd: 分配 / 迁移 / 扩缩容 / 交接)       │
│     ├─▶ 打标引擎(tag):   在线 / 流(Flink) / 批(Spark) 三端打标      │
│     ├─▶ 湖同步(lake):    Spark Iceberg 湖仓沉淀                    │
│     ├─▶ 订阅交付(sub):   变更流出口(Pull / Push)                    │
│     └─▶ 事件入站(ingest):外部事件接入                               │
└──────────────────────────────────────────────────────────────────┘
  数据资产体系(湖仓 + 血缘图谱 + 资产目录) ◀── 统一治理视图:溯源 / 影响 / 归属
```

- 同步链路负责"进"——把六类源的变更统一成一种语言,位点即序号、写者列裁判安全合流到目标表;
- 消费底座负责"递"——调度框架内核托管线程,批流衔接与防双消费由内核兜底;
- 打标引擎负责"产"——规则三端同源,把数据与标签连起来;
- 资产体系负责"管"——湖仓沉淀历史、血缘溯源、目录归类,支撑查找、评估与治理。
