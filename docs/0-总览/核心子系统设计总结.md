# 数据平台核心子系统设计总结

平台由四个核心子系统构成,它们各自解决一类通用难题,又串联成一条完整的数据价值流水线:

- **数据同步链路**——把多源异构库的变更实时搬进平台(数据入口);
- **数据消费底座**——把变更流可靠地交给业务逻辑(通用消费通道);
- **数据打标引擎**——用规则把数据变成业务标签(价值加工);
- **血缘与资产目录**——让数据与标签可查、可溯源、可治理(治理视图)。

协作关系一句话:**同步链路把数据搬进来,消费底座把它交给业务,打标引擎产生标签,血缘与资产目录让这一切可视可管**。以下按统一结构(定位与核心问题 → 整体架构 → 关键机制 → 验证 → 收口)逐一总结。

---

## 一、数据同步链路:多源异构库的统一 CDC

**定位与核心问题。** 数据同步链路是平台自研的统一 CDC 链路。它要解决的核心问题是:平台里有 MySQL、PostgreSQL、SQLServer、Oracle、Mongo 五类异构源库,变更数据都要实时汇聚到统一的目标库,而且要支持多源合流——多个源库的订单变更落到同一张物理表。过去每一类源、每一个任务都要各自实现一套采集配置、发号、幂等写入和重试机制,重复造轮子。V3 链路把"采集、发号、汇入"这三件通用难题一次性收编进链路内核,任务侧只需要配置:选哪个源、同步哪些表、落到哪张目标表。

**整体架构分三段。** 采集段由 SeaTunnel CDC source 承担,针对五类源分别做方言适配——MySQL 走 binlog 并分配独立 server-id,PostgreSQL 用独立复制槽加 pgoutput,SQLServer 走原生 CDC,Oracle 走 LogMiner 并处理 CDB/PDB 透传,Mongo 用变更流并保证 exactly-once;传输段是 Kafka,每张源表一个 topic,命名即契约;汇入段是同步消费内核,从 Kafka 攒批消费、逐批写入目标物理表。工程上拆成转换插件、同步消费内核、湖同步作业三块——转换插件负责"把五类源的变更变成同一种语言",消费内核负责"把语言变成目标表上的行",两条边界之外不再有第三种写入路径。

**数据面流转。** 源库变更被采集后,先过一层统一化转换——行类型归一、字段映射、业务键拼装、领号、路由计算,再以统一信封写入 Kafka;信封上带路由桶号作为分区键,保证同一个业务键的变更永远落在同一个分区、同一个目标分片。消费侧取出信封还原成变更记录,按逻辑表分组,主键变更拆成删加一对操作,送入写入队列。

**关键设计之一:发号权下放与写者列裁判。** 我们放弃过"全局一个递增序号"的方案:全局序号的大小跨源没有业务语义,会误拒合法更新,还会让快源饿死慢源。最终把发号权下放到每条采集流——每个"任务×源表"一条独立序列,只保证"会竞争同一行的变更"之间可比,序列只用于机制用途(路由、重放检测、写序标记),不用它裁决业务先后;序列按区间预分配、持久化只增不减,重启不重号。写入裁判以写者列为单位:每个物理列记住最后写它的采集流序号,更新逐列判断、序号更大的写者赢——多源合流时,不同来源的变更各自负责各自的列,互不踩踏;单源同步则退化为整行序号裁判。删除同样用写者序号条件防护,保证重放不会误删。这一切的前提是一条窄行纪律:每个源只负责自己的列域,并且线上变更永远走链路。

**关键设计之二:攒批汇聚与已写游标。** 消费到的操作先进有界队列,队列满就背压减速;写线程按物理表分桶,凑够条数或等够时延就触发一次落库,按写者分组拼成多值 SQL、单事务提交;只有真正写库成功,消费位点才推进——**位点跟着操作走,而不是跟着消费走**,失败的消息进死信可查可标记重放。整条链路是至少一次投递加幂等写入,目标表的业务唯一键兜底,重放不会产生错误结果。

**统一时间轴。** 变更位置与时间统一用源库的提交时间戳表达——TiDB 场景就是 TSO,换到 MySQL 集群则用 GTID 与提交时间线替代——这给批流衔接和锚点索引留出了统一的时间轴:湖同步、打标这些下游消费者,可以按"某个时间点之前的数据已全部到齐"做批打底、按之后做增量接力,而不必各自重新解决增量定位问题。

**验证。** 正确性上做两层工作:一是语义推演,把列重叠、行重叠、行列都重叠三种合流语义逐一分析,明确哪种天然安全、哪种必须靠纪律约束、哪种根本无解;二是端到端演示脚本,在真实多源库与 Kafka 上验证采集、转换、合流、写入的完整链路,包括分片订单表的多源合流场景。

**一句话收口**:采集统一五种方言、发号下放每条采集流、写入攒批且位点跟操作走——多源异构库的变更靠"独立序列加写者列裁判"安全合流,靠"至少一次加幂等写入"保证不重不乱。

## 二、数据消费底座:统一增量消费通道

**定位与核心问题。** 数据消费底座是平台自研的统一增量消费通道。它要解决的核心问题是:平台里有湖同步、打标、订阅交付等多类数据消费场景,每一类过去都要各自实现一套位点管理、调度、重试、死信和批流衔接机制,重复造轮子。底座把这些通用难题一次性收编进平台内核,业务侧只需要写一个业务逻辑、再加一份任务配置,就能获得完整的消费能力。

**整体架构分三块。** 控制面是决策大脑,负责新表感知、流登记、锚点与水位维护、任务校验、批阶段执行、起点计算、单元规划、租约管理、巡检和进度计算;计算面是执行者,可以有多个实例,只负责接收控制面下发的单元指令、从 Kafka 的指定位置开始消费、按契约裁剪数据、调用业务逻辑、提交位点并定期心跳;数据面由 TiCDC、Kafka、TiDB 源库、元数据库和逻辑仓库组成。工程上拆成六个模块:SDK、控制面内核、计算面内核、适配层、控制面服务、计算面服务,拆分遵循依赖单向、部署边界、变更频率三条准则——内核是纯函数,不依赖任何框架和中间件,因此可以离线自检。

**数据面流转。** 数据面的变更由 TiCDC changefeed 输出到 Kafka,每张表一个 topic,变更位置统一用 TiDB 的 TSO 表达。控制面有一个常驻索引器持续消费 Kafka,把提交时间戳到 Kafka offset 的映射按采样策略落成稀疏锚点索引,同时维护每个分区的最高水位。锚点只是加速器,丢了可以重建;没有锚点时退化为按时间粗定位加短扫,定位降级但正确性不变。

**批流衔接:先批打底,再增量接力。** 一个消费任务启动时先跑批阶段:控制面拉取平台快照接口,以统一边界时点 T0 为准把历史全量打底,用同一份业务逻辑以快照模式执行。T0 的取值被三条规则锁死:不能早于 changefeed 的起点,否则增量段之前的数据没进 Kafka;不能早于 GC 回收点,而且这一条取不到值就直接失败、绝不静默跳过,因为那等于允许读已被回收的版本;不能晚于分区最新水位,否则会凭空跳过数据。批阶段完成后,增量段的起点就是每个分区第一个提交时间戳大于 T0 的位置,靠锚点二分加短扫定位,保证快照覆盖到 T0、增量从 T0 之后开始,不重不丢。

**单元与租约:防双消费的两道保险。** 任务按分区规划成一个个消费单元,控制面给每个单元下发指令,内容包括起点位置、业务逻辑引用、租约和配额。租约机制保证每个单元同一时刻只有一个执行者,心跳续租;单元失联或换代时走离线返工流程,从已提交位点续跑,不猜位点。数据库里有一张单元分区表,以主题、分区、代次为唯一键,两个执行者抢同一个分区时第二个直接违反唯一键,这是防双消费的最终兜底,不依赖分布式锁。巡检每三十秒跑一次,发现异常只告警不动手。

**契约与安全:宁可中断,绝不无裁剪放行。** 计算面消费前要先拉取契约视图,按列投影、行条件、脱敏的顺序裁剪数据,顺序不能反;契约拉取失败就直接停住,宁可中断也绝不无裁剪放行。业务逻辑以 jar 形式存放在逻辑仓库,加载前做哈希校验,用独立类加载器隔离,防止篡改和冲突。写库失败的消息进死信,可查、可标记重放。进度按提交时间戳换算成滞后秒数和积压条数。

**SDK 与验证。** 业务作者只需要实现 SDK 里的消费逻辑接口,SDK 是零第三方依赖的,所以业务 jar 不会被平台升级绑架。批阶段和增量段执行的是同一份业务逻辑,执行器可以切换。底座正确性靠两层验证:内核全部纯函数化,两百多项离线断言不碰 Kafka、数据库和框架,覆盖起点算法、编排、批阶段、防双消费和端到端不丢不重;真栈检查在真实 Kafka、TiCDC、TiDB 上验证起点定位、T0 健康序和指令下发。第一个迁移上来的业务实例是打标引擎,批阶段用 Spark 回刷历史,增量段用 Flink 流式处理。

**一句话收口**:控制面决策、计算面执行、内核纯函数可离线自检;T0 三规则加锚点二分解决批流衔接,数据库唯一键加租约解决防双消费,fail-closed 契约裁剪守住数据安全。

## 三、数据打标引擎:批流一体的规则打标

**定位与核心问题。** 打标引擎要解决的核心问题是:业务方用配置(可视化/决策表/手写规则)表达"什么数据应该打上什么标签",而平台要在三种形态下执行同一份规则——**在线**单条实时求值、**流式**增量数据持续求值、**批式**全量历史回刷。如果三种形态各自实现一套规则解释器,规则语义必然漂移。引擎的答案是:**规则只写一次,三端共享同一套"生成 + 编译 + 动作"实现,只在执行承载上分化**。

**整体架构:三端一库。** 共享编译库承载唯一实现——把配置生成成 Fact 类源码与 DRL 文本、做 KieBase 编译、提供规则动作桥;三端各自承载执行:在线端在平台进程内按规则版本缓存编译产物、单条求值;流端跑在 Flink 上,按实体键分区、事件级求值,派生字段用窗口状态累计;批端跑在 Spark 上,driver 装配执行计划并做编译校验,executor 逐分区求值并把结果写进标签事实表。Drools 统一采用 8.44.1 版本(Java 17 兼容),三端同源保证同一份规则在任何形态下行为一致。

**规则模型:定义三态,执行两层。** 规则定义支持三种方式——**可视化**(单条规则)、**决策表**(分档互斥:每行一条规则,行序决定优先级,外加兜底档)、**手写 DRL**(原样直跑,保底通道);三种方式统一走同一个生成器输出 DRL。执行分两层:**平铺规则**按配置顺序逐条执行,任一规则触发停止则跳过剩余; **规则流**是步骤编排——某一步命中或未命中后,可以继续、终止、结束或跳转,支持嵌套子流程(有递归深度防护)。规则里只写业务语义,动作只有两个:tag() 打标签、halt() 停止当前求值,由平台的动作桥承接,规则作者不需要懂执行细节。

**关键设计之一:生成式的 Fact 与 DRL。** 每个任务按自己的字段清单(数据集字段加派生字段)**动态生成 Fact 类源码**——字段全部用包装类型,保证规则里"字段为空"的判空可表达;包名按任务与版本隔离,避免任务间类名冲突。规则配置再生成 DRL 文本,每个资产生成独立包。**生成而非手写**,是"可视化配置能获得与手写规则同等执行性能"的关键;而保留手写 DRL 直跑,是给复杂场景留的逃生通道。

**关键设计之二:Drools 集成的"标准姿势"。** 集成最核心的取舍是**不用任何类加载器黑客**:Fact 源码以 Java 源文件形式写进 KieModule,和所有 DRL 一起交给 Drools 的标准编译器一并编译,编译错误带文件与行号明细返回;编译产物自带的类加载器就是 Fact 类与规则引用的"同一来源",无自定义加载器、无内存编译。**分发也走标准做法**:批端广播的是"计划文本"(Fact 源码加 DRL 文本),不广播编译产物——每个 executor 用同一套编译工厂在本地重建并缓存,彻底避开"跨 JVM 反序列化动态类"的经典坑。多资产共用一个编译基座,靠包隔离加规则包过滤保证互不串扰。规则动作经线程本地上下文桥接:每次求值前绑定行级接收器与当前会话,求值后立即清理,多线程互不泄漏。

**批端的完整流水。** 批任务从读数据集开始:按 schema 真相校验字段、派生聚合字段,装配可序列化的执行计划,driver 侧先做一次编译校验——**坏规则在任务开始前就失败,不会带到分布式执行里**;然后逐分区各起一个状态化会话,逐行把数据填进 Fact 求值,命中结果以行级标签落库,写入采用"当前值语义":按任务分区删旧后追加,依靠表格式的时间旅保留历史。批端还提供试跑能力:限制采样条数、输出命中矩阵,帮助业务方在正式运行前校准规则。

**验证与收口。** 引擎的正确性建立在"三端同源"上:生成器、编译器、动作桥三处只有一份实现,在线、流、批的差异仅在会话生命周期与并发承载;同一份规则配置在三端执行结果一致,靠版本化编译产物缓存与命中矩阵保证可回归。

**一句话收口**:配置生成源码、源码标准编译、三端同源执行——规则只写一遍,在线单条、流式增量、批式全量三种形态共享同一份语义,批端负责历史回刷、流端负责增量维护,规则作者只写业务、不碰执行。

## 四、血缘与资产目录:数据资产的可视与治理

**定位与核心问题。** 前三个子系统让数据流动起来,这一层回答治理问题:**数据从哪来、到哪去、谁在消费、属于什么业务**。过去这些信息散落在同步作业配置、订阅契约、模型定义里,查一条链路要人工翻库。血缘与资产目录把它们收进一个统一的治理视图:血缘回答"关系",目录回答"分类",两者共享同一份存量元数据。

**整体架构。** 分两半:**血缘图**用图数据库承载表、字段、源系统、作业、应用之间的多跳关系,支持溯源(上游)、影响(下游)、字段级链路和全图可视化;**资产目录**用元数据库承载资产台账与人工业务标签,支持标签树、按标签检索。前端提供图谱与目录两个视图,自动标签由血缘图实时推导、人工标签按需登记,互补而非重复。

**血缘图模型。** 节点五类:**表**(逻辑表、模型表、物理落库表,是核心节点)、**字段**(表下逐字段)、**源系统**、**同步作业**、**应用**(订阅契约)。边五类:表包含字段;源系统作为作业的来源;作业是表的来源;作业逐字段记录映射关系(来源字段、目标字段、转换方式)——**多源合流时同一个目标字段会挂多条映射边**,天然表达"一列被多个源写过";应用消费表,表达订阅下游。这个模型的关键选择是**字段级**:血缘不只到表,还到列,因为多源合流场景的治理问题(某列到底谁写的)只有字段级才能回答。

**数据来源与构建。** 图谱的输入全部是**平台真实存量**:模型定义、逻辑表登记、同步作业定义与字段映射、数据源配置、订阅契约——不虚构任何关系;平台未登记的源表不猜名,只在载荷里带源字段名。构建方式是**幂等全量重建**:启动就绪后自动重建一次,清图后按存量重新解析载入,任何时候可以手动触发,结果一致。这种"从存量推导、可重建"的设计保证图谱永不过期——配置改了,重建即同步。

**查询能力。** 四类查询覆盖典型治理问题:上游溯源(这条数据从哪些源来,支持多跳与多条路径)、下游影响(这张表变了会影响谁)、字段链路(某个字段的完整流转链,含消费方)、全图(前端图谱直接渲染)。血缘因此不只是"看",而是变更评估的依据:改一张表之前,先看下游影响面。

**资产目录。** 目录由三部分组成。**资产台账**:目标库物理表加模型层/逻辑表标注加字段探测,回答"平台有哪些资产";**人工业务标签**:资产与标签路径的绑定(如"业务域/电商""项目/营销"),路径即标签、天然支持层级聚合,支持打标、去标、按标签查资产、标签树统计,全程审计留痕——这部分是业务治理的唯一录入点;**自动标签不落库**:分层、来源、类型等客观属性由血缘图实时推导,不重复存储、永不失效。人工标注表达"业务归属",自动推导表达"客观事实",两者在目录视图里合并呈现。

**边界与演进。** 当前覆盖同步层与订阅消费(表级),即数据"进"和"出"的主干;规则/打标层与字段级消费列是下一步扩展——图模型已经预留了位置(应用节点与字段节点),扩展只是增加解析源,不需要改模型。

**一句话收口**:血缘从真实存量推导关系、字段级表达合流,幂等重建保证不过期;目录用台账加人工标签回答归属、用血缘推导回答属性——数据与标签因此可查、可溯源、可评估影响,治理第一次有了统一入口。

## 附:四个子系统的协作关系

```
多源数据库 ──[同步链路]──▶ 目标库 / 湖(变更流同时进入 Kafka)
                                  │
                     [消费底座]──┼──▶ 打标引擎(在线/流/批三端打标)──▶ 标签事实
                                  ├──▶ 订阅交付
                                  └──▶ 湖同步
                                  │
                     [血缘与资产目录] ◀── 统一治理视图(关系 + 分类)
```

- 同步链路负责"进"——把五类源的变更统一成一种语言,安全合流到目标表;
- 消费底座负责"递"——把变更流可靠地交给任何业务逻辑,批流衔接与防双消费由内核兜底;
- 打标引擎负责"产"——规则三端同源,把数据和标签连起来;
- 血缘与资产目录负责"管"——把前三个环节的资产与关系收进统一图谱,支撑查找、评估与治理。
