# 监控告警体系设计与落地

> 状态:定稿(2026-10-11),汇总 Prometheus 采集三层、中间件采集三路径、平台业务指标体系与告警规则集。
> 定位:讲清「Prometheus 采什么、怎么采、告警怎么判」,并厘清两套监控体系(Prometheus 管健康、调度框架管吞吐)的边界与桥接。
> 配套:治理接入点(actuator base-path/网关白名单)见《7-微服务架构/微服务治理架构与落地细节.md》§三.6;M1-M8 实施记录见《微服务架构方案.md》§13.3a。

## 一、两套监控体系:边界先行

```
Prometheus + Grafana:  微服务健康 + 中间件水位 + 节点资源(通用治理监控)
调度框架自建体系:      rps/lag/errorRate 业务吞吐(etcd 快照 + 差分派生,不经过 Prometheus)
```

- 平台 7 服务暴露的 Actuator 指标是 Prometheus 采集面;
- 业务吞吐指标由调度框架自己算(业务侧只上报四计数器原始快照,框架差分派生),走 etcd 与前端下钻;
- 告警分工:**Prometheus 管「组件死不死」,调度框架管「数据跑不跑得动」**。

## 二、Prometheus 采集三层

### 1. 应用层:Spring Boot Actuator 原生指标(7 服务)

| 类别 | 具体指标 | 用途 |
|---|---|---|
| JVM 内存 | `jvm_memory_used_bytes`(堆/非堆)、`jvm_memory_max_bytes` | OOM 预警、内存泄漏趋势 |
| GC | `jvm_gc_pause_seconds`、GC 次数 | Full GC 频繁 → 堆不够用 |
| 线程 | `jvm_threads_live`、`jvm_threads_states` | 线程泄漏(WebFlux 线程纪律的验证窗口) |
| HTTP | `http_server_requests_seconds`(count/sum/max,按 uri/status 分维)、当前连接数 | 接口 QPS/P99、4xx/5xx 率 |
| 连接池 | `hikaricp_connections_active/idle/pending` | 元库连接池打满预警 |
| 日志 | `logback_events_total`(error/warn 计数) | 错误率趋势 |

### 2. 中间件层:exporter 采集(水位是重点)

| 中间件 | 关键指标 | 已定告警口径 |
|---|---|---|
| Kafka 平台栈 | broker CPU、磁盘 I/O、MessagesInPerSec、ISR 收缩、UnderReplicatedPartitions | **broker CPU >70% 水位告警**(2.5 万条/s/核偏紧,超了错开部分库全量) |
| TiDB | TiKV CPU/region 分布/QPS | 热窗口写入压力 |
| MySQL 元库 | 连接数、复制延迟、慢查询、缓冲池命中 | ShedLock 锁表健康 |
| etcd | 选主次数、fsync 延迟、DB 大小 | 选主抖动 → 调度不稳(平台强依赖) |
| Nacos/Redis/MinIO | 节点存活、内存、桶用量/对象数/离线盘 | 治理层健康、1.5PB 湖容量水位 |

### 2.1 各中间件指标详解(按优先级:谁最紧、谁最敏感)

**Kafka(平台栈 + 出口栈)—— 全链路最紧的偏差点**

| 指标 | 指标名 | 看什么 | 为什么 |
|---|---|---|---|
| Broker CPU | 节点 CPU / `kafka_server_broker_topic_metrics` 派生 | 水位 | 平台栈 2.5 万条/s/核偏紧,**CPU >70% 告警**(全量时错开部分库) |
| 消息速率 | `kafka_server_broker_topics_metrics_messages_in_per_sec` | 吞吐 | 分 topic 看写入是否超规划 |
| ISR 收缩 | `kafka_cluster_partition_under_replicated_partitions` | 副本同步 | ISR 掉了 = 副本落后,minISR=2 时再掉就不可写 |
| UnderReplicatedPartitions | `kafka_cluster_partition_underreplicated` | 复制健康 | 常驻 >0 说明某 broker 磁盘/网络异常 |
| 磁盘 I/O | 节点磁盘 | 落盘能力 | Kafka 顺序写,磁盘打满拖累整个 broker |

Kafka 是缓冲层,broker CPU 是定案点名「全链路偏紧点之一」——CPU 高直接影响上下游吞吐。

**TiDB(TiDB Server + TiKV + PD)—— 目标库写入压力**

| 组件 | 指标 | 看什么 |
|---|---|---|
| TiDB Server | QPS、连接数、`tidb_server_query_duration` | SQL 层算力(定案「TiDB SQL 层算力被低估」,1C 打 8.3MB/s 就 90%) |
| TiKV | CPU、`tikv_engine_size_bytes`、region 数量、调度并发 | 存储引擎 + 写入压力 |
| PD | region 分布、leader 分布 | region 是否倾斜(热点) |

重点看 TiKV region 分布:写入热点会钉死在某几个 region,导致单 TiKV 节点过载——这是「热点桶迁移」问题的底层信号。

**MySQL(元库 + demo 源库)—— 元数据与锁的底座**

| 指标 | 指标名 | 看什么 | 告警 |
|---|---|---|---|
| 连接数 | `mysql_global_status_threads_connected` | 连接池水位 | **>80% 池上限告警** |
| 复制延迟 | `mysql_slave_status_seconds_behind_master` | MGR 半同步 | **>10s 告警** |
| 慢查询 | `mysql_global_status_slow_queries` | SQL 性能 | 元库慢查询拖累所有控制面 |
| 缓冲池命中率 | `innodb_buffer_pool_reads` / `read_requests` | 内存是否够 | 命中率骤降 = 缓冲池太小,退磁盘 |

项目特殊点:MySQL 元库承载 **ShedLock 锁表 + 对账判据**,锁表健康决定定时任务互斥是否正常——元库指标是「分布式锁底座」的监控,不是普通业务库。

**etcd(调度框架底座)—— 平台强依赖,最敏感**

| 指标 | 指标名 | 看什么 | 告警 |
|---|---|---|---|
| 选主次数 | `etcd_server_leader_changes_seen_total` | 主稳定性 | **1h 内 >2 次告警**(选主抖动 = 调度不稳) |
| fsync 延迟 | `etcd_disk_wal_fsync_duration_seconds` | 磁盘写入延迟 | **P99 >100ms 告警** |
| DB 大小 | `etcd_mvcc_db_total_size_in_bytes` | 存储膨胀 | 压缩失效会无限涨 |
| 请求延迟 | `etcd_grpc_unary_requests_duration` | API 性能 | 调度主的每次判死/分配都过 etcd |

调度框架的分区归属、判死、交接、扩缩容全靠 etcd 的 CAS 写,**etcd 抖动 = 整个调度体系抖动**。

**Nacos(注册中心)—— 治理层健康**:节点存活、注册/订阅数、JVM/内存。本地 `SPRING_CLOUD_NACOS_DISCOVERY_ENABLED=false`(发现注册关闭),生产三机才用 Nacos 服务发现。

**Redis(打标在线层)—— 热路径**:内存 `redis_memory_used_bytes`、命中率 `keyspace_hits/(hits+misses)`、命令延迟 P99。标签实时查询打 `tag:online:{entity}`,命中率低 = 回源 MySQL 事实表、延迟飙升。

**MinIO(湖存储)—— PB 容量水位**:桶用量(1.5PB 容量规划)、对象数(小文件堆积)、离线盘(EC 纠删码磁盘故障)。

### 3. 基础设施层:节点与容器

| 采集器 | 指标 |
|---|---|
| Node Exporter | 节点 CPU/内存/磁盘 I/O/磁盘空间/网卡流量 |
| cAdvisor | 容器 CPU/内存/网络 |
| kube-state-metrics | Pod 状态、Deployment 副本数、节点 taint 状态 |

## 三、中间件指标采集:三种路径

| 路径 | 原理 | 适用中间件 |
|---|---|---|
| **原生 /metrics 端点** | 中间件自带 Prometheus 格式,直接抓 | TiDB 全家桶、etcd、Nacos、MinIO |
| **JMX Exporter** | JVM 系只暴露 JMX,挂 javaagent 转 /metrics | Kafka |
| **独立 exporter 进程** | 第三方小进程连中间件转 /metrics | MySQL、Redis |

### 三种路径的本质与选择决策树

**为什么有三种路径?** Prometheus 只能抓「HTTP 端点输出 Prometheus 文本格式」,而中间件暴露状态的方式各不相同——所以核心是找一个「翻译器」,把各自的状态翻译成 Prometheus 文本。三种路径的本质区别是**翻译器放在哪**:

| 路径 | 翻译器位置 | 进程关系 | 原理 |
|---|---|---|---|
| 原生 /metrics | 中间件内置 | 无额外进程 | 中间件开发时就埋了 metrics,自带 /metrics HTTP 端点直接输出 Prometheus 文本 |
| JMX Exporter | JVM 进程内 | 同进程(javaagent) | JVM 系只暴露 JMX(非 HTTP),挂 javaagent 在进程内读 JMX MBean 转成 /metrics |
| 独立 exporter | 独立旁路进程 | 旁路进程 | 中间件只暴露专有协议(SQL/RESP),exporter 伪装只读客户端去连,把「客户端视角」转 /metrics |

**选择决策树(按顺序判断)**:

```
① 中间件自带 /metrics 端点?        → 原生路径(零组件,如 TiDB/etcd/Nacos/MinIO)
② JVM 系、只暴露 JMX?              → JMX exporter(挂 javaagent,如 Kafka)
③ 只暴露专有协议(SQL/RESP 等)?     → 独立 exporter 进程(如 MySQL/Redis)
```

**三种路径的典型数据流**:

```
原生:      中间件进程 → 内置 HTTP /metrics(Prometheus 文本)→ Prometheus 直接抓
JMX:       JVM 进程(内嵌 jmx_exporter agent 读 JMX)→ 7071/metrics → Prometheus 抓
独立 exporter: mysqld_exporter 进程 --只读账号--> MySQL(SHOW STATUS)
                → 转指标 → 9104/metrics → Prometheus 抓
```

**选择动机(面试口径)**:路径 1 最省(零组件零配置);路径 2 是 JVM 系的无奈之选(JMX 不是 HTTP,必须 agent 翻译);路径 3 是「中间件没埋点」时的通用兜底——exporter 本质是「中间件的一个只读客户端」,把客户端能观测到的指标翻译出来。

### 逐个落地方式

**Kafka(JMX javaagent)**:

```bash
# kafka-server-start.sh 的 KAFKA_OPTS 里加
-javaagent:/opt/jmx_exporter/jmx_prometheus_javaagent.jar=7071:/opt/jmx_exporter/kafka.yml
```

**TiDB 全家桶(原生)**:PD `2379/metrics`、TiKV `20180/metrics`、TiDB Server `10080/metrics`,零配置直接抓。

**MySQL(mysqld_exporter)**:`mysqld_exporter --config.my-cnf=/etc/mysqld_exporter/.my.cnf`——只读监控账号。

**etcd(原生)**:`2379/metrics`,关注 leader_changes/fsync 延迟/DB 大小。

**Redis(redis_exporter)**:INFO 命令转指标(内存/命中率/延迟)。

**MinIO(原生,带认证)**:`/minio/v2/metrics/cluster` + bearer_token(svcacct 生成)。

**Nacos(原生)**:开 `nacos.metric.enabled=true` 走 `/actuator/prometheus`。

### Prometheus 侧配置(混合部署形态)

```yaml
scrape_configs:
  # ① 裸机中间件:static_configs 写死(拓扑同构,IP 固定)
  - job_name: kafka
    static_configs:
      - targets: ['10.66.1.11:7071', '10.66.1.12:7071', '10.66.1.13:7071']
  - job_name: tidb-pd
    static_configs:
      - targets: ['10.66.1.21:2379', '10.66.1.22:2379', '10.66.1.23:2379']
  # ② K8s 内组件:annotations 自动发现
  - job_name: k8s-pods
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: true
```

- 裸机用 static_configs;K8s 内用 annotations 自动发现(exporter 独立进程,不经网关、非边车模式);
- **抓取频率分层**:水位类 15s、计数类 30s、延迟类 60s——全部 15s 会给 Prometheus 本身加压。

### 两个工程细节(易踩坑)

1. **exporter 故障隔离**:JMX javaagent 是进程内挂载,配置写坏会导致 **Broker 起不来**——kafka.yml 规则需灰度验证;mysqld_exporter 用只读账号;
2. **告警规则收 AlertManager**:水位类(broker CPU、磁盘、堆内存、复制落后)与框架巡检告警互补。

## 四、平台业务指标体系(调度框架自建,不经过 Prometheus)

### 4.1 业务侧:只上报四个累计计数器

每 10s 续写一帧到 etcd,TTL 30s:`processedCount`(已处理数)、`committedOffset`(已提交位点)、`errorCount`(错误数)、`totalLatencyMs`(总延迟)。业务侧不做任何指标计算。

### 4.2 框架侧:差分派生 + 实查水位

| 派生指标 | 计算方式 |
|---|---|
| rps | 两周期快照 processedCount 差值 ÷ 周期 |
| errorRate | errorCount 差值 ÷ processedCount 差值 |
| avgLatency | totalLatencyMs 差值 ÷ processedCount 差值 |
| lag | **Kafka AdminClient 实查 endOffset** − 业务上报 committedOffset(框架内置,不靠快照) |

### 4.3 三级视图与四级聚合

- **三级视图**:分区级(线程自报)→ 表级(聚合流量与延迟)→ 实例级(加权负载);
- **四级聚合管线**:分区 → 实例 → 任务 → ns;
- **TTL 自动过期**:实例宕机后指标 key 自动消失,不出现脏数据;
- 展示用 3 帧滑动平均(平滑),判定用原始窗口 + 持续期(防毛刺误报)。

## 五、告警规则集

### 5.1 调度框架巡检规则(业务吞吐)

| 规则 | 阈值 |
|---|---|
| lag 高位 | lag > rps×5 且持续 3min |
| 错误率 | > 1% |
| 追平超时 | 10min 未追平 |
| 容量水位 | > 0.9 且已到 max |
| 实例失联/卡死 | lease 过期 / 快照 TTL 失效 |
| 迁移超时、无可用实例 | 事件触发 |

- 同对象同级别 10min 去重 + 恢复补发;推送 AlertSink 并写入事件流;告警通道复用网关。

### 5.2 Prometheus/AlertManager 规则(组件水位)

| 对象 | 规则示例 |
|---|---|
| Kafka broker | CPU > 70% 持续 5min(平台栈 2.5 万条/s/核口径) |
| 节点/容器 | 磁盘 > 85%、内存 > 90% 持续 5min |
| 元库 | 连接数 > 80% 池上限、复制延迟 > 10s |
| etcd | leader 变更 1h 内 > 2 次、fsync P99 > 100ms |

## 六、桥接与边界(诚实说明)

1. **现状**:M1-M8 已实现未部署验证;Prometheus 容器直连抓取 6 业务服务 `/api/actuator/prometheus`(网关白名单放行),不经网关;
2. **双轨**:业务下钻走平台前端(调度框架数据),组件水位走 Grafana,不强行合并;
3. **可选桥接**:业务指标若要进 Grafana 统一大屏,可经 exporter/PushGateway 转接——目前定论是维持双轨;
4. **部署形态**:Prometheus ×2 + Grafana ×2(治理面外挂裸机,Prometheus 远程写);告警通道复用网关,不另建告警服务。

## 七、面试口径(一句话版)

> 监控分两套:Prometheus 管「组件健康」——三层采集(应用层 Actuator 原生指标、中间件三路径 exporter/JMX/原生端点、基础设施 Node Exporter/cAdvisor),水位告警收 AlertManager;调度框架管「数据吞吐」——业务只报四计数器,框架差分派生 rps/lag/errorRate、Kafka AdminClient 实查水位,四级聚合到 ns,巡检告警 10min 去重 + 恢复补发。两套互补,告警分别收敛,监控链路不经网关。
