# 正式上线部署方案(百亿级容量定案)

> 定案日期:2026-10-08。本文档承载正式上线的完整容量规划与部署方案,配套图:[正式上线部署架构与流量图.svg](正式上线部署架构与流量图.svg)。

## 1. 定案参数与决策记录

| 参数 | 定案值 |
|---|---|
| 存量 | 100 亿条 × 1KB/条 = **10TB** |
| 源库 | **50 个**,跨机房分散分布,每机房千兆出口 |
| 单库全量限速 | **10MB/s**(read_limit 2.5MB/s × 4 chunk 线程) |
| 增量稳态 | **10 万 QPS** = 100MB/s |
| 部署位置 | **SeaTunnel 集中目标侧**(50 分散机房无法就近部署 worker,未压缩流必经专网,与部署位置无关) |
| 跨网链路 | **专网直连**(非公网 VPN),目标侧万兆入口直扛 |
| 部署形态 | 混合部署:有状态裸机 + 无状态 K8s |
| TiDB 热窗口 | **永久保留**(容量账见 §5) |
| 机房 | 自建 |
| 物理机 | **50 台**:64C/512G ×25 + 32C/256G ×25 |

决策口径(用户拍板,2026-10-07~08):

- 单库 10MB/s 源自源机房出口保护:每库 80Mbps = 千兆出口 8%,92% 留给源库业务。
- 50 库全并行 = 500MB/s = 万兆专网的 40%,无需分批错峰。
- 瓶颈优先级(修正后):**源机房出口带宽 > 源库读能力 > SeaTunnel 引擎 CPU > Kafka 写入 > 网卡带宽**。限速单位下沉到「源机房出口」,共享出口聚合限速。

## 2. 时序设计:先全量,后增量(不并发)

```
T0 ────────────── T1(5.56h) ─────────── T2(+9.3h) ────────→
│ ①全量段:50 库全并行    │ ②增量切换 + 追平段        │ ③稳态
│ 500MB/s = 50 万行/s    │ 增量作业从快照起点位点启动 │ 增量 10 万 QPS
│ 10TB 全部灌入 Kafka    │ 同步链路净消化积压 15 万/s │ 全链路满载
│ (增量不采,binlog 挂着) │ 增量补窗口期变更 ~37min/库 │ 只占全量设计 20%
└──────────────────────┴──────────────────────────┴──────────→
```

- **全量段**:50 库全并行,每库 2 亿条 = 200GB,10MB/s 限速,5.56 小时搬完全部 10TB。
- **切换点**:全量作业结束后,增量作业从快照起点位点启动。窗口期源库产生的 ~20 亿条变更(10 万 QPS × 5.56h)由增量补读:每库窗口期积压 4000 万条,单库增量作业 2 万条/s vs 产生速率 2000 条/s,净追赶 1.8 万条/s,**~37 分钟/库追平**,之后实时跟随。
- **追平段**:同步链路 25 万 QPS 中 10 万实时消化增量,净 15 万/s 消化全量积压 50 亿条 → 9.3 小时追平。**总历时 14.8 小时**(一个工作日内)。
- **设计原则**:全量峰值(采集 50 万行/s、下游 25 万 QPS)全面高于增量常态(10 万 QPS),**架构只按全量峰值设计,自然覆盖增量**。

## 3. 端到端链路与逐实例流量明细

### 3.1 源库 ×50(平台外)

| 项 | 每库分担 |
|---|---|
| 全量出流量 | 10MB/s = 80Mbps = 1 万行/s |
| 分线程 | 4 chunk 线程 × 2.5MB/s = 2500 行/s/线程 |
| 连接 | 4 JDBC 流式读 + 1 binlog(增量段) |
| 出口占用 | 千兆 8% |
| 增量段 | 2000 条/s = 16Mbps |

汇聚:500MB/s = 50 万行/s → 专网峰值 4Gbps(万兆 40%)。专网上跑的是**未压缩流**——压缩只发生在 SeaTunnel 写 Kafka 时(§7.1)。

### 3.2 SeaTunnel ×18 worker(时段分工,总数不变)

**全量段:12 个 worker 跑 50 个全量作业族(一库一作业族)**

| worker 分组 | 挂库数 | 入流量 | 负载(能力线 60MB/s) | 出流量 |
|---|---|---|---|---|
| 10 个 | 4 库 | 40MB/s = 4 万行/s | 67% | 压缩后 10MB/s 写 Kafka |
| 2 个 | 5 库 | 50MB/s = 5 万行/s | 83% | 压缩后 12.5MB/s |

**增量段:6 个 worker 跑 50 个 CDC 作业族(每库恒 1 并行度)**

| worker 分组 | 挂库数 | 入流量 | 负载(能力线 2 万条/s) |
|---|---|---|---|
| 4 个 | 8 库 | 1.6 万条/s = 16MB/s | 80% |
| 2 个 | 9 库 | 1.8 万条/s = 18MB/s | 90% |

能力线口径:全量 60MB/s(8C 流式读+序列化理论 8~12 万行/s × 50% 安全系数)、增量 2 万条/s(CDC 信封解析成本高,保守值)。**均为工程估算值,正式上线前必须用真实源库做单作业族压测校准**(跑满 read_limit 顶格,看 worker CPU 实际水位回填)。

### 3.3 Kafka 平台栈 ×3 broker(~400 分区 = 100 逻辑表)

topic 粒度:100 逻辑表一表一 topic(topic=dcp.{logicalTable},一组一 topic)。**分区数以并发量为原则**(数据量不参与,只决定全量时长):表峰值并发 = 来源库数 × 单库贡献(库限速 1 万条/s ÷ 库内表数),分区数 = 表并发 ÷ 单分区能力线 2000 条/s 向上取 2 的幂。均匀基线(每表 1 库来源)4 分区/表 = 400 总分区;多源合流表按来源库数上调(2 库→8、4 库→16、8 库→32),总分区落 350~500。消息 key=__bucket(MurmurHash3(业务主键)%4096),Kafka 默认分区器 murmur2(bucket)%P 落物理分区。

| 项 | 全量段每 broker | 增量段每 broker |
|---|---|---|
| 写入 | 16.7 万条/s = 41.7MB/s(压缩后) | 3.3 万条/s = 8.3MB/s |
| leader 分区 | ~133 个,每分区 1250 条/s 写 / 625 条/s 消费 | 250 条/s 写 |
| RF3 复制输出 | 83.4MB/s | 16.6MB/s |
| 总网络 | ~125MB/s(25GbE 4%) | ~25MB/s |
| CPU | **2.1 万条/s/核 ⚠ 全链路偏紧点之一(另一处 TiDB SQL 层,§6.2)** | 0.4 万条/s/核 |
| 落盘 | 积压 50 亿条压缩后 1.25TB×RF3÷3 = 1.25TB(容量 8%) | — |

### 3.4 同步链路 ×17 实例(25 万 QPS)

| 项 | 每实例分担 |
|---|---|
| 消费分区 | ~24 个(400÷17,跨 5~6 张逻辑表任务,一组一 topic 控制面异构调度) |
| 消费速率 | 1.47 万条/s = 14.7MB/s(压缩后),负载 74%(能力线 2 万) |
| 写 TiDB | 1.47 万条/s = 14.7MB/s,攒批多值 INSERT |
| 投递出口栈 | 1.47 万条/s,压缩后 ~3.7MB/s |
| 线程结构 | 1 消费线程(解析/路由/判身份)+ 共享写线程池(BatchWriteService) |

积压账(设计内,非故障):窗口期写入纯全量 100 亿条,同步链路同期吃掉 50 亿,**积压峰值 50 亿条**(压缩后 1.25TB×RF3,平台栈容量 38.4TB ✓);追平期净消化 = 25 万 − 增量 10 万 = 15 万/s → 9.3h 追平,总历时 14.8h。

25 万 QPS 的推导:下限 = 增量 10 万必须实时消化;追平时间 = 积压 ÷ (C − 10 万)。C=20 万(14 实例)总历时 22.2h;C=25 万(17 实例)14.8h;C=30 万(20 实例)11.1h。选 25 万 =「一个工作日内追平」与「单实例 1.5 万条/s 上限」的交集,再往上收益递减。

### 3.5 Kafka 出口栈 ×6 broker(128 分区)

每 broker:写入 4.2 万条/s = 10.4MB/s(32C/128G 的 ~5%,零压力);~21 分区;存储 53TB ÷ 6 = 8.8TB(容量 23TB 的 38%)。

### 3.6 消费底座 ×15 实例(ns 分池)

| ns | 实例数 | 每实例消费 | 每实例分区 |
|---|---|---|---|
| indexer | 3 | 1.67 万条/s | 8~9 |
| outlet | 3 | 1.67 万条/s | 8~9 |
| tag | 2 | 1.67 万条/s | 8~9 |
| sub | 2 | 1.67 万条/s | 8~9 |
| lake | 2 | 1.67 万条/s | 8~9 |
| ingest | 3 | 1.67 万条/s | 8~9 |

每实例 8C/16G,负载 ~83%;与出口栈写入同速率 → 零积压。各 ns 按订阅面过滤,实际处理量低于全量消费速率。

### 3.7 TiDB ×26 实例(Server 3 + PD 3 + TiKV 20)

| 组件 | 实例数 | 每实例分担 |
|---|---|---|
| TiDB Server | 3 | 入 8.3 万条/s = 83MB/s 攒批 SQL;按实测 8.3MB/s/核(1C 打满 90.6%)校准,3×8C 负载 ~42%,偏紧点之一(§6) |
| PD | 3 | 无数据流,region 调度/TSO 元信息,4C/8G |
| TiKV | 20 | 写 12.5MB/s 逻辑 → 压缩后 ~4.2MB/s 物理;容量 13.5TB/节点(88% 水位) |

### 3.8 湖仓 MinIO ×8 节点

每节点:湖批 2.16TB/天 ÷ 8 = 270GB/天;夜间 4h 批窗口 18.8MB/s;EC 8+4 后容量 95TB/节点,够 1 年,按年扩 8 节点。

## 4. 物理机装箱(50 台:64C/512G ×25 + 32C/256G ×25)

| 用途 | 台数 | 装箱方式 |

## 5. TiDB 永久保留容量账

```
日增逻辑 8.64TB(10 万 QPS × 1KB × 86400s)
→ RocksDB 压缩 3:1 → 2.9TB 物理 → RF3 → 8.6TB 物理/天
存量 10TB + 30 天增量 259TB = 269TB ÷ 15.36TB/节点 = 18 节点满水位 → 取 20 节点(88%)
永久保留:年增 3.1PB 物理 → 年 +205 节点(≈ 月 +17,即 5 台 64C 各 4 节点/月)
```

**两条落地路径**(用户已拍板永久保留,容量真相与备选并存):
- 路径 A(拍板口径):TiKV 20 节点起步,之后每月 +17 节点滚动扩容,3 年 ~615 节点。
- 路径 B(备选,防容量爆炸):TiDB 热 30 天(20 节点不动)+ 冷数据每日归档湖仓(Parquet 4:1,年增 790TB,MinIO 按年扩 8 节点)——数据在平台内同样永久保留,只是 30 天以上冷数据物理形态从 TiKV 变为 Parquet。

## 6. TiDB 写入能力实测与校准(2026-10-08 本机实测)

压测环境:本机 M1 Pro 8C/16G Docker,cgroup 限定资源复刻受限规格(TiKV 2C/2G、TiDB 1C、sync-log=true、bg-jobs=1、block-cache 128M),复刻同步链路攒批形态(16 分表、500 行/批多值 `INSERT ... ON DUPLICATE KEY UPDATE` 字段级 IF、1KB/行)。脚本:`scripts/tidb-bench/`。

### 6.1 实测矩阵

| 场景 | 配置 | 结果 |
|---|---|---|
| 3 节点集群 A3 | 3×TiKV 2C/2G + 2×TiDB 1C | **3323 行/s**(平台期) |
| **单节点 S1** | 1×TiKV 2C/2G + 1×TiDB 1C(无 raft 复制/2PC) | **8306 行/s** = 集群的 2.5 倍;TiDB 1C 打满 90.6%,TiKV 仅 15.6% |
| 同机 MySQL 8 基准 | 无 cgroup 限制,同形态压测 | 18053 行/s(宿主磁盘/网络无问题) |
| sync-log 对照 | 集群同条件 sync-log=false | +15% |
| batch-size 梯度 | 500 / 1000 / 2000 | 500 较优(2492/2435 下降) |

### 6.2 单节点对照的三个结论

1. **集群瓶颈不在 TiKV 存储引擎**:同样 2C 的 TiKV,去掉 3 副本复制和 2PC 后吞吐翻 2.5 倍——集群 3.3k 中约 60% 被 RF3 副本同步等待 + 跨节点 2PC 吃掉。
2. **TiDB SQL 层算力被低估**:1C 在 8.3MB/s 就打到 90.6%,即每核 ~8.3MB/s;3×8C 对 83MB/s 负载 ~42%,不再是「轻松」,与 Kafka broker 并列偏紧点。
3. **每核口径差 7 倍**:单节点 4.15k 行/s/核(无副本开销)vs 集群 580 行/s/核(含全部开销),量化了本机受限环境副本链路的代价。

### 6.3 外推区间与风险修正

- **下限 18.5 万行/s**:集群口径 580 行/s/核 × 320C(20×16C)线性外推。
- **上限 53 万行/s**:单节点口径 4.15k 行/s/核 × 320C ÷ 2.5 副本系数。
- 25 万 QPS 目标落在区间中下段,结论「**大概率达标但无冗余**」不变。
- **风险点修正**:从「TiKV 算力不足」改为「**副本同步链路(网络/fsync 等待)+ TiDB SQL 层算力**」;本机是 Docker 桥接 + cgroup 节流 + SATA 虚拟盘 fsync,真实物理机万兆 + NVMe + sync-log=false 会大幅收窄副本等待,实际吞吐偏向区间上段。
- **上线前必做**:真实规格(16C/64G、NVMe、sync-log=false、bg-jobs 6-8)重测校准,再定 TiDB 写入的最终实例数。

### 6.4 三预案(优先级修订)

| 优先级 | 预案 | 触发条件 |
|---|---|---|
| 1(前移) | **B:TiDB Server 3→4-5,并确认 NVMe/万兆/sync-log=false 落地** | 真实规格重测未达标时首选,直接对冲两个新识别的风险点 |
| 2(降级) | **A:TiKV 20→24-28** | TiKV 算力/容量侧再受限时启用(实测证明存储引擎非首要瓶颈) |
| 3 | C:追平期限速 20 万(总历时 22.2h) | 保底,以时间换空间 |

## 7. 关键配置与待办

### 7.1 Kafka producer 压缩(⚠ 代码待办)

压缩点:SeaTunnel worker 进程内 producer 端(源库读出行流 → SeaTunnel 序列化 JSON envelope → KafkaProducer 压缩 → 发送)。broker 零成本原样落盘,消费者透明解压,一次压缩两头受益(网络 + 落盘各省 4 倍)。选 lz4:3:1 压缩比已把平台栈写入压到 125MB/s,zstd 多压出的 1:1 只省内网带宽/盘,却多花 worker CPU(全量段已 70% 水位),不划算。

**当前代码未配置压缩**:`CdcStService.buildFamilyJobConfig` 的 Kafka sink 无 compression 参数(KafkaProducer 默认 none),**规划中的「压缩后 125MB/s」在配置落地前不成立**。落地写法(SeaTunnel Kafka sink 支持 kafka.config 透传官方 producer 参数):

```java
sink.put("kafka.config", Map.of(
    "compression.type", "lz4",
    "linger.ms", "5",
    "batch.size", "1048576"
));
```

broker 端无需改(默认 compression.type=producer 原样保存)。

### 7.2 read_limit 限速

```hocon
env {
  read_limit.bytes_per_second = 2621440   # 2.5MB/s/线程 × 4 chunk 线程 = 10MB/s/库
  read_limit.rows_per_second  = 2500      # 2.5MB/s ÷ 1KB,与 bytes 先到生效
}
```

参数语义:env 级**每线程**值,全局 = 参数值 × chunk 并行度;改并行度必须重算。已知坑:rows 过小阻塞 checkpoint(全量窗口 checkpoint 间隔 10s→60s)。

### 7.3 跨网 TCP 调优

50 库 × 4 chunk = 200 条跨专网 JDBC 长连接;单连接 BDP(2.5MB/s × RTT)默认 socket buffer 基本够,建议调大 SeaTunnel 节点 tcp_rmem/wmem 一层,防高 RTT 链路吞吐掉速。

## 8. 告警清单(部署时必建)

1. **平台栈 broker CPU 水位**(全链路偏紧点之一):>70% 时错峰部分库全量(专网有 60% 余量)。
2. **同步链路 lag**:全量窗口期允许到 50 亿条上限;窗口结束后应持续下降,9.3h 未追平说明有积压外故障。
3. **TiKV 容量水位**:永久保留口径按「月 +17 节点」预留采购周期;若改冷热分层,改为监控「归档作业成功率」。
