# 最小集群部署演练方案（v5）

> 目标：以三机异构环境验证**故障恢复与 HA 机制**（调度框架调度功能、数据面 HA、服务实例集群部署下的正常/故障演练）。不要求 QPS 和数据量。后续全量部署只是加实例。
> 执行结果与验证路径见配对文档《[最小集群部署演练结果](最小集群部署演练结果.md)》(H1-H17 逐场景结果 + 证据链 + 需确认项)。

## 1. 三机拓扑

| 机器 | 规格 | 角色 | WireGuard IP |
|---|---|---|---|
| 本地 Mac | M1 Pro 8C/16G/122G 盘/arm64 | 本机（bridge+端口映射） | 10.66.0.1 |
| 阿里云 ECS | 4C/8G/34G（ecs.u1-c1m2.xlarge）/x86_64 | 云机 1（host 网络） | 10.66.0.2 |
| 腾讯云 CVM | 4C/8G/43G/x86_64 | 云机 2（host 网络） | 10.66.0.3 |

- 网络：WireGuard 组建虚拟内网（UDP 51820）；云机容器 host 网络模式，macOS bridge+端口映射。
- 元库：阿里云 RDS MySQL 8.0（**X1 公网+白名单**）作主库 + 腾讯云 MySQL 从库容器（binlog 异步复制）。
- 关键参数：etcd election-timeout 5s 适配跨云延迟。
- 源库：单节点（demo TiDB / demo 业务库），不要求自身 HA，用 H11 断点续传演练替代。

## 3. SeaTunnel 集群化（v5 核心变化）

| 机制 | 说明 |
|---|---|
| 形态 | Zeta 引擎原生集群（Hazelcast IMDG），3 节点自动选主，平台侧无需自研任务分派 |
| 调度/迁移 | JobMaster 自动分配 slot；节点宕机 → Hazelcast 成员变更感知 → 作业重调度并从最近 checkpoint 恢复 |
| 提交入口 | 打任意节点自动转发（经 nginx LB 或直连任一 5801），backend SeaTunnelEngine 提交地址改 LB |
| Checkpoint 共享存储 | 本地卷 → **MinIO S3**（`seatunnel.engine.checkpoint.storage.type=s3`）；不共享 = 宕机后全量重发 |
| 恢复参数 | 提交必须带 savepoint 参数（REST `isStartWithSavePoint=true` 已由 backend 落地；CLI restore 同 jobId `-c -r`） |
| 发号语义 | CdcSeqTransform 故障重放重新领号段，序号间隙不影响 seq 大小幂等裁判（只增不重、允许跳变、严禁回退） |
| 源库资源 | server-id/复制槽按任务一源一采，迁移复用无冲突 |

**落地配置改动**：
1. `seatunnel/config/hazelcast.yaml`：member-list 扩为 10.66.0.1/2/3:5801
2. `seatunnel/config/seatunnel.yaml`：checkpoint storage 改 S3（MinIO endpoint + bucket）
3. docker-compose：seatunnel 拆为 3 服务（host 网络绑 WireGuard IP）

## 4. 内存预算（云机 8G 张力下的调整）

| 项目 | 原 | 调整后（compose 实际值，2026-10 核对） |
|---|---|---|
| MinIO | 2G/节点 | 400M/节点（demo 数据量小；兼作 checkpoint） |
| SeaTunnel | — | **1536M/容器，每机 1** |
| 其余 | 不变 | 不变 |

**SeaTunnel 按双 JVM 核算（问题记录 A1/二.4）**：容器内实际跑两个 JVM——常驻引擎（heap 192M）+ 每次提交/savepoint 的客户端 JVM（各约 200~300M）。按"引擎堆 192M"做的 768M 预算只覆盖引擎，客户端一启动即触发 cgroup OOM（exit 137 / SIGKILL，dmesg 可见 Memory cgroup out of memory），故上调至 1536M。

**核算模型**：内存预算必须按「常驻进程 + 所有配套瞬态进程之和」核算，不能只算主进程堆；若以"每 job 一个提交进程"方式运营，还需按并发提交数放大。

## 5. 部署阶段（A → F）

- **A 治理接入**：六服务 + dcp-worker 接 Nacos discovery/config；直连 URL 改服务名；公共配置外迁 Nacos Config；Nacos Gateway lb:// 路由；TaskScheduler 下发改 Nacos 实例轮询；本地 compose 回归。
- **B 网络**：三机 WireGuard 组网、防火墙放行、跨云连通性验证。
- **C 中间件**：TiKV/PD/etcd/Kafka/Redis/Sentinel/MinIO/Nacos 集群启动与健康检查。
- **D 数据面**：TiDB server/TiCDC/demo TiDB/**SeaTunnel 集群**（S3 checkpoint 验证）。
- **E 服务**：应用服务接入注册中心、网关路由生效、直连调用改服务名回归。
- **F 演练**：H1-H16 全场景。

## 6. HA 演练手册（H1-H16）

| 场景 | 操作 | 预期与验收 |
|---|---|---|
| H1 控制面宕机 | kill 某服务单实例 | 请求经注册中心转到存活实例；前端功能不中断 |
| H2 ShedLock 接管 | kill 持有锁的定时任务实例 | 存活实例在锁到期后接管，无重复执行（域级锁） |
| H3 Kafka broker 宕机 | kill 1/3 broker | 生产者重试、消费者组 rebalance，同步链路不丢消息 |
| H4 TiKV 宕机 | kill 1/3 TiKV | PD 调度副本补齐，TiDB 读写不中断 |
| H5 PD 宕机 | kill 1/3 PD | 集群自动选主，无脑裂 |
| H6 元库主从 | RDS 重启 + 从库追平 | 服务重连成功；从库 binlog 位点追平无差异 |
| H7 etcd 宕机 | kill 1/3 etcd | 选主迁移（5s 超时），dcp-worker 注册/租约不中断 |
| H8 rebalance | 扩缩 worker 实例 | 消费组平滑 rebalance，无重复无丢失 |
| H9 整台云机关机 | 关腾讯云整机 | 其上全部组件漂移/重建于余下两机；恢复后数据追平 |
| H10 补偿闭环 | 制造 activate 失败/交接中断 | handover-pending 判据触发补偿，任务恢复或转出 |
| H11 源库断点续传 | 杀源库 10 分钟 | TiCDC 与 SeaTunnel 均从位点续采，无全量重发 |
| H12 Nacos 宕机 | kill 1/3 Nacos | 服务发现/配置不中断（本地缓存 + 选主） |
| H13 调度框架判死迁移 | kill dcp-worker 实例 | TaskScheduler 判死 → TaskSpec 迁移到存活实例执行 |
| **H14 Zeta 主节点宕机** | kill SeaTunnel 集群主节点 | Hazelcast 自动选新主；已实证：master 宕机后 RUNNING job 从列表消失、不自动恢复，需显式 savepoint + restore（问题记录二.1）→ 控制面已加巡检自动 restore（待办1） |
| **H15 任务节点宕机** | kill 执行采集任务的非主节点 | 任务迁第三节点；验证 S3 checkpoint 生效（停 10 分钟重启不丢状态）；断点续采 + seq 确定性（重放复现原号） |
| **H16 提交入口切换** | 依次打 3 节点提交（经 LB） | 任意节点宕机不影响新任务提交与存量任务 |
| **H17 全量重发演练** | 删 checkpoint（模拟位点丢失）后 initial 重启 | 值变行重建、值同行静默（0 事件）、全量完成后流衔接无缝（增量接续不重不漏）、seq 单调不回退 |

**成功标准**：17 场景全部通过，且数据最终一致。

> H17 依据「路径1-位点即序号与全程正确写入-设计方案」：全量重发只重建"值变行"，值同行静默（0 行）；全量重发后增量从新起点 S′ 截流衔接。

## 7. 数据流链路（演练覆盖路径）

demo 源库（TiDB/MySQL/PG）→ SeaTunnel CDC 采集（3 节点 Zeta，位点透传 + cdc-seq 发号）→ 平台 Kafka → dcp-worker 消费底座（etcd 调度）→ 目标库（TiDB）+ 出口（outlet-service）→ 订阅推送。TiCDC 采集 demo TiDB 并行一路，验证双采集面。
