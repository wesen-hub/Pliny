# Kafka 双栈部署模型与参数配置

> 定稿日期:2026-10-08。本文档承载 Kafka 平台栈/出口栈的部署模型、物理隔离原则与关键参数配置,配套文档:[正式上线部署方案.md](正式上线部署方案.md)(§3.3 平台栈、§3.5 出口栈、§4 物理机装箱、§7.1 压缩待办)。

## 1. 部署模型总览

```
平台栈(批同步链路,分钟级可接受)          出口栈(CDC 实时流,秒级敏感)
┌─────────────────────────────┐         ┌─────────────────────────────┐
│ 3 broker,1 机 1 broker      │         │ 6 broker,1 机 2 broker ×3 台 │
│ 32C/128G,25GbE,NVMe ~15.6TB │         │ 32C/128G,25GbE,NVMe 23TB     │
│ 200 分区(100 逻辑表),RF3,minISR=2  │         │ 128 分区,RF3,minISR=2        │
│ 短保留 48h                  │         │ 7 天保留(下游回溯)            │
│ 窗口期积压 1.25TB×RF3/台    │         │ 53TB 总量,盘水位 38%          │
└──────────────┬──────────────┘         └──────────────┬──────────────┘
   SeaTunnel 50 万条/s 全量灌入             TiCDC 25 万条/s 实时输出
   → 同步链路 17 实例消费 → TiDB            → 消费底座 15 实例(6 ns 分池)
```

| 维度 | 平台栈 | 出口栈 |
|---|---|---|
| 职责 | 源库 → Kafka → 同步链路 → TiDB 的批同步主链路 | TiDB → TiCDC → Kafka → 下游消费任务(打标/湖增量/订阅推送) |
| 连接方 | sync/ingest ns | indexer/outlet/tag/lake/sub ns |
| 流量形态 | 全量窗口突发 500MB/s 未压缩(压缩后 125MB/s) | 稳态 25 万条/s = 10.4MB/s/台 |
| 数据生命周期 | ~14.8h(窗口期积压 + 追平段消化) | 7 天回溯窗口 |

## 2. 物理隔离五原则(必须,逐条论证)

双栈物理隔离不是「风格偏好」,是五条必须满足的硬性原则。每条给出「不隔离的后果」与「本项目落点」。

### 原则一:延迟敏感度隔离

**内容**:出口栈承载 CDC 实时流,秒级敏感——下游打标、订阅推送对 lag 的容忍是秒级;平台栈承载批同步,全量窗口期是「50 万条/s 灌入 + 25 万条/s 消费」的突发大流量,分钟级可接受。

**不隔离的后果**:批任务的 IO 尖峰(全量段每台 broker 41.7MB/s 写 + RF3 复制出 83.4MB/s + 落盘压缩)与 CDC 流共享磁盘/网络/broker 进程时,批风暴会周期性把 CDC 消费 lag 拖到分钟级甚至小时级——下游打标与实时订阅的业务 SLA 直接崩塌。批流两类负载的峰值时间片重叠时,底层资源争抢无法靠「topic 隔离」消除。

**本项目落点**:两栈各自独立 broker 进程、独立物理机、独立磁盘——批风暴最猛的时刻,出口栈 broker 的 IO/网络/CPU 水位纹丝不动。

### 原则二:故障域隔离

**内容**:一栈的故障(磁盘打满、broker 重启、误删 topic、参数改错)不允许传染另一栈,影响面必须封在栈内。

**不隔离的后果**:共集群时,平台栈窗口期磁盘被 50 亿条积压打满(这是设计内的高水位),会直接把出口栈的写入拒掉——CDC 实时流因为「隔壁批任务的数据太胖」而停写,两个故障域合成一个,排障时也无法区分「批任务的锅」和「实时流的锅」。

**本项目落点**:一栈抖动不传染主路径;平台栈 broker 磁盘打满时,出口栈照常写入,反之亦然。

### 原则三:容量规划独立

**内容**:出口栈按 CDC 吞吐线性扩(定案 6 broker,历史口径 6-9);平台栈按批峰值 + 积压扩(定案 3 broker)。两栈的扩容触发器完全不同,互不牵扯。

**不隔离的后果**:共集群时必须取「两栈需求的并集」做统一扩容——平台栈因积压要加盘,出口栈被迫跟着买盘;出口栈因 CDC 吞吐要加 broker,平台栈的分区被迫跟着迁移。扩容决策被绑死,任何一侧的演进都要付另一侧的钱。

**本项目落点**:平台栈扩容触发器 = 吞吐 50 万→100 万条/s、或积压 50 亿→150 亿条、或分区 200→2000+;出口栈扩容触发器 = TiCDC 输出吞吐增长、7 天存储水位逼近 70%。两边独立决策。

### 原则四:保留策略独立

**内容**:出口栈 7 天保留(下游任务回溯重启的数据基础);平台栈短保留 48h(积压生命周期 14.8h × 3 倍余量)。保留时间决定磁盘容量水位,必须各自独立。

**不隔离的后果**:共集群时保留策略要么取最大公约数(平台栈陪着存 7 天,磁盘成本 ×3.5),要么取最小(出口栈只留 48h,下游回溯窗口塌缩);共享磁盘的容量互相挤压——平台栈窗口期积压吃掉的盘位,就是出口栈 7 天回溯数据被挤掉的空间。

**本项目落点**:平台栈 48h 保留(1.25TB×RF3,盘水位 8%);出口栈 7 天(53TB,盘水位 38%)。互不挤压。

### 原则五:集群模式 ≠ 隔离(面试口径)

**内容**:「单集群多 topic」只解决管理问题(一套集群统一运维),不解决底层 IO/网络争抢;双栈买的是故障域与容量规划的独立性,不是「topic 分开」的形式。

**不隔离的后果**:同一 broker 进程内,topic 的磁盘 IO、page cache 抢占、网络队列、复制线程全部共享——逻辑隔离掩盖物理争抢,批流混部在压测与故障复盘时无法归因,是「看起来省了集群、实际赔了 SLA」的典型陷阱。

**本项目落点**:双栈物理隔离是定案,最小集群验证环境(3 台云机)可临时合并为一个 3-broker 集群、用 topic 前缀区分业务域,但生产正式上线必须物理分离。

## 3. 设计原则七定案

| # | 原则 | 结论 |
|---|---|---|
| 1 | broker 数由 RF3 下限 + 故障域决定,吞吐从不参与 | 平台栈 3 = RF3 理论最小;吞吐水位 25%,冗余 4 倍是「白送的」 |
| 2 | 宕机容忍度由 RF 决定,不由 broker 数决定 | RF3 只能容忍 1 台宕;加 broker 只降「受影响分区比例」(1/3→1/5),ROI 低 |
| 3 | 积压容量是平台栈硬约束 | 50 亿条 × 1KB ÷ lz4 3:1 ≈ 1.25TB × RF3,每台 8% 水位;磁盘满=死,CPU 满只是慢 |
| 4 | 故障域分档:生命线数据 1 机 1 broker,可重放数据 1 机 2 broker | 平台栈积压「重拉全量要 5.56h」→ 1 机 1 broker;出口栈可由 TiCDC 重放 → 1 机 2 broker |
| 5 | 分区数 = 逻辑表粒度分级 × 2 的幂 | 平台栈 100 逻辑表一表一 topic:10 超大表×8 + 30 大表×2 + 60 小表×1 = 200 总分区(每表分区数 = 表峰值速率 ÷ 单分区能力线 2000 条/s 向上取 2 的幂);出口栈 128 = 底座 15 实例 × 8~9 |
| 6 | 压缩在 producer 端,broker 不解压 | broker 原样落盘 + 零拷贝转发,解压成本推给 consumer;省网络省盘,broker CPU 零负担 |
| 7 | 消费组退位为「位点存储键」,不做 rebalance | 调度内核显式 assign 分区,分区归属由选主调度器唯一决策(避免 rebalance 风暴) |

补充论证(与原则相关的三个关键结论):

- **单 broker 吞吐 20 万条/s 完全可行**:CPU 9.5 核(30% 水位)、网络 850MB/s(25GbE 27%)、磁盘 132MB/s(NVMe 7%)。broker 数之所以不按吞吐买,是因为 RF3 下限、积压容量、故障域三个约束在「3」这个数字上恰好同时满足。
- **压缩后的计量口径**:网络/磁盘/复制流量按压缩后 MB/s 记账(平台栈总网络 125MB/s);broker CPU 按 QPS + 每核能力线(2.1 万条/s/核)记账——压缩只减字节账本,不减条数账本,两个账本各自独立、互不换算。
- **broker 端不解压消息体**:只解析批次头(CRC/offset/幂等),消息体原样落盘、零拷贝转发;解压成本完整转移到 consumer 端,broker CPU 对消息条数钝感、对字节量与批次数敏感。

## 4. 参数配置

### 4.1 broker 端(server.properties 关键项)

| 参数 | 平台栈 | 出口栈 | 理由 |
|---|---|---|---|
| `broker.id` / `listeners` | 0-2 / PLAINTEXT://:9092 | 0-5 / :9093 | 自建机房内网直连,专网内无需 SSL |
| `log.dirs` | NVMe XFS 单独挂载 | 同左 | XFS 顺序写最优;与系统盘分离 |
| `auto.create.topics.enable` | **false** | **false** | 禁止误写自动建 topic |
| `default.replication.factor` | 3 | 3 | 显式创建时写死,双保险 |
| `min.insync.replicas` | **2** | **2** | 核心一致性参数:ISR 不足 2 拒写,配合 acks=all 实现「已 ack 不丢」 |
| `unclean.leader.election.enable` | **false** | **false** | 宁停写不丢数据:禁止从非 ISR 副本选主(会截断数据) |
| `compression.type` | producer | producer | 保留 producer 压缩态,不重压缩 |
| `log.retention.hours` | **48** | **168**(7 天) | 平台栈 14.8h 生命周期 × 3 余量;出口栈 7 天回溯 |
| `log.segment.bytes` | 1GB | 1GB | 段文件大小,影响清理粒度 |
| `num.network.threads` / `num.io.threads` | 8 / 16 | 8 / 16 | 网络线程与磁盘 IO 线程分离,32C 合理切分 |
| `replica.fetch.max.bytes` | 10MB | 10MB | 复制拉取批量上限(1MB 批 × 10) |
| JVM | **-Xmx8G -Xms8G,G1GC** | 同左 | heap 只做请求队列/索引缓存,112G 留给 page cache |

**集群模式**:KRaft(3.3+ GA,去掉 ZK 依赖)。⚠ 三机跨公网环境教训:WG MTU 偏小 + 跨网抖动导致 controller 反复切换、已 ack 消息被 leader epoch bump 截断;治理参数 `quorum.fetch.timeout.ms` 调大。生产同机房专网不受此影响,但该参数作为治理项留档。

**OS 层**:`vm.swappiness=1`(page cache 不换出)、文件描述符 ulimit 100 万、XFS 挂载 `noatime`。

**内存分工**:物理 128G = JVM heap 8G + OS page cache ~112G。Kafka 性能核心是「读写命中 page cache」,不是 heap;平台栈追平段顺序追读靠 LRU + readahead 覆盖尾部热点,增量段 8.3MB/s 写全程命中。

### 4.2 topic 级

| 参数 | 平台栈 | 出口栈 |
|---|---|---|
| 分区数 | 200(100 逻辑表分级:10×8+30×2+60×1,创建时显式指定) | 128 |
| 副本分配 | 机架感知:broker.rack 按物理机划分,3 副本强制跨 3 机 | 同左(1 机 2 broker 场景副本禁止同机) |
| 保留 | 48h(覆盖积压生命周期 + 故障重放窗口) | 7 天 |

分区只增不减,创建即终态——分区数必须在设计期算准(表峰值速率 ÷ 单分区能力线 2000 条/s,向上取 2 的幂)。

### 4.3 producer 端(SeaTunnel → 平台栈)

| 参数 | 值 | 理由 |
|---|---|---|
| `compression.type` | **lz4**(⚠ 代码待办,见正式上线部署方案 §7.1) | 3:1 压缩比,CPU 代价最小;zstd 多压 1:1 但吃 worker CPU(全量段已 70% 水位) |
| `linger.ms` | 5 | 攒批等待,5ms 换来 1MB 大批 |
| `batch.size` | 1048576(1MB) | 全量段每批 1000 条,批越大 broker 端 batch header 摊薄越狠 |
| `acks` | **all** | 与 minISR=2 联动:leader + 1 follower 确认才算成功 |
| `enable.idempotence` | true | 幂等重试,配 acks=all 使用 |
| `max.in.flight.requests` | 5 | 幂等开启后允许并发 5 个在途请求 |
| `buffer.memory` | 64MB | 攒批缓冲,窗口期 500MB/s 突发不阻塞采集 |

落地写法(SeaTunnel Kafka sink 的 kafka.config 透传):

```java
sink.put("kafka.config", Map.of(
    "compression.type", "lz4",
    "linger.ms", "5",
    "batch.size", "1048576"
));
```

broker 端无需改(默认 compression.type=producer 原样保存)。

### 4.4 consumer 端(同步链路 / 消费底座)

| 参数 | 值 | 理由 |
|---|---|---|
| 分区分配 | **显式 assign,不用 subscribe** | 调度内核唯一决策分区归属,组只当位点键,杜绝 rebalance 风暴 |
| `enable.auto.commit` | **false** | 手动提交;同步链路 offset 提交与业务写同线程(commitSync),防位点跳跃 |
| `fetch.min.bytes` / `fetch.max.wait.ms` | 1MB / 500ms | 拉取攒批:要么攒够 1MB 要么等 500ms,减少空轮询 |
| `max.partition.fetch.bytes` | 10MB | 单分区单次拉取上限 |
| `max.poll.records` | 500(与攒批对齐) | 每次 poll 500 条 = 1 个写入批的量 |
| 解压 | 客户端自动 lz4 解压 | 解压 CPU 落在消费者进程,已计入同步链路实例 8C 能力线 |

## 5. 两栈差异化对照

| 维度 | 平台栈 | 出口栈 | 差异根因 |
|---|---|---|---|
| broker | 3(1 机 1) | 6(1 机 2) | 积压是生命线 vs 可重放 |
| 分区 | 200(100 表分级) | 128 | 表粒度分级 vs 底座并行度 |
| 保留 | 48h | 7 天 | 数据生命周期 14.8h vs 下游回溯需求 |
| 写压力 | 全量段 41.7MB/s/台(突发) | 10.4MB/s/台(稳态) | 批峰值 vs CDC 恒流 |
| 故障容忍 | 1 台宕,积压 1/3 短时不可读 | 1 台宕(丢 2/6 副本),仍可写 | minISR=2 双栈一致 |
| 扩容触发器 | 吞吐翻倍 / 积压加厚 / 分区暴涨 | CDC 吞吐增长 / 存储水位 70% | 容量规划独立(原则三) |

## 6. 部署遗留待办

1. **lz4 压缩代码落地**:`CdcStService.buildFamilyJobConfig` 的 Kafka sink 增加 kafka.config 透传(compression.type=lz4 + linger.ms=5 + batch.size=1MB),当前代码 compression.type=none,规划中的「压缩后 125MB/s」在配置落地前不成立;
2. **broker.rack 机架感知**:副本分配脚本必须按「物理机」粒度写,防 1 机 2 broker 场景同机副本;
3. **告警三件套**:broker CPU 水位(偏紧点之一,>70% 错峰)、平台栈积压容量水位(8% 起步,>60% 告警)、ISR 收缩(<2 即拒写,秒级告警);
4. **KRaft 治理项**:`quorum.fetch.timeout.ms` 调优留档生产模板(三机跨网教训,生产同机房防御性配置);
5. **最小集群验证口径**:三机开发环境可双栈合并为一个 3-broker 集群(topic 前缀区分),但生产正式上线必须物理分离(原则五)。
