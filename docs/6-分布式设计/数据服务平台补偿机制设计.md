# 数据服务平台 · 补偿机制设计

> 全平台横切可靠性设计：补偿点如何选、补偿如何执行、互斥如何保证、为什么这么设计。
> 适用于：消费底座（湖/订阅/打标/入站四域）、同步链路、模型→topic 链路等全部服务间状态同步场景。

---

## 一、问题域与设计目标

### 1.1 四类问题

| # | 问题 | 触发场景 | 失败后果 |
|---|---|---|---|
| P1 | 长生命周期状态一致性 | 任务从业务登记到框架托管，跨多服务多阶段 | 某阶段失败后状态卡死，无法推进 |
| P2 | HTTP 单请求不可靠 | 业务服务 → 控制面 → 框架下发，均为 HTTP | 调用方无法区分"执行失败"与"响应丢失" |
| P3 | 集群部署并发 | 多实例同时对同一任务补偿 | 重复补发、日志噪音、无效竞争 |
| P4 | 补偿误判 | 无法区分"正常执行中（慢）"与"已死（失败）" | 对正在执行的任务误补发 |

### 1.2 设计目标

- **最终一致**：所有失败最终被收敛到目标态，无需精确恢复
- **可安全重放**：任何补偿动作可重复执行，结果收敛（幂等）
- **自动收敛**：可自动判定的差异自动修复；需人工决策的（不猜起点）只告警
- **可审计**：补偿失败留下告警与日志证据，不静默

## 二、设计总纲：状态同步域 vs 事件流域

### 2.1 本质二分

| 维度 | 状态同步域（对账 tick） | 事件流域（Kafka） |
|---|---|---|
| 判据 | 目标态可判定（应有 vs 实际） | 事件本身不可物化 |
| 时效 | 分钟级容忍（≥对账周期） | 秒级甚至毫秒级 |
| 频率 | 低频（任务生命周期变更） | 高频（逐行数据变更） |
| 一致性 | 最终一致 | 保序/准实时 |
| 失败恢复 | 重扫即重试，无失败记录 | 位点/offset 重放 |
| 代表场景 | 任务创建/激活/停止/删除 | TiCDC 行变更、事件投递 |

### 2.2 定论

1. **任务生命周期管理完全落在状态同步域**：目标态落库即声明，对账 tick 是唯一推进机制（双向判据），重放动作按安全性分自动/人工。
2. **对账永远是最后一道网**：它解决"收敛"，不解决"通知"。Kafka 解决通知（时效/吞吐/解耦），若场景对时效无要求，Kafka 的增量价值为零——此时直接用 tick 对账即可，无需 Kafka。
3. **生命周期中若出现事件型节点（如批完成），先物化成状态（batch_job 终态行）再归入对账域**。

### 2.3 Kafka 使用条件（仅当同时满足才引入）

- 事件不可物化、或物化成本高于消息本身
- 时效要求严于对账周期（秒级）
- 高频、多消费者、需保序
- 且：Kafka 投递失败仍由 tick 对账兜底（发 Kafka 本身需要对账，则直接用对账）

## 三、补偿点设计

### 3.1 插点维度（七维度框架）

| 维度 | 含义 | 设点理由 |
|---|---|---|
| **D1 耗时** | 阶段耗时远大于巡检周期 | 时间窗口大 = 失败概率高；需要租约判活 |
| **D2 所有权移交** | 状态推进者发生变化的边界 | 前组件已退出、后组件未接手，中间是丢失窗口，移交事实必须物化 |
| **D3 重放成本** | 阶段内是否支持断点续做 | 不可续做且重放代价高 → 阶段边界必设点 |
| **D4 自动/人工分界** | 重放能否安全自动执行 | 需人工决策（不猜起点）的动作设点并标记"人工" |
| D5 数据完整性风险 | 失败导致丢数/重数 | 衔接点必须可精确重放 |
| D6 外部副作用 | 写湖/推送等对外动作 | 以确认点（offset 提交）为补偿边界 |
| D7 扫描频率分级 | 疑似失败频率自适应 | 可选优化：宽限期内低频、疑似失败高频 |

### 3.2 两条插点原则

1. **物化输入事实，不物化可重算输出**：handover 的起点（输出）可幂等重算（栅栏索引纯查询），不物化；handover 的输入 t0（批完成时刻）算不出来，必须物化。**能重算的不存，算不出来的才落库**——这是控制补偿点数量的核心原则。
2. **补偿点 = 移交点 ∪ 耗时段边界 ∪ 人工决策点**：其余中间步骤被相邻点覆盖或幂等重放，不为"完整"而过度插点。

### 3.3 全链路补偿点清单（消费底座，湖域为例）

```
业务任务创建
  ├─ CP0 登记目标态 ── 业务在 ∧ consumer_task 缺 → 补 CREATE（宽限期, 自动）
  ├─ consumer_task 落库(STOPPED)
  ├─ CP1 激活目标态 ── running ∧ 框架无 spec → 重放 onCreated（宽限期, 自动）
  ├─ snapshot 分叉: submitBatching(BATCHING)
  │    ├─ CP2a 批判活 ── 未终态 ∧ 心跳超租约 → 判死 → 重做批（租约, 自动接管）
  │    ├─ CP2b 批终态 ── 终态(含t0) ∧ 未 handover → 补 handover（目标态, 自动）
  │    └─ CP2c 批失败 ── batch-failed 事件键 → 人工重做批换新 T0（人工, 不猜起点）
  ├─ handover → activate → 框架托管(etcd)
  ├─ 【不设点】执行段 ── Kafka offset + 框架自治 + DLQ 已闭环
  ├─ CP3 停止目标态 ── stopped ∧ 框架 spec 在 → 补 cancelTask（自动）
  └─ CP4 删除目标态 ── 业务已删 ∧ consumer_task 在 → 补注销（自动）
```

每个点的完整规格：

| 补偿点 | 判活手段 | 判据 | 补偿动作 | 自动/人工 | 幂等保障 |
|---|---|---|---|---|---|
| CP0 登记 | 宽限期 2-5min | 业务在 ∧ 底座缺 | 补 CREATE（五步登记） | 自动 | exists 短路 + task_id 唯一约束 |
| CP1 激活 | 宽限期 | running ∧ 框架无 spec | 重放 onCreated | 自动 | etcd put 覆盖 + hasTask 收敛分支 |
| CP2a 批判活 | 租约/心跳 | 未终态 ∧ 心跳超时 | 接管重做批 | 自动接管 | 批任务幂等（换新 T0） |
| CP2b 批终态 | 目标态 | 终态 ∧ 未 handover | 补 handover(t0) | 自动 | 起点幂等重算 + put 覆盖 |
| CP2c 批失败 | 事件键 | batch-failed 存在 | 人工重做批 | **人工** | 事件键标记 |
| CP3 停止 | 目标态 | stopped ∧ spec 在 | 补 cancelTask | 自动 | deleteSpec 幂等 |
| CP4 删除 | 目标态 | 业务删 ∧ 底座在 | 补注销 | 自动 | 同上 |

### 3.4 模型→topic 链路补偿点（sync 域）

| 补偿点 | 判据 | 动作 | 自动/人工 |
|---|---|---|---|
| CP-M1 topic | logical_table 在 ∧ topic 缺 | 补建 topic（含 dcp.in.* 入站 topic） | 自动 |
| CP-M2 spec | logical_table 在 ∧ 框架 spec 缺 | 补 submitSyncTask | 自动 |
| CP-M3 删除 | logical_table 删 ∧ spec 在 | 补 cancelSyncTask | 自动 |
| 半成品恢复 | model_definition 在 ∧ logical_table 缺 | create 续跑 ②③④ | 自动（重试即续跑） |

### 3.5 为什么不设点（负向清单）

| 区域 | 理由 |
|---|---|
| 执行段（消费稳态） | Kafka offset 即补偿点，框架自治 + 重试×5 + DLQ 已闭环，业务层再插点是越界重复建设 |
| 登记五步内部 | 秒级原子序列，全 INSERT IGNORE 幂等，整段由 CP0 一个点覆盖 |
| handover 输出（起点） | 可幂等重算，物化是冗余 |

### 3.6 为什么批阶段独占三个点

批阶段是全链路唯一同时命中 D1（耗时最长）+ D2（批执行体→调度器移交）+ D3（不可断点续做）+ D4（失败不能自动猜）+ D5（衔接丢数风险）五个维度的阶段，值得最高密度补偿保障。

## 四、补偿机制：对账 tick

### 4.1 判据是目标态差异，不是失败记录

> 对账扫的是"应有状态 vs 实际状态"的不一致，不是"失败的任务"。

理由：
- "找失败的"模式需要可靠失败记录——但"记录失败"这个动作本身也可能失败，失败记录还要清理，是无底洞
- 对账模式不需要失败记录：失败的效果就是目标态未达成，直接扫效果
- **判据本身就是重试队列**：某次补发失败？不记录。下轮扫描判据仍命中，自然再补

### 4.2 判活两档（区分"执行中"与"已死"）

| 机制 | 判活方式 | 适用阶段 | 本质 |
|---|---|---|---|
| 宽限期 | `create_time + 宽限 > now` 静态推断"还在执行中" | 短时段（秒级流程） | 无心跳的租约 |
| 心跳租约 | 执行体刷 heartbeat_at，超时判死 | 耗时段（批执行） | 有心跳的租约 |

宽限期参数：`reconcile-grace-seconds`（默认 180s），写在判据 SQL 的时间过滤里；心跳租约：批执行体每 30s 刷新 `batch_job.heartbeat_at`，判据为 `heartbeat_at + 租约超时 < now`。

### 4.3 一轮 tick 的完整执行逻辑

```java
@Scheduled(fixedDelay = 15000)
@SchedulerLock(name = "lakeTaskReconcile", lockAtMostFor = "2m", lockAtLeastFor = "5s")
public void reconcileBaseTasks() {
    // ① 扫描: 只读 SQL, 一次找出全部目标态差异(宽限期过滤在 SQL 里)
    List<Map> missingBase = metaJdbc.queryForList(
        "SELECT t.* FROM lake_sync_task t WHERE t.enabled = 1 "
      + "  AND t.create_time < NOW() - INTERVAL 180 SECOND"
      + "  AND NOT EXISTS (SELECT 1 FROM consumer_task c "
      + "      WHERE c.task_id = CONCAT('lake-inc-', t.logical_table))");
    List<Map> orphanBase = metaJdbc.queryForList(
        "SELECT c.task_id FROM consumer_task c WHERE c.namespace='lake' "
      + "  AND NOT EXISTS (SELECT 1 FROM lake_sync_task t "
      + "      WHERE CONCAT('lake-inc-', t.logical_table) = c.task_id)");
    // ② 挨个补发: 幂等动作, 每个独立 try-catch, 互不阻断
    for (Map row : missingBase) {
        try { lakeTaskDeployer.deploy(toTask(row)); }
        catch (Exception e) { log.warn("补发失败(下轮重试): {}", e.getMessage()); }
    }
    for (Map row : orphanBase) {
        try { lakeTaskDeployer.cancelBase(row.taskId); }
        catch (Exception e) { log.warn("注销失败(下轮重试): {}", e.getMessage()); }
    }
    // ③ 结束。什么都不删、什么都不记——已收敛的目标态下轮自然不再命中判据
}
```

### 4.4 重试规则

1. **扫描只读、补发幂等写，之间无事务**——扫描结果只是待办清单，丢了也无妨
2. **挨个补发、相互独立**——单个失败只影响自己，下轮判据再命中
3. **无失败队列、无失败计数表**——判据即队列
4. **顺序有依赖时按序扫**——CP0（创建）先于 CP1（激活），因 CP1 判据基于 consumer_task 存在
5. **固定 tick 间隔（15s），不做指数退避**——退避是高频事件重试场景的省资源手段；对账低频低负载，恒定间隔即可，退避反而增加恢复延迟方差
6. **升级**：连续 N 轮（约 5 分钟）判据持续命中 → 告警人工（"重试无效必有新故障"，如控制面整体挂掉）
7. **批失败（CP2c）不自动重试**——batch-failed 事件键命中即转告警，换新 T0 是人工决策

### 4.5 双向对账三方向

| 方向 | 判据 | 动作 |
|---|---|---|
| 创建 | 业务任务在 ∧ 底座缺 | 补 CREATE |
| 运行 | desiredState=running ∧ 框架无 spec | 重放 onCreated |
| 删除 | 业务任务删 ∧ 底座在 | 补 STOP/注销 |

## 五、互斥机制：ShedLock 域级锁

### 5.1 为什么是 ShedLock（不是 Redisson/etcd/ZK）

ShedLock 是分布式锁的数据库租约锁流派（MySQL 锁表 + lock_until）。选型理由：

1. **语义匹配**：定时任务互斥需要"抢不到跳过本轮 + 实例挂掉锁自动失效 + 注解零侵入"，正是 ShedLock 定制语义；通用锁（Redisson/etcd）默认"阻塞等待 + 显式 release + 可重入"，与 tick 场景错位
2. **零新组件**：锁表建在元库，四个服务（backend/subscription/tagengine/outlet）都有 metaJdbc，无 Redis 部署、无 etcd 客户端依赖（仅 backend 连 etcd）
3. **故障语义**：租约到期自动释放，实例崩溃不产生死锁——守护者不能比被守护者更脆弱
4. **项目定论**：backend 已落地（filesyncAutoTick/filesyncCleanOldRuns 在用），依赖/锁表/@EnableSchedulerLock 就位

### 5.2 互斥原理：一条原子 UPDATE 的 CAS

```sql
UPDATE shedlock
SET lock_until = :now + lockAtMostFor, locked_at = :now, locked_by = :本机标识
WHERE name = :锁名 AND lock_until <= :now
```

- 影响 1 行 → 抢到，进入方法体；影响 0 行 → 抢不到，**方法体整体跳过**（不阻塞、不排队）
- 原子性来源：InnoDB 行锁使两个实例的 UPDATE 串行执行，后执行者看到的 lock_until 已更新，WHERE 不成立——**MySQL 行锁天然提供 CAS 仲裁，零协调组件**

### 5.3 锁生命周期与正常轮时序

```
T=0.000  A、B 的 @Scheduled 同时到点, 各自抢锁
T=0.001  A: UPDATE 影响 1 行 → 抢到, lock_until = T+120s
T=0.003  B: WHERE lock_until<=now 不成立 → 影响 0 行 → 本轮跳过
T=0.050  A: 对账完成(50ms)
T=0.050  A: unlock → 持有 < lockAtLeastFor(5s) → lock_until 保持为 locked_at+5s = T+5s
T=15.00  下一轮: 锁已过期, A/B 再竞争, 谁先执行 UPDATE 谁抢到
```

- **lockAtLeastFor 真实作用**：unlock 不立即置空，而是把 lock_until 更新为 `locked_at + lockAtLeastFor`——防止背靠背（A 刚释放 B 立刻又跑一轮），是"对账频率下界"守护
- **lockAtMostFor 租约语义**：锁靠到期释放而非 unlock；崩溃时无人 unlock，锁自然到期

### 5.4 故障时序

**实例崩溃（主故障模式）**：A 抢到锁后 OOM → 无人 unlock → B 每轮抢锁失败 → 到 lockAtMostFor（2m）时锁到期 → B 接管。对账停摆上限 = lockAtMostFor，自愈无人工。

**方法超时（配置纪律由来）**：A 执行超过 lockAtMostFor → 锁过期 → B 抢到也进入 → 双执行。ShedLock 对此无能为力（租约锁固有代价），故 **lockAtMostFor 必须显著大于方法耗时上界**；且双执行的后果仍被幂等键收敛（结果正确、过程不干净）。

### 5.5 锁粒度：域级（为什么）

锁粒度 = 临界区粒度，判定标准：**锁粒度细到临界区开销之下就是负优化**。

- 临界区（一轮对账 = N 行扫描 + M 个补发）毫秒-秒级 >> 锁开销（一次 DB UPDATE 毫秒级）→ 域级一把锁
- 每任务一把锁：锁表随任务膨胀、逐任务抢锁往返、锁表成热点——收益为零
- 每补偿点一把锁：CP0-CP4 判据同轮一趟跑完，切开无收益
- 演进路径：任务数到万级、单实例一轮对账撑爆 tick 周期时 → 分片对账（hash(taskId)%N，每分片一把锁）；当前规模属过度设计

### 5.6 lockAtMostFor 确定方法（四步法）

1. 测临界区耗时**上界**（最坏情况：慢查询 + 接口慢 + 补发激增 → 约 10s）
2. 加安全系数：`lockAtMostFor = 上界 × 10~20` → 2m（系数大是因为超过它即双执行，必须绝对避免）
3. 校验三条约束链：
   - 防双执行：`lockAtMostFor >> 方法耗时上界`（2m >> 10s ✓）
   - 停摆预算：`lockAtMostFor ≤ 故障停摆容忍上限`（崩溃后停摆 ≤ 2m ✓）
   - 频率下界：`lockAtLeastFor < tick 间隔`（5s < 15s ✓）
4. lockAtLeastFor = 大于集群时钟漂移幅度（秒级）→ 5s

### 5.7 锁名规划

| 锁名 | 覆盖临界区 | 竞争实例 | 参数 | 状态 |
|---|---|---|---|---|
| `filesyncAutoTick` | 文件同步调度 tick | backend 全部实例 | 30s/10s | 已落地 |
| `filesyncCleanOldRuns` | run 归档清理 | backend 全部实例 | 30m/1m | 已落地 |
| `lakeAutoTick` | 湖域到期触发 | backend 全部实例 | 2m/5s | 已落地 |
| `lakeTaskReconcile` | 湖域底座对账(CP0/CP4) | backend 全部实例 | 2m/5s | 已落地 |
| `lakeOrphanRuns` | 湖批孤儿 run 收尾 | backend 全部实例 | 2m/5s | 已落地 |
| `syncModelReconcile` | sync 域模型/topic 对账(CP-M) | backend 全部实例 | 2m/5s | 已落地 |
| `outletSupervisorTick` | 底座任务巡检(CP1/CP3 自动修复) | outlet-service 实例 | 2m/5s | 已落地 |
| `subTaskReconcile` | 订阅域对账(CP0/CP4) | subscription 实例 | 2m/5s | 已落地 |
| `tagTaskReconcile` | 打标域对账(CP0/CP4) | tagengine 实例 | 2m/5s | 已落地 |

跨域锁行隔离（锁名不同 → 锁表不同行），域内互斥（同锁名 + 原子 UPDATE）。锁表 `shedlock` 在共享元库建一份，切勿各服务各建（= 锁空间分裂 = 互斥失效）。

### 5.8 工程注意点

1. **usingDbTime 已落地为显式配置**：四个服务的 LockProvider 全部显式 `JdbcTemplateLockProvider.Configuration.builder().withJdbcTemplate(...).usingDbTime()`，用 DB 时钟判到期，规避多实例应用时钟漂移误判（lockAtLeastFor=5s 仍保留防秒级漂移）
2. **多数据源陷阱**：outlet-service 存在两个 DataSource（元库/TiDB 只读）——LockProvider 必须显式用元库（`@Primary` 元库 bean 直接注入即可），切勿依赖隐式装配
3. **LockProvider 必须显式注册 bean**：ShedLock 5.16.0 无 Spring Boot 自动装配（`@EnableSchedulerLock` 找不到 LockProvider 启动即失败）——各服务均建 `ShedLockConfig` 注册；backend 曾缺此 bean（编译过、运行会挂），实施中已补
4. **ShedLock 只做空间互斥，不做判活**：抢到锁 ≠ 该补；该不该补由判活（宽限期/心跳）决定

## 六、可靠性四层体系（防重全景）

```
┌ 判活（该不该补?）  ── 宽限期(静态租约) ┐
│                   └─ 心跳租约(动态租约) │── 与互斥正交
├ 互斥（谁能补?）  ── ShedLock 域级锁(空间互斥, 串行化补偿动作)
├ 结果（补了会怎样?）─ 幂等键矩阵(重复补发收敛到同一目标态)
└ 兜底（全都不行?）── 巡检告警(人工介入)
```

四对并发关系与对应机制：

| 并发对 | 机制 | 说明 |
|---|---|---|
| 补偿 tick vs 补偿 tick | ShedLock | 同一时刻全集群唯一实例执行对账+补发 |
| 补偿 tick vs 正常流程 | 判活（宽限期/心跳） | ShedLock 管不了正常请求线程，靠时间窗隔离 |
| 先后重放（A 补完 B 下轮再补） | 幂等键 | 互斥锁管不了时序，幂等收敛结果 |
| 全部机制失效 | 巡检告警 | 人工介入 |

## 八、落地实施方案（P0 四项）

### 8.1 batch_job 终态物化表（CP2a/CP2b 载体）

```sql
CREATE TABLE IF NOT EXISTS batch_job (
  task_id       VARCHAR(128) NOT NULL,          -- 底座任务 taskId(lake-inc-{表})
  state         VARCHAR(16)  NOT NULL,          -- PENDING/RUNNING/SUCCEEDED/FAILED
  t0            BIGINT       NULL,              -- 批完成时刻(交接输入, 算不出来必须物化)
  handover_at   TIMESTAMP(3) NULL,              -- 交接完成标记(CP2b 收敛依据: 补发成功即回写)
  heartbeat_at  TIMESTAMP(3) NULL,              -- 批执行体续约(每 30s 刷新)
  create_time   TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  update_time   TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (task_id)
) ENGINE=InnoDB COMMENT='底座批阶段终态物化(对账判据载体)';
```

### 8.2 各补偿点判据 SQL

```sql
-- CP0 创建方向(宽限期 180s 过滤 = 判活)
SELECT t.* FROM lake_sync_task t
WHERE t.enabled = 1 AND t.create_time < NOW() - INTERVAL 180 SECOND
  AND NOT EXISTS (SELECT 1 FROM consumer_task c
      WHERE c.task_id = CONCAT('lake-inc-', t.logical_table));

-- CP4 删除方向
SELECT c.task_id FROM consumer_task c WHERE c.namespace = 'lake'
  AND NOT EXISTS (SELECT 1 FROM lake_sync_task t
      WHERE CONCAT('lake-inc-', t.logical_table) = c.task_id);

-- CP1 运行方向(desired_state=running ∧ 框架无 spec; spec 判据经 worker.getSpec 查 etcd)
SELECT c.* FROM consumer_task c
WHERE c.desired_state = 'running' AND c.update_time < NOW() - INTERVAL 180 SECOND;

-- CP2a 批判活(心跳超时判死)
SELECT b.* FROM batch_job b
WHERE b.state IN ('PENDING','RUNNING')
  AND b.heartbeat_at < NOW() - INTERVAL 90 SECOND;   -- 租约超时(3 个心跳周期)

-- CP2b 批终态未交接
-- 收敛关键: handover 动作幂等但“已交接”是动作不是状态, 必须回写 handover_at 标记判据收敛;
-- 补发成功后 UPDATE batch_job SET handover_at = NOW() WHERE task_id = ?(否则判据永不收敛、每轮重复补发)
SELECT b.* FROM batch_job b
WHERE b.state = 'SUCCEEDED' AND b.t0 IS NOT NULL AND b.handover_at IS NULL;

-- CP-M1/M2/M3(sync 域; 复用 SchedulerRuntime.resubmitAll 逻辑周期化)
SELECT l.* FROM logical_table l
WHERE l.update_time < NOW() - INTERVAL 180 SECOND
  AND NOT EXISTS (worker spec 判据);                -- spec 缺失 → 补 submitSyncTask
```

**落地时对设计的三处修正**（实施口径）：

1. **宽限期落地分两式**：SQL 判据场景（CP0/CP4/CP-M）用 `update_time/create_time < NOW() - INTERVAL 180 SECOND` 过滤；无可靠时间字段的进程内场景（Supervisor CP1/CP3）用"首次发现时间戳 Map"实现同一语义——`pastGrace(map, taskId, now)` 首次发现记时间、超 180s 才动手
2. **CP4 判据必须带 `desired_state <> 'stopped'`**：否则 stop 动作（幂等 deleteSpec）后任务行仍残留，判据永不收敛、每轮重复补发
3. **孤儿 run 收尾只收 running 态**：`lake_sync_run.status='running' ∧ started_at < NOW()-30min → failed`，不碰 simulate 演练态 submitted 行

5. **handover-pending 判据复用 batch_job 行**（不新增表/事件键）：`state='SUCCEEDED' ∧ t0 非空 ∧ handover_at IS NULL` 即交接未落地态——activate 失败（批路径）与控制面中断共用同一判据；修复动作 = 读 t0 重放 activate（幂等 put 覆盖）+ 回写 handover_at 收敛
6. **activate 失败隔离在 onBatchDone 内**（不靠调用方 try-catch）：批回调链中 activate 异常若逃出回调会被 runner 外层 catch 二次 `done(0, false)` 归并批失败——必须在 onBatchDone 内 catch，仅留日志，判据留待巡检

## 九、设计决策记录（ADR）

| # | 决策 | 候选方案 | 选择理由 |
|---|---|---|---|
| ADR-1 | 生命周期用 tick 对账不用 Kafka | Kafka 事件通知 / tick 对账 | 目标态可判定 + 时效容忍 + 低频 → 状态同步域；对账是最后一道网；发 Kafka 仍需对账兜底则直接用对账 |
| ADR-2 | ShedLock 而非 Redisson/etcd | 四种分布式锁流派 | 定时任务语义匹配 + 元库零新组件 + 租约崩溃自愈 + 项目既有定论 |
| ADR-3 | 域级锁而非任务级/补偿点级 | 三粒度 | 锁粒度 = 临界区粒度；细分到临界区开销之下即负优化 |
| ADR-4 | 判据是目标态差异而非失败记录 | 失败记录表 / 目标态扫描 | 失败记录自身不可靠（记录动作也会失败）；判据即重试队列，零额外存储 |
| ADR-5 | 判活两档（宽限期 + 心跳租约） | 统一宽限期 / 统一心跳 | 短时段不值得养心跳（流程秒级）；耗时段时间推断误差不可接受 |
| ADR-6 | 批失败人工不自动重试 | 自动换新 T0 / 人工 | T0 不能猜（防漏/防重）；自动换起点有数据正确性风险 |
| ADR-7 | 物化输入不物化输出 | 全物化 / 全不物化 | 能重算的不存（起点），算不出来的才落库（t0）——控制补偿点数量 |
