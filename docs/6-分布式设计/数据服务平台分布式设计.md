# 数据服务平台分布式设计(PB 级 · 10万+ QPS)

> 状态:设计稿 v1(总纲 + 各缺口方案骨架,细节随讨论迭代)。
> 设计基准:**PB 级存量 + 10万+ qps 峰值吞吐**。
> 配套:统一调度框架(docs/5-统一调度框架/)、栅栏方案(docs/4-数据消费/批流衔接栅栏方案设计.md)、索引器分片(docs/3-索引器/索引器分片设计.md,路线已被框架分派取代,见 §2)。

## 〇、定位、口径与总纲

### 0.1 定位与核心问题

数据服务平台四个子系统——数据同步链路、数据消费底座、数据打标引擎、血缘与资产目录——目前是 demo 级部署(单实例容器)。本设计回答一个问题:**当平台撑到 PB 级存量、10万+ qps 吞吐时,每一层的水平扩展怎么做、单点在哪、用什么机制消除**。它承接两条既有线:一是 PB 级分布式方案缺口清单(缺实现 6 项 + 缺设计 8 项),二是 TB 级四大子系统部署架构(硬件规格与扩容公式)。

### 0.2 设计基准(量化口径)

| 指标 | 口径 | 推导 |
|---|---|---|
| 峰值吞吐 | 10万+ qps | 日均约 86.4 亿条事件 |
| 平均消息体积 | ~700B(CDC 信封:行数据 + 元数据) | 入口带宽 ~70 MB/s |
| 存量规模 | PB 级 | 目标库 + 湖累计(约 6 TB/天,数月达 PB 级) |
| 目标库写入 | 10万 qps(攒批后) | 单实例保守按 1.5万 qps 写估算 |

> 所有容量数字均为**初估口径,以压测实测校准**(落地路线 §六第 1 步)。

### 0.3 分布式管理总纲(做减法)

- 能用**确定性**(位点即序号)就不协调;
- 能用**单条 SQL 原子性**(唯一键)就不用分布式锁;
- 能用**无状态重建**就不做状态复制;
- 拒绝 Redis/ZK 外部强依赖(etcd 仅为调度框架底座,已内置于平台栈)。

## 一、已落地的分布式能力(现状盘点)

### 1.1 统一调度框架消化三大原缺口

原 PB 级缺口清单中的三个高优先级项,已被 dcp-scheduler 顺带解决:

| 原缺口 | 消化方式 |
|---|---|
| 控制面主备选举 | 每 ns 独立选主(etcd lease 竞选),MasterLoop 单主执行决策循环 |
| 巡检互斥 | 巡检(告警巡检/判死/再平衡)归入 MasterLoop,lease 保证唯一执行者,天然互斥 |
| 索引器分片(单线程 PB 击穿) | 分区为调度原子:indexer ns 45 分区每分区一执行器(AnchorSamplerExecutor,AGGRESSIVE + 全程幂等),分派/防双由框架归属键统一保证 |

### 1.2 缺实现 6 项落地确认

| 条目 | 状态 | 落点 |
|---|---|---|
| 控制面八大逻辑 | ✅ | MasterLoop 决策循环(分配/扩缩/判死/巡检/告警)+ outlet 控制面规划 |
| 计算面单元执行器 | ✅ | UnitTaskExecutor(outlet)/ AnchorSamplerExecutor(indexer)/ SyncWriterExecutor(sync) |
| 防双消费 | ✅ | etcd 归属键 CAS + 判死双确认 + 保守交接窗口;数据库唯一键兜底退位 |

| taint 持久化 | ✅ | chg_anchor_poison 表(INSERT IGNORE + 接管时查询恢复) |
| 索引器接线 | ✅ | indexer ns 45 分区端到端验证 |

## 三、分系统设计

### 3.1 采集段:SeaTunnel 多 worker 规划(⬜)

**现状。** compose 单 seatunnel 容器(8082 对外 + 5801/5802 debug 端口),所有 CDC 作业跑在单 worker 上;checkpoint 挂卷持久化("丢 = 全量重发"语义已在 compose 注释固化)。

**目标形态。** 多 worker 无状态集群 + 平台侧任务分派:

1. **worker 无状态**:作业配置(job-json)由平台组装下发,worker 只执行;任务可迁移(停旧启新,checkpoint 续跑);
2. **任务→worker 分派策略**:按"源库"维度分组(一个源库的作业族挂一个 worker,减小单点资源冲突),worker 间容量均衡;分派记录落平台元库,重启可恢复;
3. **源库单点资源约束**(设计关键):MySQL 每 worker 独立 server-id、PG 每 worker 独立复制槽、SQLServer CDC 实例级约束——**一个源库不能同时被多个 worker 重复采集**,分派必须保证"源库→worker 一对多只读、采集一对多禁止",与既有"独立 server-id 分配"机制衔接;
4. **checkpoint 存储**:共享卷或对象存储;丢 checkpoint 退化为全量重发(既有语义,幂等写入兜底);
5. **与发号的关系**:采集端领号(CdcSeqTransform)在 worker 进程内,多 worker 并发领号已由 seq_counter 行锁保证不重号(见 §3.3 量化),无需改造;
6. **容量初估**:10万 qps 入口 / 每 worker(16C/64G)约 2万 qps ≈ **5~6 worker 起步**,余量部署 8~10。

### 3.2 汇入段:目标库分片策略(🟡)

**现状。** 单实例目标库;logical_table 已固化:4096 固定桶(定死不可改)× 50 物理分表(定死不可改)+ bucket_map 桶→分区映射(JSON,扩容重算热更新)。业务键哈希定桶 → 同一业务键永远同一桶、同一分区。

**跨实例分库设计。** 桶模型天然支持两级映射扩展:

1. **两级路由**:`桶 → (分片实例, 物理表)`;路由键不变(业务键哈希),只把 bucket_map 的映射目标从"分区"升级为"实例+表";
2. **扩容**:新实例入池 → 部分桶迁移。迁移优先"**先新写后迁存量**"(新数据直接落新实例,存量批量搬移,读侧按桶号路由可容忍短暂双读);停写窗口迁移为兜底;
3. **与写者列裁判兼容**:裁判单位是(物理表, 行, 列),逐条判断、与实例无关——桶迁移后裁判语义不变,seq 只增不减保证跨实例重放检测仍成立;
4. **与 seq 的关系**:seq 区间预分配在元库(单点领号,见 §3.3),目标实例只消费已领号信封,不依赖全局时钟;
5. **两条选型路径**:
   - TiDB 路径:目标库自身分片(region 自动分裂),平台侧只维持桶→表映射,分片实例 = 逻辑实例;
   - MySQL 路径:应用层分片,桶→实例映射落元库,分片数 = 写吞吐 / 单实例能力(**10万 qps / 1.5万 ≈ 7 实例**,余量 8~10);
6. **容量初估**:单实例保守 1.5万 qps 写入(攒批多值 SQL + 单事务提交),瓶颈在磁盘 IO 与主键/唯一键维护。

### 3.3 发号器 HA 与 seq_counter 热点治理(🟡)

> ⚠️ 本节已过时(2026-10-06 标注):平台统一发号(seq_counter 号段)在设计上已废弃,正解为「位点即序号」(SeaTunnel 源码补丁透传源库位点、PositionSeq 编码;快照行用快照级号)。seq_counter 表仍存在,现实使用方为入站链路(kafka-ingest 按 appKey 分组领号)与灰度回退分支。本节仅作历史设计存档,后续规划/整理场景不再引用发号器概念。

**现状。** seq_counter 每逻辑表一行(cur = 已分配最大号),区间预分配 + 行锁保证并发不重号;持久化只增不减,重启不重号。logical_table 注册 topic/桶数/分表规则/bucket_map。

**热点量化(证明区间预分配已消化热点)。** 10万 qps 领号、区间长度 1000 → 每秒仅 **100 次单行 UPDATE**;MySQL 单行主键 UPDATE 上限约 1万 QPS(SSD),占用率 **1%**,无热点、无需分片治理。原"seq_counter 热点治理"缺口结论:**已由区间预分配解决,剩余工作是护栏而非重构**。

**发号器 HA。**
1. MySQL 半同步主从:领号走主库,切换窗口内从 max+1 续(区间只增不减 → 不重号,可能有空洞,seq 仅用于机制用途,空洞无害);
2. TiDB→MySQL 迁移路径:序号连续性由"区间预分配 + 只增不减"保证;迁移 = 新库从旧库 max+1 起分配,双写校验后切读;seq 语义跨库不变(seq 不裁决业务先后,只做路由/重放检测/写序标记);
3. **护栏**:区间长度(吞吐 vs 重启丢号窗口的权衡)、cur 水位监控(接近上限告警)、区间回收(弃号回收策略)。

### 3.4 消费段:outlet 规划面 HA(🟡)

**现状。** outlet-service 单实例,承担规划(UnitPlanner → FrameworkUnitSink 提交 TaskSpec)+ 索引器外壳 + 进度/告警读通道;调度主选举已由框架承担(WorkerSchedulerRuntime 参选,ns=outlet),但**规划面进程无备**。

**设计。**
1. **主备模型**:规划面进程主备——复用框架 etcd lease 竞选(平台栈内已有底座,不引入新组件),或元库选举表;备机只巡检不规划;
2. **规划幂等**(无状态重建的立足点):规划输入是登记流扫描(元库状态表),输出是 TaskSpec 提交——框架侧 taskId 唯一,重复提交幂等覆盖;扫描幂等(登记表状态机);
3. **接管**:主死 → 备接管 lease → 全量重扫登记流重建规划态 → 幂等提交,与存量 TaskSpec 对齐;
4. 规划面本身无状态,HA 成本低,重点是"扫描-提交"幂等闭环(已有基础,补状态机)。

### 3.5 治理段:Neo4j/Iceberg/Kafka 容量规划(⬜)

| 组件 | 量级估算(10万 qps 口径) | 预案 |
|---|---|---|
| Kafka | 入口 ~70 MB/s × 3 副本 × 保留 2 天 ≈ 36 TB | 6~9 broker(2×3.84TB NVMe,有效 ~6.5TB/台),25GbE;分区规划:CDC 主题分区数随吞吐,预留 bucket_map 扩容位 |
| Neo4j | 血缘存量节点:表 ~1万、字段 ~50万、作业/应用 ~千级 | 单节点起步 + 只读副本;采样率控制写放大(血缘采样器与索引器同源,已有稀疏采样) |
| Iceberg | 湖同步日增 ~86.4 亿条(≈6 TB/天) | 湖同步批作业(LakeSync)分区按小时/天;小文件 compaction 策略;Iceberg REST catalog 容量 |

### 3.6 打标引擎 TB 级形态(⬜)

三端(在线/流/批)的扩展形态:流端 Flink 按实体键分区已有;TB 级需定 Flink 集群规模、Spark 批端 executor 规划、在线端(进程内缓存求值)的实例化部署。此节依赖打标引擎自身演进节奏,列入路线末位。

## 六、落地路线与验证计划

优先级(按断点先后,承接原缺口排序):

1. **容量基线实测**:各环节单实例吞吐压测,校准 §四 全部初估数字;
2. **SeaTunnel 多 worker**(§3.1,采集段唯一完全空白,10万 qps 第一个断点):验证 = 多 worker 并发采集压测 + 领号不重号对账 + 任务迁移续跑;
3. **目标库分片**(§3.2,核心难点):验证 = 桶迁移期间写入不重不乱(写者列裁判对账)+ 扩容演练 + seq 重放检测回归;
4. **发号器 HA + seq_counter 护栏**(§3.3):验证 = 主从切换不重号(区间对账)+ 热点压测数字;
5. **outlet 规划面 HA**(§3.4):验证 = 杀主演练,接管后 TaskSpec 幂等对齐、无重复单元;
6. **治理段容量**(§3.5):Neo4j/Iceberg/Kafka 扩容预案与演练;
7. **打标引擎 TB 级**(§3.6):随引擎演进节奏推进。

**每项落地时遵守既有验证纪律**:内核纯函数离线断言(不碰 Kafka/库/框架)+ 真栈端到端 + 口径回放对账(ts 一致性)。

## 七、一句话收口

> 做减法的分布式设计:调度主备/巡检互斥/索引器分片由统一调度框架的"etcd 选主 + 分区原子"一次性消化,发号热点由区间预分配证明为伪热点(占用 1%),真正的新增战场只有三处——采集段多 worker(唯一空白)、目标库两级桶路由(分片实例化)、发号器 HA(半同步主从)——其余全是护栏、量化和预案。
