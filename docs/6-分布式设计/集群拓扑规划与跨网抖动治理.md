# 集群拓扑规划与跨网抖动治理方案

> 依据:2026-10-04 三机实测资源盘点 + 问题记录一.B3/B4 + 待办 10/新3。
> 目标:在「云机只放部署物、构建全在本地」的工艺约束下,给出集群拓扑收敛方案与跨网抖动处置建议,并列出需用户拍板的决策点。
> 澄清:所谓"云机弃用约束"实指**云机不再保留源码与构建环境**(镜像构建在本地 buildx 交叉编译后 scp 分发),并非弃用云机本身——云机仍是数据面主体。

## 1. 现状盘点(2026-10-04 实测)

| 机器 | 内存 | 实测 available | 在跑容器 | 备注 |
|---|---|---|---|---|
| Mac 10.66.0.1 | 16G(Docker Desktop VM 受限) | — | worker-1(仅此 1 个) | 数据面已事实停摆 2h+;kafka-1/backend-1/seatunnel-1 曾 exit 137(cgroup OOM) |
| 阿里云 10.66.0.2 | 8G | 1094M | 17 容器 | 近张力,难以再迁入新组件 |
| 腾讯云 10.66.0.3 | 8G | 2922M | 8 容器 | 已减负(停 backend-3/seatunnel-3/mysql-slave/deliv-2/tag-2/sentinel-3,释放 2.5G) |

**Mac 侧停摆容器**(exit 137/143/0,约 2h 前):kafka-1、tikv-1、pd-1、etcd-1、tidb-server、demo-tidb、seatunnel-1、sentinel-1、backend-1、asset-1、sub-1、tag-1、deliv-1、outlet-1、dcp-agent、dcp-outlet-worker-service、scheduler-console、perm-*(8 个)。

**集群当前实际形态(2 云机撑起 quorum)**:

- TiCDC(阿里)、SeaTunnel 引擎 1~2 节点(腾讯 seatunnel-3 减负已停,Mac seatunnel-1 已停)
- 业务影响:**TiDB server 与 demo-tidb 源库均在 Mac 且已停** → TiDB SQL 入口不可用、源库无新数据;唯一在跑的消费底座是 Mac worker-1

结论:quorum 存活 ≠ 业务可用。Mac 16G 已实证**无法承载完整数据面节点角色**(三个关键容器 exit 137),且 Mac 家宽链路是 B3/B4 抖动源头。

## 2. 待办 10:跨网抖动处置

### 2.1 根因回顾(问题记录一.B3/B4)

- **KRaft 抖动**:三机经 WireGuard 跨公网组 quorum,Mac utun7 mtu=1000 偏小;跨网 fetch 响应超时(KRaft 2s / replica fetch 30s)→ controller 反复切换 → leader epoch bump → 已 ack 消息被 log 截断。
- **Nacos 抖动**:gRPC 9848 长连接服务端检查 3s 超时 → 断连重连横跳 → 实例注册表状态漂移,gateway lb:// 命中心跳未刷新实例。

### 2.2 三个处置选项

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 参数调优保留跨网 | Kafka `quorum.fetch.timeout.ms` 2s→8s、election timeout 调大;WG MTU 1000→1400;Nacos gRPC 检查超时调大 | 改动小、不迁组件 | 跨公网本质不可控,调参只是放宽容忍度;Mac 内存不足无法稳定承载 broker,治标不治本 |
| B 拓扑收敛(推荐) | quorum 类中间件只落在两云机,Mac 退出数据面,只留 demo 源库 + 提交入口 + 前端 | 根治抖动(家宽退出 quorum);顺应现状(已事实停摆 2h);云间链路为骨干网,延迟稳定 | 2 副本 quorum 降级为"容忍 0 故障";TiDB server/demo-tidb 需重新安置 |
| C 全上云 + 增购第三台 | 恢复三副本,Mac 纯开发 | 恢复 HA | 成本;超出当前验证阶段 |

### 2.3 推荐:B(顺势收敛) + A 的 WG MTU 参数兜底

1. Mac 16G 已实证撑不起数据面(kafka-1/backend-1/seatunnel-1 全 exit 137),继续三机 quorum 是带病运行;
2. Mac 家宽是 B3/B4 抖动主因,退出 quorum 即消除主因,云间(KRaft 2s/Nacos 3s 超时)余量充足;
3. 两云机间走云厂商骨干网,延迟稳定可控;
4. WG MTU 仍建议提升(提交/开发流量也走 WG,MTU 1000 对大数据包分片损耗明显)。

## 3. 收敛后的目标拓扑

### 3.1 组件归属

| 组件 | 现状 | 收敛后 | 说明 |
|---|---|---|---|
| Kafka KRaft | 2/3 活 | 维持云机 2 副本(3 voter 中 1 永久离线,2/3 即多数派可写) | 调大 replica fetch 超时避免对离线 Mac broker 的长阻塞重试 |
| TiKV/PD/etcd | 2/3 活 | 维持 2 副本 | 同上,2/3 多数派 |
| TiDB server | Mac(已停) | 迁云(建议腾讯云,available 2922M 有余量) | 恢复 SQL 入口 |
| demo-tidb(演示源库) | Mac(已停) | 留在 Mac(常开禁休眠) | 源库在开发机便于造数;不经 quorum,家宽抖动无碍 |
| TiCDC | 阿里云 | 不动 | 连 PD/TiKV 读 changefeed,不依赖 TiDB server |
| SeaTunnel 引擎 | 1~2 节点 | 云机 2 节点(恢复腾讯 seatunnel-3 或保持单节点) | 单节点无 HA 但可提交;引擎节点不经 quorum,可随内存弹性 |
| 应用服务/worker | 3 机 | 云机各 2 实例为主,Mac 保留 worker-1 | 消费底座与 TiKV/Kafka 就近 |
| MinIO/Nacos/Redis/Sentinel | 现分布 | 不动 | 已全在云机(除 Mac sentinel-1 可停) |

### 3.2 内存规划(云机 8G 张力)

- 阿里云 available 1094M 近极限:**不再迁入任何组件**;候选腾挪——scheduler-console(若在阿里)、minio-2b/3(400M×2,冗余盘取舍)。
- 腾讯云 available 2922M:承接 TiDB server(数百 M)绰绰有余。
- Mac:裁剪后 Docker VM 只跑 demo-tidb + worker-1 + 前端类,内存无压力。

### 3.3 副本降级声明(重要取舍)

2 副本 quorum 形态下:**任一云机整机故障 → Kafka/TiKV/etcd/PD 不可写**(多数派不足)。这是开发验证环境的明确取舍;若要 HA,唯一出路是增购第三台机器(或引入更小规格的第三副本机)。

## 4. 决策点(2026-10-04 用户已拍板:方案 B 全按推荐)

1. **方案 B 拓扑收敛已批准**:Mac 数据面容器(kafka-1/tikv-1/pd-1/etcd-1/seatunnel-1/tidb-server/sentinel-1)正式下线不再重启。
2. **TiDB server / demo-tidb 安置已批准**:demo-tidb 留 Mac(需 Mac 常开禁休眠);TiDB server 迁腾讯云。
3. **2 副本 quorum 已接受**:明确接受"任一云机故障即不可写"的开发环境取舍,不增购第三台。

## 5. 执行清单(方案 B 获批后)

1. Mac:compose 裁剪为 demo-tidb + worker-1 + 前端/演示组件;停删 kafka-1/tikv-1/pd-1/etcd-1/seatunnel-1/sentinel-1(不动云机)。
2. 腾讯云:起 TiDB server 容器(host 网络连 PD),验证 `TIDB_CURRENT_TSO()` 正常。
3. Kafka:云机 broker 调 `replica.fetch.wait.max.ms`/fetch 超时,避免对离线 Mac broker 长阻塞;`kafka-metadata-quorum` 确认 2/3 voter 多数派健康。
4. WG MTU:Mac 侧 utun mtu 1000→1400(家宽 1500 − WG 开销)。
5. 验收:三机 worker 消费正常、sync ns lag=0 errorCount=0、引擎可提交且 checkpoint 落 MinIO、TiDB SQL 入口可用、`/api/sync/overview` 数据正常。
