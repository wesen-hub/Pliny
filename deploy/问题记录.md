# 最小集群部署问题记录

> 记录 2026-10 三机最小集群（Mac + 阿里云 + 腾讯云）部署与 H1-H16 演练全程踩过的问题。
> 分两部分：**通用型问题**（可迁移到其他项目/环境的部署运维坑）与**开发/设计阶段验证出的问题**（部署演练暴露的设计缺陷，需要开发侧跟进）。
> 每项按「现象 → 根因 → 修复 → 通用启示」展开。

---

## 一、通用型部署问题

### A. 容器与资源类

#### A1. 双 JVM 同容器触发 cgroup OOM（exit 137）

- **现象**：`seatunnel.sh -s`（savepoint）执行到一半客户端进程被杀，报 `SAVEPOINT_EXIT=137`（SIGKILL）；`dmesg` 显示 `Memory cgroup out of memory: Killed process (java)`。
- **根因**：SeaTunnel 容器内实际跑两个 JVM——常驻引擎（heap 192m）+ 每次提交/savepoint 的客户端 JVM（各自约 200-300m）。按"引擎堆 192m"做的 768m/1g 内存预算只覆盖了引擎，客户端一启动就超限，被 cgroup OOM killer 强杀。
- **修复**：三机 `mem_limit: 1536m`，重建容器。
- **通用启示**：容器内存预算必须按"常驻进程 + 所有配套进程之和"核算，不能只算主进程堆；exit 137 / SIGKILL 是容器 OOM 的典型症状（普通 JVM OOM 是 exit 1 且打 heap dump），第一时间用 `dmesg | grep -i oom` 确认。

#### A2. 精简 JRE 镜像缺调试工具，反编译链路迁移到宿主

- **现象**：需要在容器内反编译 `FactoryUtil.class` 验证 SPI 匹配逻辑，但容器是精简 JRE（无 `javap`、无 `unzip`）。
- **修复**：调试链路由容器迁到宿主——云机 python3 `zipfile` 从 jar 提取 class → base64 输出 → 本地 `base64 -D` 解码 → 本地 javap 反编译。
- **通用启示**：生产镜像精简与可调试性要平衡；"宿主提取 + base64 中转 + 本地反编译"是一条可复用的跨机反编译链路。

### B. 网络类

#### B1. Docker Desktop 容器访问宿主机 VPN 接口黑洞

- **现象**：Mac 容器内直连 `10.66.0.1`（WireGuard utun 接口）黑洞。Kafka 消费 job 的 partition leader 解析到 `mac.wg:9092`（Mac broker）后 AdminClient 超时 → checkpoint FAILED → pipeline CANCELING。
- **根因**：Docker Desktop 已知限制——容器流量经 VM（192.168.65.x）转发，回连宿主 utun 自连黑洞。
- **尝试与取舍**：
  - pfctl 把 VM 流量重定向回本机：可行但复杂、易与既有规则冲突；
  - 给 10.66.0.1 加回环优先路由（需 sudo、utun 接口名动态变化）；
  - **最终方案**：compose `extra_hosts: mac.wg:host-gateway`——容器内 `mac.wg` 解析到 VM 网关 192.168.65.254，经宿主端口映射到达 Kafka；云机侧 `/etc/hosts` 保持 `mac.wg=10.66.0.1` 不变。
- **通用启示**：开发机作为集群节点时，容器内访问"宿主机服务"必须走 `host-gateway`；域名（走 /etc/hosts 解析）与 IP 字面量在容器网络里行为不同，用域名间接寻址才能两侧一致。

#### B2. macOS WireGuard 组网坑合集

- `wg setconf` 报 Address 拒绝（接口已存在时先 flush 或换新接口）；lo0 主机路由与 wg 地址冲突；utun 接口名动态适配（utun0/utun7 变化）；组网后缺网段路由导致包根本不进隧道。
- **通用启示**：wg 组网验证清单固定四步——接口 up → 网段路由存在 → 对端 handshake 建立 → 双向实际 ping（协议层与 ICMP 分开验）。

#### B3. 三机 Kafka KRaft 跨公网抖动：controller 反复切换、已 ack 消息被截断

- **现象**：① broker 1（Mac）日志持续 `Disconnecting from node 3 due to request timeout`（fetch 30s 超时）；② 腾讯云 kafka-3 的 RaftManager fetch 对 node 1/2 均 2s 超时，controller 在 node 2/3 间反复切换，三节点互投拒绝票；③ 01:18 分区 `dcp.cdc_watchdog_src-0` 的 log 被重建（0 字节），01:20 sink 已成功写入的 row-h（已 ack、SinkWriteCount+1）事后从 log 中消失（被 leader epoch 变更截断）。
- **根因**：三机经 WireGuard 跨公网组 KRaft quorum，Mac utun7 mtu=1000 偏小，跨网大 fetch 响应易超时；TCP 层（nc 9092/9093）与 ping（75ms 0% 丢包）均正常，问题出在应用层超时（KRaft 2s / replica fetch 30s），网络抖动触发 quorum 动荡 → 分区 leader epoch bump → 本地 log 截断。
- **处置**：验证期间改用"插入后立即消费 + 全量 `--from-beginning` 对账"取证；producer 直连 broker 1 写入实测可用（probe 消息落盘可读）。
- **遗留**：调大 `quorum.fetch.timeout.ms` / election timeout、评估 WG MTU 提升，或 Kafka 集群拓扑整改（见待办 10）。

#### B4. Nacos gRPC 跨网抖动：服务注册心跳反复重连

- **现象**：业务冒烟侦察中 asset-2 日志持续 `Fail to connect server, after trying N times`，gRPC 连接在 10.66.0.2/10.66.0.3 之间反复横跳（3s TimeoutException 后重连成功），期间伴随实例注册 redo；nacos-2 容器多次重启。
- **根因**：与 B3 同源——跨公网 WireGuard 链路延迟波动，Nacos 2.x 的 gRPC 长连接（9848 端口）服务端检查 3s 超时即断连重连。
- **影响**：重连窗口内该实例在注册表里状态漂移，gateway `lb://` 可能命中到心跳未及刷新的实例（超时/503 面扩大）；属观察项，尚未造成业务中断。
- **遗留**：并入待办 10 的跨网治理（WG MTU / 云内自建 Nacos 集群替代跨网部署）。

### C. 配置生效与文件传输类

#### C1. scp 传错目录，compose 旧文件生效

- **现象**：`scp compose-aliyun.yml ...:/opt/dcp/seatunnel-config/` 把 compose 文件误传到配置子目录；`docker compose up -d` 读的是旧 compose，force-recreate 后挂载仍缺新文件。
- **根因**：scp 目标目录笔误 + 未验证落点就执行后续操作。
- **修复**：`mv` 回正确位置再 force-recreate；用 `docker inspect --format '{{range .Mounts}}{{.Source}}{{println}}{{end}}'` 验证挂载落点。
- **通用启示**：多机文件分发后必须先验证"目标路径 + 文件内容"再执行依赖它的操作；云机上 compose 有多个同名文件时最容易读错。

#### C2. compose 挂载变更必须 force-recreate

- **现象**：volumes 增加挂载后 `up -d` 不生效。
- **根因**：`docker compose up -d` 只重建"定义有变化"的容器，挂载路径变化不会触发重建。
- **通用启示**：改挂载/env/mem_limit 后统一 `up -d --force-recreate`，并用 `docker inspect` 验证。

### D. 引擎/中间件配置语义类

#### D1. SeaTunnel checkpoint S3 的 SPI 匹配陷阱

- **现象**：`checkpoint.storage.type: s3` 启动即报 `Could not find any factories that implement CheckpointStorageFactory`。
- **根因**（javap 反编译确认）：`CheckpointService` 用配置的 `storage.type` 作 identifier 调 SPI 发现，按 `factoryIdentifier().equals(identifier)` 匹配，而 `HdfsStorageFactory.factoryIdentifier()` 硬编码返回 `"hdfs"`（另一实现为 `"localfile"`）——**外层 type 是 SPI 工厂标识，不是存储类型**。真正的存储类型在 `plugin-config.storage.type`（大写 `FileConfiguration.valueOf` 分派 S3/OSS/COS/HDFS）；且 `s3.bucket` 值必须以 `s3a://` 开头才走 S3AFileSystem（否则走已废弃的 s3n），`fs.s3a.*` 前缀键原样透传给 hadoop conf。
- **修复**（seatunnel.yaml）：
  ```yaml
  checkpoint:
    storage:
      type: hdfs            # SPI factoryIdentifier，只有 hdfs/localfile
      plugin-config:
        storage.type: s3    # 实际存储类型
        s3.bucket: s3a://seatunnel-checkpoint
        fs.s3a.endpoint: http://10.66.0.2:9000
  ```
- **通用启示**：SPI factoryIdentifier 与业务配置语义分离的模式很常见（type 字段名同但含义不同），配置语义必须查代码确认而非依赖文档直觉；"按文档配了却报工厂找不到"优先怀疑 identifier 匹配。

#### D2. SeaTunnel restore 必须 -c 与 -r 同带

- **现象**：`seatunnel.sh -r {jobId}` 单独执行报 "SeaTunnel job executed failed"。
- **修复**：`seatunnel.sh -c job.conf -r {jobId}` 同时给出；恢复后沿用同一 jobId，checkpoint 编号连续（实测 20/21/22）。
- **通用启示**：CLI 参数组合约束不明时，失败信息常不准确，直接看命令解析源码。

### E. 验证方法误判类

#### E1. console-consumer 缺 --from-beginning 误判消费异常

- **现象**：`kafka-console-consumer` 报 TimeoutException，误以为消费链路异常。
- **根因**：默认从 latest 读，15 秒无新消息自然超时；协议层实际正常。
- **修复**：加 `--from-beginning` 消费历史消息验证。
- **通用启示**：Kafka 验证先确认 offset 语义（latest/earliest），再判断异常。

#### E2. FakeSource 有限 split，不适合恢复演练

- **现象**：task 宕机自动恢复后 FakeSource 0 个新 split，误以为恢复失败。
- **根因**：FakeSource 是有限 split 语义，恢复后没有剩余 split 可分配。
- **修复**：改 Kafka source 演练——恢复后 `Seeking to offset 5` 断点续采，真实验证不重不漏。
- **通用启示**：演练/测试的 source 选择必须匹配演练目标；"恢复成功"与"有新数据产出"是两个维度，要分开断言。

#### E3. 消费验证用错 topic：源表名 ≠ sink topic

- **现象**：场景①②验证中 SinkWriteCount 持续增长（1→2→9），但三机 Kafka 消费 `dcp.cdc_watchdog_src`（源表名）始终 0 条，误判 sink 链路断、甚至怀疑"消息落点不明"，浪费大量排查时间。
- **根因**：sink 实际写入的 topic 是 `cdc_st_task.topic` 的配置值（本例为 `dcp.watchdog_test`），与源表名（`dcp.cdc_watchdog_src`）不同名；按"源表名=topic"的命名直觉消费永远读不到。历史消息（30xxx~37xxx 全部批次）其实一直完整保存在 `dcp.watchdog_test` 中。
- **修复**：`SELECT topic FROM cdc_st_task` 确认真实 sink topic 后消费，消息全量可见。
- **通用启示**：验证消费前先查控制面配置（DB），不要按命名直觉；源表、逻辑表、sink topic 是三个独立概念，"job 名里的源表名"只标识采集对象、不代表投递目的地。

### F. 操作纪律类

#### F1. 终端与远程操作工具链注意事项

- 终端 `grep` 无匹配时输出异常（zsh 回显命令、空输出）→ 一律重定向到文件再 `cat/grep` 中转；
- `docker compose` 必须显式 `-f` 指定文件名；
- 容器 sh 无 `/dev/tcp`（bash 特性），连通性探测改用 `nc` 或应用层验证；
- macOS `base64` 解码用 `-D`（非 `-d`）；
- 腾讯云无密钥登录，用 expect 封装密码交互（scp/ssh/sudo 一条龙）。

#### F2. 网速实测驱动的传输决策

- 实测：家宽→腾讯云 1.5MB/s，1.85G 镜像 tar 需 21 分钟；源码 452MB 仅 5 分钟。
- 决策：云机构建镜像（端到端约 20 分钟），后续迭代只传源码 diff。
- **通用启示**：跨网络大镜像传输前先实测带宽，按"传输时间 vs 构建时间"取小者，不要凭直觉。

#### F3. scp 传 jar 传成目录，容器内 bundle 缺失

- 现象：云机 `/opt/dcp/bundles/*.jar` 全是目录（`drwxr-xr-x`）而非文件，worker 日志报"本地业务 jar 不存在"，`bundles=0`。
- 根因：scp 上传 jar 时目标路径已存在同名目录（可能是容器/某次部署自动为挂载源创建的目录），scp 把文件传进了目录里而非覆盖。
- 排查：`ls -la /opt/dcp/bundles/` 看目录标志位；`docker logs worker | grep BundleAssembler` 看装载失败原因。
- 修复：删掉假目录 → 重传 jar → force-recreate worker → 日志确认 `bundles=4`。

#### F4. 环境变量未显式声明 → yml 默认值静默生效

- 现象：worker 只装载 1 个 bundle（`bundles=1`），sync/indexer/outlet ns 空转；挂载了 jar 但从未装载。
- 根因：`dcp.worker.bundles` 在 compose 未声明时回退到 application.yml 默认值（只有 filesync 一个），Spring 环境变量缺失不会报错，默认值静默生效。
- 启示：部署"按池裁剪"的配置项（bundles/namespaces/kafka 映射）必须在 compose 里显式声明，不能依赖 yml 默认值；上生产前用日志验证实际装载（"骨架启动 bundles=4"），不要只看挂载。

#### F5. expect 并发 spawn 耗尽 pty

- 现象：连续多次 expect 脚本报"The system has no more ptys"。
- 修复：`pkill -f "expect /tmp"` 清理残留后重试；多次 expect 调用之间留间隔或复用同一脚本。

## 二、部署验证出的开发/设计阶段问题

> 这类问题在开发/设计阶段已存在，部署演练将其暴露或实证。每项含「设计现状 → 部署实证 → 修正与开发待办」。

### 1. 【设计假设不成立】SeaTunnel 2.3.12 master 宕机后 job 不自动恢复

- **设计现状**：采集任务依赖"SeaTunnel Zeta HA 集群 master 宕机自动恢复"的假设。
- **部署实证（H14）**：杀 master 后新 master 1 秒接管，但 RUNNING job 从列表消失、不自动恢复；需显式 savepoint + `-c -r` restore，恢复后同一 jobId、checkpoint 编号连续。
- **修正**：README 已沉淀"master 宕机需显式恢复"运维要点。
- **开发待办**：控制面需要两件事——① 定期 savepoint 调度（对 RUNNING 采集任务）；② 巡检检测 job 丢失并自动 restore。当前平台若只"提交后放任"，master 故障 = 任务静默消失。

### 2. 【设计预测被实证】checkpoint 容器本地存储随容器消失

- **设计现状**：设计阶段已预警"checkpoint 在容器本地 → 重启/OOM/升级即丢失 → 全量重发"（防护清单第 1 条：checkpoint 持久化到分布式存储）。
- **部署实证**：容器 OOM（exit 137）真实发生，本地存储路径随容器消失的风险成立；演练中 task 迁移后从 MinIO 恢复（isRestored=true）验证了共享存储方案。
- **修正**：checkpoint 已迁移 MinIO S3（`s3a://seatunnel-checkpoint` + namespace 隔离）。
- **开发待办**：启停纪律落地——启停脚本总是带 savepoint + 启动前断言 savepoint 存在；无 savepoint 时必须 initial 模式（禁止 `startup.mode=latest` 静默丢历史）。

### 3. 【设计缺陷】提交入口单点：客户端成员列表默认 localhost

- **设计现状**：`hazelcast-client.yaml` cluster-members 默认只有 `localhost:5801`。
- **部署实证（H16）**：本机节点宕机则提交即断（集群还活着但无人可提交）。
- **修正**：客户端成员列表改三节点（mac.wg + 10.66.0.2 + 10.66.0.3:5801）。实测 kill Mac 后阿里云/腾讯云提交成功：客户端先试 mac.wg 被拒（Connection refused）→ 自动 failover 本地引擎 → 集群 Members [2]。
- **通用设计原则**：客户端入口配置必须与引擎成员列表一致，**框架默认值（localhost）在生产拓扑下不可信**。

### 4. 【资源预算低估】双 JVM 同容器的内存核算

- **设计现状**：按引擎 heap 192m 预算容器 768m/1g。
- **部署实证**：提交/savepoint 客户端是独立 JVM，同容器运行后 768m 触发 cgroup OOM 杀客户端（SAVEPOINT_EXIT=137）。
- **修正**：mem_limit 1536m。
- **设计反馈**：资源预算表需按"引擎常驻 + 客户端瞬态双 JVM"核算；平台若以"每个 job 一个提交进程"的方式运营，还要按并发提交数放大。

### 5. 【文档与实现脱节】表结构与配置语义

- **表结构**：按文档/记忆写的测试数据用 `uk_uid` 列，实际 TiDB 表 7 列无此列（DESC 实查纠正）——文档结构与实例脱节会导致测试数据、演练脚本集体失效。
- **配置语义**：checkpoint 按"直觉文档"配 `type: s3` 必失败（见 D1），配置样例必须实测验证后入库。
- **通用纪律**：文档中的表结构、配置样例要"过实例"（DESC/docker exec 实测），不能只过记忆。

### 6. 【网络模型遗漏】开发机作为集群节点的容器视角

- **设计现状**：网络模型只覆盖"三机宿主 WireGuard 互通"，未覆盖"Mac 容器"这一层。
- **部署实证**：Mac 容器内 10.66.0.1 黑洞，Kafka leader 在 Mac 时消费链路断（checkpoint FAILED → pipeline CANCELING）。
- **修正**：extra_hosts `mac.wg:host-gateway`，云机侧不动。
- **设计反馈**：网络设计要覆盖"容器视角"（容器内怎么解析、怎么路由），不只是"宿主视角"；开发机兼作集群节点时要单列网络处理。

### 7. 【测试设计缺陷】演练 source 与演练目标不匹配

- **设计现状**：演练脚本用 FakeSource。
- **部署实证**：FakeSource 有限 split，task 恢复后 0 新 split，"是否续采"无法验证。
- **修正**：改用 Kafka source 演练，`Seeking to offset N` 实证断点续采不重不漏。
- **设计反馈**：HA 演练脚本的 source 必须能产出"跨故障点的增量数据"，否则恢复验证是空转。

### 8. 【契约不一致】规则条件键 "value" vs "val" 静默不命中

- **设计现状**：DrlGenerator(三端共用执行器)读 `conds[].val`，前端 RuleEdit/mockLib 也用 val；但历史资产数据(tag_rule.def_json)里条件键是 "value"(早期前端/手工创建遗留)。
- **部署实证(打标批次端到端)**：批阶段 OK 但 Redis/tag_fact_view/dcp.tag.events 三路全空；追查发现 DRL 生成条件 `status == ""`(val 缺失取空串)→ 恒假 → **静默无输出、无任何告警**。

- **开发待办**：① DrlGenerator 兼容读取(缺 val 回退 value)或发布时统一规范化；② "批完成但 0 命中"可观测性(批阶段统计命中数，0 命中打 warn)——执行器静默不命中无法区分"无数据"与"条件恒假"。

### 9. 【ts 域错配】TiCDC enable-tidb-extension 下 canal-json 顶层 ts=毫秒，TSO 在 _tidb.commitTs

- **设计现状**：ProductionMessageDecoder 取顶层 ts 作 tso(注释声称是 TSO)；单测样例混用 TSO/毫秒两种域。
- **部署实证(打标流阶段)**：批 OK 后流阶段静默无输出——毫秒 tso ≪ TSO 域 T0 → 会话过滤(`d.tso() > t0`)全部丢弃；TIDB_WATERMARK 被解码为 OTHER → 水位不推进。消费组位点正常前进，无任何异常日志(与索引器 CanalJson 修复同源问题)。
- **修正**：解码器 tso 优先 `_tidb.commitTs` 回退顶层 ts；TIDB_WATERMARK → WATERMARK(`_tidb.watermarkTs`)；新增 3 单测；三机 worker 分发重启后重做批，流阶段 UPDATE 秒级三路输出。
- **开发待办**：TiCDC 协议变体(enable-tidb-extension)写入文档；测试样例统一用真实抓包形状(ts=毫秒 + _tidb.commitTs=TSO)。

### 10. 【环境脆弱】开发机休眠导致 TiDB TSO 停摆 + TiCDC 卡死

### 11. 【引擎行为缺陷】无 checkpoint 时静默降级 initial，backend 回退分支永不触发

- **设计现状**：backend `startOne` 回退分支（restore 失败 → 弃旧 jobId 换新 + initial 全量重采）只捕 IllegalStateException；而 SeaTunnel 2.3.12 `RestJobExecutionEnvironment.getJobConfigParser` 在 `isStartWithSavePoint=true` 且 `getLatestCheckpointData` 返回空时**静默返回空 list 走 initial（不抛错、同 jobId）**——回退分支永不触发。
- **部署实证（场景②初验）**：删 MinIO checkpoint 后 stop-job，watchdog 以同 jobId + isStartWithSavePoint 提交，引擎静默 initial（同 jobId、seq 36xxx 重发），与"restore 失败 → 换新 jobId 回退 initial"的契约不符。字节码反编译确认根因在引擎侧，backend 逻辑无错。
- **修正**：ASM 补丁 `seatunnel/PatchSavepointGuard.java` 在 `new MultipleTableJobConfigParser` 前注入 guard：`isStartWithSavePoint && list.isEmpty()` → throw `IllegalArgumentException("restore failed: start with savepoint but no checkpoint state found for this job, fallback to initial full re-sync")`；REST `ExceptionHandlingFilter` 将其转 HTTP 400 + error body → `SeaTunnelClient.submitJob` 统一包 IllegalStateException → 回退分支触发。补丁工艺要点：必须用 `COMPUTE_FRAMES + ClassReader.SKIP_FRAMES + 自定义 getCommonSuperClass`（用被 patch 的 fat jar 自身作 URLClassLoader 解析类型层级、失败回退 Object）；用 `COMPUTE_MAXS + 手动 visitFrame` 会产出非法 StackMapTable（ClassFormatError），靠 `java -Xverify:all` 加载测试拦截。
- **场景②复验（补丁后）**：01:50:38 watchdog 检出 CANCELED → 01:50:40 restore 提交 400（补丁报错文本原样出现在 backend 日志）→ 回退 → 新 jobId=179104984001801（=now 毫秒×100+taskId）initial 全量 9 行，seq 38001-38009 单调、`__src_pos` 全 `mysql::0:`，Kafka 不重不漏。
- **开发待办**：补丁 jar 固化进引擎镜像构建流程（见待办 9）。

### 12. 【拆分空窗】微服务拆分后多组前端接口无归属：gateway 无路由/新服务未补位

- **设计现状**：控制面四域拆分（backend 迁出域移除、独立服务承载），但 gateway 路由表与新服务接口没有同步补齐。
- **部署实证（2026-10-04 业务冒烟侦察，线上带 token 逐接口实测）**：

  - `/api/subscriptions`（订阅中心）、`/api/tags/**`（标签树/资产打标）、`/api/assets/**`（资产详情/预览）→ 均在拆分前的 backend-legacy，新架构未补位 → 兜底 backend → 9000。

- **修正**：见待办 11/13/14（gateway 补路由、部署 Neo4j、迁出域接口补位）。
- **通用启示**：服务拆分必须把「前端实际调用的全部端点」作为拆分清单的验收维度——按域拆代码容易，按请求路径拆路由表容易漏；拆分后要做一次全量端点 → 服务 → 路由的对照审计，而不是只看新接口是否可用。

### 13. 【构建缺陷】dcp-worker 未开 -parameters 编译参数，带 @RequestParam 接口全部 400

- **现象**：直连 dcp-worker 8097 调 `/api/scheduler/metrics?ns=sync`、`/alerts`、`/instances`、`/ops` 均返回 `code:400 Name for argument of type [java.lang.String] not specified... compiler uses the '-parameters' flag`；仅无参接口（`/namespaces`、`/audits`）正常。
- **根因**：SchedulerRestController 的 `@RequestParam String ns` 等未显式写 name，而 dcp-worker 模块编译未启用 `-parameters`，运行时反射拿不到参数名 → Spring 无法绑定。
- **修正**：dcp-worker pom 的 compiler 配置加 `<parameters>true</parameters>`（或接口显式 `@RequestParam("ns")`），重建镜像分发。见待办 12。
- **通用启示**：Spring Boot 3.x 依赖 `-parameters` 做参数名绑定；多模块工程里父 POM 统一开此开关，新模块接入时先跑一次"带查询参数的 GET 接口"冒烟。

### 14. 【链路异常】消费落地全量进死信：dcp.cdc.target_db.t_user 死信 3.1 万条

- **现象**：`/api/sync/dlt` 实测 total=31728（topic `dcp.cdc.target_db.t_user` 分区 0，offset 29299→29343 仍在增长），status 全 PENDING、logical_table=未知、无 error_msg；TiDB `target_db.t_user` 表仅 1 行，与 Kafka 侧持续产出严重不符。
